# テスト / TDD の役割ノート

profit_band の「別 pane に表示される」バグ修正（`indicator_ui`）を題材に整理した、
テストと TDD の役割に関する学習メモ。汎用知見のため特定モジュールに依存しない。

## 1. テストには2つの役割がある

1. **動作確認** — 今このコードが正しく動くか。書いた直後に効く。
2. **回帰防止** — 将来も壊れないか。ずっと効き続ける。

長期的な価値は **2 のほうが大きい**ことが多い。バグは「最初に作り込む」より
「直したものが後で再発する」ほうが厄介で、人間のレビューは見落とすが、
テストは毎回・機械的に同じ箇所を見張る。

## 2. テストは「実行可能な仕様書」である

- 普通の仕様書（Word / Markdown）は書いた瞬間から実装とズレ始め、誰も気づかず陳腐化する。
- テストで書かれた仕様は、**ズレた瞬間に赤くなって教えてくれる**＝常に実装と一致が保証された仕様書になる。

実務の勘所：
- **テスト名は仕様文として書く**：`test('returns true')` ではなく
  `test('profit_band は価格 pane へ重畳する')`。
- **「なぜ」をコメントに残す**：値そのもの（`'overlay'`）はコードを見れば分かるが、
  「別 pane だとバグる」という理由はテストにしか残せない。

## 3. 「テストとコードが違う」には2パターンある

### パターン1：コードが仕様（テスト）から外れた
**自動で気づける。** テストが赤くなる。CI で毎回回す理由。
例：誰かが `placement` を `'overlay'` → `'pane'` に戻すと
`assert.equal(d.placement, 'overlay')` が失敗する。

### パターン2：テスト自体が実態とズレている（こちらが怖い）
**テストは緑なのに挙動はバグっている。** 赤くならないので仕組みで炙り出す：

1. **わざとコードを壊す（ミューテーション）**：1か所おかしくしてテストが赤くなるか確認。
   赤くならなければ、そのテストはそこを見張っていない＝飾り。
   「一度も失敗を見たことがないテストは、何もテストしていない可能性がある」。
2. **TDD で「先に赤」を見る**：実装前に必ず一度失敗させてから直す。
3. **カバレッジで死角を見る**：未実行の行＝仕様が書かれていない場所。

## 4. TDD が固有に保証するもの

「revert を捕まえる」性質は、テストが**存在すること**の効果であり TDD 固有ではない
（後から書いたテストでも捕まえる）。

TDD が固有に保証するのは **パターン2 の防止**：
実装前に一度赤を自分の目で見るので、
**「このテストは本当に違反を検知できる（配線ミス・空アサーションではない）」が証明済み**になる。

> - テストがある → revert は赤くなる
> - TDD で書いた → その「赤くなる」が**信頼できる**（一度実際に赤を見たから）

## 5. TDD でも消えない注意点：「正しい層」をテストしているか

TDD は「テストが**検査している対象**を確実に見張る」ことは保証するが、
「**検査している対象が正しい層か**」は保証しない。これは設計判断。

### 今回の実例と残る穴
追加した回帰テストは `catalog.js` の定数を見ている：

```js
// web/tests/catalog.test.js
test('catalog: profit_band is overlaid on the price pane (not a separate pane)', () => {
  const d = get('profit_band');
  assert.equal(d.placement, 'overlay');
});
```

しかし「その値が実際に pane 0 への重畳になる」変換は別ファイルにある：

```js
// web/js/adapter/front/indicator_controller.js
const opts = { pane: def.placement !== 'overlay', ... };
```

→ この**変換ロジック側**が壊れると、カタログテストは緑のままバグが再発する。
完全に塞ぐには `controller → renderer` を通した結果まで確認する統合テスト
（`chart_renderer.test.js` の層）を別途用意する。

## まとめ

- コードがズレた → **赤で自動検知**
- テストがズレた → **わざと壊して赤を確認／赤を一度見る／正しい層で検査**
- バグ修正の習慣：**修正 + その間違いを禁止する回帰テストを1本**をワンセットにする
- 問いの立て方：「テストが緑だから安心」ではなく
  **「このテストは何を壊したら赤くなるか？」** を問う
