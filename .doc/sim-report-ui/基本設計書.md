## 2. プロジェクト概要

> 出力元：S-1 要件分析と設計方針決定

### 2.1 システム概要

- **位置付け**：`simulator` バウンデッドコンテキストが算出する 1 run（および IS/OOS 2 区間）の
  バックテスト結果を、ブラウザ上でマルチビュー可視化・相互ハイライト・ヒートマップ・
  インタラクティブグラフ・区間比較判定として閲覧する READ-ONLY ビューア。
- **解決する業務課題**：MT5 Strategy Tester の静的 HTML レポート（`ReportTester-900005560.html`）
  では、チャート（売買タイミング）と集計指標（時間帯別損益・相関・保有時間）・取引明細が
  分離しており、過剰最適化の兆候（IS 黒字 ⇄ OOS 赤字）を横断的に確認できない。本ビューアは
  チャートと全レポート要素をデータ接続し、区間切替で IS/OOS を一画面比較する。

### 2.2 開発目的・背景

- **背景**：試作 `prototype_260623-02`（単一 HTML 1200 行・`prep_data.py` 327 行）で
  SPEC 4 点＋OOS 統合の到達点が確認済み。試作は xlsx 直読み・全再描画・10MB JSON 等の
  割り切りを含む使い捨て品質であり、本番化には**データソース境界の確定**と
  **クリーンアーキ整合**が必要。
- **達成したい目標**：
  - G-1：試作の UX（区間切替・双方向ハイライト・ヒートマップ・グラフ群・比較判定）を本番品質で再現。
  - G-2：既存 `simulator` エンジン・既存データ（oracle xlsx / bars CSV / marketdata / fixtures）を
    **1 バイトも変更せず**、新規モジュール追加のみで構成。
  - G-3：別アクター `indigators/indicator_ui`（テクニカル分析専用）に相乗りさせず独立モジュール化。

#### 制約条件（技術 / 運用）

- **C-1（最優先・絶対遵守）データ read-only**：oracle xlsx・bars CSV・marketdata・fixtures・confirmation は
  読み取り専用。書込/改変/移動/再生成しない（NFR-01）。
- **C-2 既存コード無改変**：`simulator` の domain/usecase/adapter（既存）/main、`indigators/indicator_ui` の
  committed コードを変更しない。新規ファイル追加で構成する（NFR-02）。
- **C-3 アクター完全分離**：本ビューアを `indicator_ui` に相乗りさせない。`simulator/report_ui/` として新設する。
- **C-4 技術スタック不変**：バックエンドは既存 `simulator`（純 Python・標準ライブラリ＋既存依存 openpyxl 等）、
  フロントは vendor の lightweight-charts standalone・chart.umd.js に揃える。バージョンの無断変更禁止。
- **C-5 vendor 再利用**：lightweight-charts は vendor ライブラリとして再利用するが、`indicator_ui` の実装コード
  （ChartRenderer 等）には一切依存しない。

#### 設計上の課題と技術的リスク（詳細は §9）

- 課題①（最重要）：データソース境界 — 試作 `prep_data.py` の生成責務を report_ui の新規アダプタ/ユースケースに
  置くか（案 a）、`simulator` 本体エンジンの run 出力を消費するか（案 b）。§3.2 で代替案比較のうえ推奨案を確定。
- 課題②：試作 payload（2 区間 bars 込み 10MB・全再描画）の本番での扱い（性能・転送量）。
- 課題③：エンジン出力（`BacktestResult`）に非含有の派生データ（report 指標テキスト・生注文 orders・
  各種 agg 集計・MFE/MAE）の算出責務の配置。

## 3. システムアーキテクチャ

> 出力元：S-1 採用パターン選定 ／ S-2 アーキテクチャ設計

### 3.1 全体構成図

本機能は「データ生成（バックエンド・Python）」と「データ消費（フロント・ブラウザ）」を
JSON 契約（`report.json`）で疎結合する。バックエンドは既存 `simulator` クリーンアーキの内向き依存を踏襲する。
（★＝本機能で新規追加。既存要素は無改変。）

```
[既存] bars_m1_is.csv / bars_m1.csv          [既存・READ-ONLY] oracle xlsx（突合の正・本番経路では非依存）
         │ (read-only)
         ▼
[既存] simulator main.build_interactor → Interactor.execute(request)
         │   ＝ committed IF のみ使用（reconcile_is.py と同一経路・MT5 と bit-exact 一致 実証済）
         ▼
[既存] BacktestResult { trades, deals, equity_curve, balance_curve, stats }
         │   (1 区間ぶん。IS / OOS で 2 回実行)
         ▼
★[usecase] BuildReportPayload UC      ← BacktestResult（IS/OOS）→ 報告ドメインモデルへ集約
         │   ・FIFO ペア確認 / MFE・MAE バー走査 / 時間帯・曜日・月別・ヒートマップ集計
         │   ・保有時間バケット / 散布図 / balance_curve / drawdown 系列 / 区間 summary
         │   ・degradation（既存 run_is_oos の MetricDegradation 思想を再利用）/ verdict
         │   ・依存: domain + 既存 usecase（run_is_oos の比較ロジック）のみ
         ▼
★[usecase port] ReportPayloadPresenterPort（新規 Output Boundary・既存 Port 非拡張）
         ▼
★[adapter] ReportUiPresenter           ← 報告ドメインモデル → JSON 契約（segments.{is,oos}…）へ純変換
         │   ・依存: usecase + domain + stdlib（json）のみ
         ▼
★ report.json（生成物・新規パス web/data/ 配下に出力）   ← C-1: 既存データを上書きせず新規パスのみ
         │
         ▼  GET（既存 static 配信・no-cache 簡易サーバ）
★[front] report_ui web（vendor: lightweight-charts / chart.umd.js）
         │   ・マルチビュー（FR-01）/ チャート別ウィンドウ・インジケーター（FR-02）
         │   ・取引明細（FR-03）/ 双方向ハイライト（FR-04）/ ヒートマップ（FR-05）
         │   ・グラフ群（FR-06）/ 区間切替（FR-07）/ 比較判定タブ（FR-08/09）
         ▼
[ブラウザ] 閲覧者
```

> 注：oracle xlsx は「エンジン出力が MT5 と一致することを保証する突合の正（confirmation）」として
> 既に役割を終えており、本番 report_ui の生成経路は **bars CSV → エンジン → BacktestResult** を一次入力とする。
> xlsx 直読みは試作の便宜であり本番経路の所与にしない（§3.2 案 b 採用根拠・§10.2）。

### 3.2 アーキテクチャパターン選択理由

#### 3.2.1 全体アーキテクチャパターン

- **採用：クリーンアーキテクチャ（既存 `simulator` 踏襲）＋ Presenter/JSON 契約による front 疎結合**
- **比較した代替パターン**：

  | パターン | 概要 | 採否 |
  |---|---|---|
  | クリーンアーキ（採用） | domain→usecase→adapter→framework の内向き依存。Output Boundary（Port）で front を隔離 | 採用 |
  | レイヤードMVC（front にロジック集約） | 試作のように front（HTML/JS）で集計・判定まで担う | 棄却 |
  | BFF（専用バックエンドサービス新設） | report 専用の独立 Web サービスを別プロセスで新設 | 棄却 |

- **採用根拠**（公式設計原則：Martin 2017『Clean Architecture』／プロジェクト規約 `BACKTEST_CLEAN_ARCH.md`）：
  - 要件適合：既存 `simulator` がクリーンアーキで構築済み（`ReportPresenterPort` / `JsonPresenter` の前例、
    `run_is_oos.py` の IS/OOS オーケストレーション前例）。同一パターンで Port を追加するのが最小差分。
  - 集計・判定ロジックを front に置く（レイヤードMVC）と、過剰最適化判定という**ドメイン知識**が
    ブラウザ JS に散逸し SRP（アクター「レポート閲覧者」）違反。試作はこの割り切りを採っており本番では是正する。
  - BFF 新設は C-4（技術スタック不変・新規プロセス追加なし）に反し運用コスト増。既存配信機構で足りる。

#### 3.2.2 データソース境界の判断（最重要・推奨案確定）

- **論点**：試作 `prep_data.py` は oracle xlsx を直読みし、FIFO ペアリング・MFE/MAE バー走査・各種集計・
  degradation/verdict を計算する。本番でこの生成責務を、(a) report_ui 側の独立アダプタ/ユースケースに置くか、
  (b) `simulator` 本体エンジンの run 出力を消費するか。

- **代替案比較**：

  | 評価軸 | 案 a：xlsx を report_ui 内で直読み | 案 b：エンジン run 出力（BacktestResult）を消費 ★推奨 |
  |---|---|---|
  | C-1 read-only 適合 | 適合（xlsx 読むだけ） | 適合（bars CSV 読むだけ。xlsx 非依存） |
  | C-2 既存無改変 | 適合（新規モジュールに閉じる） | 適合（committed IF `build_interactor`/`execute` のみ使用） |
  | データの正統性 | xlsx は MT5 外部生成物＝当エンジンの一次出力でない。**本番に MT5 export を恒久依存**させる | エンジン出力が一次。MT5 とは bit-exact 一致を確認済（confirmation） |
  | 再現性・自動化 | run のたびに人手で xlsx を export・配置する運用が固定化 | bars CSV から自動再生成。run パラメータ変更に追従可能 |
  | クリーンアーキ整合 | adapter が外部 xlsx スキーマに密結合。エンジンを迂回する第 2 経路が発生 | UC-001 の正規出力を UC-004（レポート）が消費する正準フロー |
  | 派生データ（report 指標/orders/agg） | xlsx に同梱の表示テキストをそのまま転記できる（実装は容易） | `BacktestStats`＋`trades` から report_ui 側 UC で派生算出（実装は要追加） |
  | 試作との差分 | 最小（prep_data.py をほぼ移植） | 中（生成経路を build_interactor 経由へ置換） |

- **推奨案：案 b（エンジン run 出力を消費）。** ただし `BacktestResult` に非含有の派生データ
  （report 指標テキスト・各種 `agg`・MFE/MAE）は report_ui 側の新規 UC（BuildReportPayload）で
  `BacktestStats`＋`trades`＋`bars` から**派生算出**する。
  生注文 `orders`（FR-03 の `state`/`comment` を含む 11 列）は `BacktestResult`（trades/deals/stats のみ・
  生注文テーブル非保持を実証）から再構成可能か未実証であり、案 b で満たせるかは詳細設計で確定する
  （§9.3 TBD-08・R-7。証拠不在の前提を所与にしない）。

- **採用根拠**（実務的推奨／仮説 ＋ 実証）：
  - 実証 1：`reconcile_is.py` が committed IF（`build_interactor` → `Interactor.execute`）のみで
    bars_m1_is.csv を実行し、trades 5224・net +11370・balance 21370 が MT5 oracle と
    **建てイベント lockstep 100%・件数一致**（`NOTE.md` ✅）。OOS も bars_m1.csv で 2438/−4020/5980 一致。
    ＝案 b の技術的実現可能性は実証済。
  - 実証 2：`domain/trade_record.py` の `TradeRecord` は side/volume/entry_time/exit_time/entry_price/
    exit_price/`pnl()` を保持。試作 `prep_data.py` の trades 構造（FIFO ペア・損益・保有秒）は
    エンジン trades から再構成可能。
  - 棄却理由（案 a）：xlsx を本番経路に恒久依存させると、run パラメータ変更のたびに MT5 export が必要となり
    自動再生成性を失う。また外部 xlsx スキーマへの adapter 密結合はエンジンを迂回する第 2 経路を生み、
    SSOT（単一の真実の源＝エンジン出力）を二重化する。
  - 棄却理由の限定（案 a の部分的妥当性）：xlsx の `report` 指標テキスト（PF/Sharpe/Z-Score 等の表示値）は
    MT5 が確定した参照値であり、案 b の派生算出値との**桁・丸めの一致検証**に有用。本番は案 b を一次とし、
    xlsx は「検証用の突合の正」として confirmation に留める（恒久の生成経路にしない）。

#### 3.2.3 IS/OOS 比較・判定ロジックの再利用

- **採用：既存 `usecase/run_is_oos.py` の `MetricDegradation`（ratio・delta 両格納）思想を report_ui UC で再利用。**
- **代替**：report_ui 内で degradation/verdict を独自再実装（試作 `prep_data.py` のロジック移植）。
- **採用根拠**（プロジェクト規約）：既存 `run_is_oos.py` に IS/OOS 区間実行（`RunSegment` コールバック DI）・
  劣化指標が確立済。verdict（過剰最適化判定）の閾値ロジック（試作：IS 黒字⇄OOS 赤字／OOS PF<1.0／PF 比<0.7／
  勝率差<−5pt／期待値正→負反転）は report_ui の表示要件に固有のため report_ui UC 側に置くが、
  指標劣化の計算構造は既存 `MetricDegradation` を踏襲し二重実装を避ける。

### 3.4 レイヤー構成・責務分担

| レイヤー | 要素（★＝新規） | 責務 | 依存先 | 出典／根拠 |
|---|---|---|---|---|
| domain | 既存（Bar/TradeRecord/BacktestStats 等） | 不変条件・pnl() 等の計算規則 | なし（最内） | 既存・無改変 |
| usecase（境界） | ★`ReportPayloadPresenterPort`（新規 Output Boundary） | 報告モデル→出力の境界抽象。既存 `ReportPresenterPort` は非拡張（ISP） | domain のみ | 公式（DIP/ISP・Martin 2017） |
| usecase（UC） | ★`BuildReportPayload`（新規 UC） | BacktestResult(IS/OOS)→報告ドメインモデル（trades 派生・agg 集計・degradation/verdict） | domain＋既存 `run_is_oos`（MetricDegradation） | 公式（SRP・アクター「レポート閲覧者」） |
| adapter（変換） | ★`ReportUiPresenter`（新規 Presenter） | 報告モデル→JSON 契約（§5）へ純変換・ファイル書出（既存 JsonPresenter と同型 I/O） | usecase＋domain＋stdlib | 既存 `JsonPresenter` 前例 |
| adapter（生成トリガ） | ★`export_report_payload`（新規ツール・main 無改変） | committed IF（build_interactor/execute）で IS/OOS を run し UC→Presenter を結線 | 既存 main＋上記 UC/Presenter | 既存 `reconcile_is.py`／`CHART_TRADE_MARKERS` C-1 解決の前例 |
| framework（殻） | 既存 static 配信（無改変・案 A） | 生成 JSON の配信 | adapter へ | `CHART_TRADE_MARKERS` §12.4 案 A 前例 |
| front（report_ui web） | ★`simulator/report_ui/web/`（新規一式） | JSON 消費・全 UI 描画・区間切替・双方向ハイライト | vendor（lwc/chart.js）のみ | C-3/C-5（indicator_ui 非依存） |

- **依存方向**：framework → adapter → usecase → domain（内向き）。front は JSON 契約のみに依存し
  バックエンド実装に非依存。vendor は front の最外（上流）として隔離。
- **アクター分離（SRP）**：本モジュールのアクターは「レポート閲覧者」。`indicator_ui` のアクター
  「テクニカル分析者」とはモジュール境界（`simulator/report_ui/`）で完全分離する（C-3）。

## 4. 機能設計

> 出力元：S-3 機能設計

### 4.1 機能一覧・優先度

実装は機能単位の 5 段階で進める（アーキは本書で 1 度に整合・実装のみ段階移植）。優先度＝段階順。

| F-1b | チャート別ウィンドウ・インジケーター | Balance／Drawdown を独立 lwc インスタンスで縦積み・時間軸相互同期・クロスヘア同期・高さ可変・最大化 | ① | FR-02 |
| F-2 | 取引明細⇄マーカー双方向ハイライト | 取引明細テーブル（11 項目・ソート）と売買マーカーの双方向 hover ハイライト | ② | FR-03/FR-04 |

### 4.2 機能詳細仕様（主要機能のみ）

- **F-1b チャート別ウィンドウ・インジケーター（FR-02）**
  - 入力：選択区間の `bars`（OHLC）・`agg.balance_curve`・drawdown 系列。
  - 出力：ローソク足／Balance（エリア系列）／Drawdown（0 基準ベースライン系列）の 3 ウィンドウ縦積み。
  - 前提：3 ウィンドウは別 lwc インスタンス。可視論理レンジを相互同期（どれをズーム/パンしても時間軸一致）。
  - 後条件：時間軸ラベルは最下段（DD）のみ。既定は取引全期間表示。
  - 例外：bars 欠落区間はギャップ表示（補間しない）。

- **F-2 双方向ハイライト（FR-04）**
  - 入力：選択区間の `trades`（id・entry/exit 時刻・価格・side・損益）。
  - 出力：マーカー hover → 取引明細該当行ハイライト／明細行 hover → マーカーハイライト。
  - 前提：マーカーと明細行は trade `id` で一意対応（試作 `prep_data.py` の連番 `tid` を踏襲）。
  - 後条件：ハイライトは READ-ONLY 表示。既存チャート描画・live 経路に干渉しない（前例 `CHART_TRADE_MARKERS`）。
  - 例外：マーカー時刻が bars 時間軸に非整合の場合は当該マーカー非描画（無音切り捨て禁止＝件数をメタに明示）。

- **F-3 ヒートマップ（FR-05）**
  - 入力：`agg.heat`（曜日|時間帯セルごとの profit/count/wins）。
  - 出力：曜日 × 時間帯グリッドのカラーグラデーション＋ツールチップ（PF 等）。
  - 後条件：セルクリック/連動でチャートの該当時間帯にフォーカス（FR-05 チャート連動）。

- **F-5 OOS 統合（FR-07/08/09）**
  - 入力：`segments.is` / `segments.oos` の各完全 payload＋`summary`/`degradation`/`verdict`。
  - 出力：区間セレクタ（全パネル再描画）／比較・判定タブ（劣化比較表 IS|OOS|比|差・重畳エクイティ・判定バナー）。
  - 前提：IS/OOS は別 run（両方 10,000 始点）。エクイティ重畳で IS 終端と OOS 始点に段差が出るのは正しい挙動。
  - 後条件：verdict（fail/warn/pass）をヘッダ判定バッジ＋バナーに表示。

### 4.3 処理フロー図

```
[生成（バックエンド・1回）]
  bars CSV(IS) ─┐
                ├→ build_interactor → execute → BacktestResult(IS) ─┐
  bars CSV(OOS)─┘                                                    ├→ BuildReportPayload UC
                  build_interactor → execute → BacktestResult(OOS)─┘   │ (派生集計・degradation・verdict)
                                                                        ▼
                                                          ReportUiPresenter → report.json（新規パス）

[消費（フロント・区間切替ごと）]
  区間セレクタ(IS/OOS) → DATA.segments[sel] 取得 → 各パネル再描画
       ├ チャート3窓（OHLC/Balance/DD）論理レンジ同期
       ├ 取引明細テーブル（ソート）＋双方向ハイライト購読
       ├ ヒートマップ（heat セル）
       ├ グラフ群（agg 各系列を Chart.js へ）
       └ 比較タブ（summary/degradation/verdict）※区間非依存・両区間同時表示
```

### 4.4 業務フロー・ユースケース

- 主アクター：レポート閲覧者（戦略開発者）。
- 業務フロー：(1) run 実行者が bars CSV を入力に IS/OOS を run し `report.json` を生成 →

## 5. データ設計

> 出力元：S-3 データ設計

### 5.1 データモデル概要

概念モデルは「1 つの ReportPayload が 2 つの Segment（IS/OOS）を持ち、各 Segment が
Meta・Report・Bars・Trades・Orders・Agg を持つ。Payload は Segment 横断の Summary・Degradation・Verdict を持つ」
（試作 `prep_data.py` の出力構造を基準にスキーマ化）。

```
ReportPayload (1)
 ├─ Meta（symbol/timeframe/strategy/params/initial_deposit/split/note）
 ├─ Segment[is]  (1) ──┬─ Meta（symbol/timeframe/strategy/bars/trades/period）
 │                     ├─ Report（MT5 指標 label:value テキスト群／検証用参照値）
 │                     ├─ Bars[]（time/open/high/low/close）
 │                     ├─ Trades[]（id/side/entry・exit time/price/profit/volume/sl/tp/mfe/mae/hold_sec/balance）
 │                     ├─ Orders[]（生注文 11 列：open_time/order/symbol/type/volume/price/sl/tp/time/state/comment）
 │                     └─ Agg（entries_*/pl_*/balance_curve/scatter_mfe/scatter_mae/hold_*/heat）
 ├─ Segment[oos] (1) ── （同上）
 ├─ Summary{is,oos}（trades/net/final_balance/win_rate/profit_factor/expectancy/payoff/return_pct/max_dd_pct）
 ├─ Degradation{metric → {is,oos,ratio,delta}}（KEYS: net/profit_factor/win_rate/expectancy/payoff/return_pct/max_dd_pct）
 └─ Verdict{result: fail|warn|pass, reasons[]}
```

### 5.2 主要エンティティ定義

| エンティティ | 概要 | 主要属性 | 関連 |
|---|---|---|---|
| ReportPayload | 1 回の IS/OOS 比較レポート全体 | meta, segments, summary, degradation, verdict | Segment(2), Summary, Degradation, Verdict |
| Segment | 1 区間（IS or OOS）の完全データ | label, meta, report, bars, trades, orders, agg | Trade(N), Order(N), Bar(N), Agg |
| Trade | FIFO ペアリング済確定トレード | id, side, entry/exit time・price, profit, volume, sl, tp, mfe, mae, hold_sec, balance | Order（order id 参照） |
| Order | 生注文（明細・FR-03 の 11 項目） | open_time, order, symbol, type, volume, price, sl, tp, time, state, comment | Trade |
| Bar | OHLC バー | time(UNIX 秒 UTC), open, high, low, close | — |
| Agg | 区間集計（グラフ/ヒートマップ源） | entries_hour/session/wday/month, pl_*, balance_curve, scatter_mfe/mae, hold_pl/cnt, heat | — |
| Degradation | 指標ごとの IS/OOS 劣化 | metric → {is, oos, ratio=oos/is, delta=oos−is} | 既存 MetricDegradation 思想 |
| Verdict | 過剰最適化判定 | result(fail/warn/pass), reasons[] | — |

> JSON 契約スキーマの確定キー一覧（試作 `prep_data.py` 出力構造を基準）：
> - `meta`：symbol, timeframe, strategy, params, initial_deposit, split, note
> - `segments.{is,oos}`：label, meta{symbol,timeframe,strategy,bars,trades,period},
>   report{<指標名>:<値文字列>}, bars[{time,open,high,low,close}],
>   trades[{id,side,entry_time,exit_time,entry_price,exit_price,profit,volume,sl,tp,order,comment,balance,hold_sec,mfe,mae}],
>   orders[{open_time,order,symbol,type,volume,price,sl,tp,time,state,comment}],
>   agg{entries_hour,entries_session,entries_wday,entries_month,pl_hour,pl_wday,pl_month,
>       balance_curve[{time,value}],scatter_mfe[{x,y,id}],scatter_mae[{x,y,id}],
>       hold_pl,hold_cnt,weekorder,heat[{wday,hour,profit,count,wins}]}
> - `summary.{is,oos}`：trades, net, final_balance, win_rate, profit_factor, expectancy, payoff, return_pct, max_dd_pct
> - `degradation.<metric>`：{is, oos, ratio, delta}
> - `verdict`：{result, reasons[]}

### 5.3 データフロー図

- 生成：bars CSV（read-only）→ エンジン → BacktestResult → BuildReportPayload UC（派生算出）→
  ReportUiPresenter → `report.json`（新規パス・既存データ非上書き）。
- 消費：`report.json` → fetch → DATA グローバル → 区間切替で `DATA.segments[sel]` を各パネルへ。

### 5.4 データライフサイクル

- `report.json` は run のたびに新規パスへ生成（上書き対象は前回の同名 report.json のみ・既存データ非対象）。
- 保持期間：閲覧用の揮発的生成物。アーカイブ・削除ポリシーは運用判断（本機能では恒久保存を前提にしない）。
- bars CSV / oracle xlsx は read-only の入力・検証参照であり本機能はライフサイクルを管理しない（C-1）。

| ブラウザ ↔ 配信サーバ | HTTP GET（static） | JSON / HTML | 閲覧ごと | fetch 失敗時は UI にエラー表示（既存描画を破壊しない） |

### 6.4 通信プロトコル・データ形式

- プロトコル：HTTP（localhost・no-cache）。選定理由：既存配信機構を踏襲（C-4）・read-only で十分。
- データ形式：JSON。選定理由：既存 `JsonPresenter` と同型・ブラウザ fetch ネイティブ対応・vendor グラフ

- 転送量最適化（NFR-05 論点）：bars が payload の大半（試作 10MB）を占めるため、初期描画に必要な
  summary/agg/trades を先行配信し、bars は区間/遅延ロードに分割する案を §9.3 TBD-02 で詳細設計へ委譲。

| 要件 | 数値目標 | 設計対策 | 測定方法 |

| 要件 | 数値目標 | 設計対策 | 測定方法 |
|---|---|---|---|
| 配信可用性 | ローカル開発用途（SLO 設定なし＝該当なし） | static 配信。サーバ停止時はブラウザにエラー表示・既存データは無影響（read-only） | 手動起動確認 |

> 本機能はローカル閲覧ビューアであり本番サービス可用性（99.9% 等）の対象外。該当なしを明示。

### 7.3 セキュリティ設計

- 認証・認可：ローカル開発用途・localhost バインドのため認証なし（該当なし）。外部公開は対象外。
- 通信暗号化：localhost のため TLS 非対象（該当なし）。
- 入力検証：生成 JSON にユーザ入力を生挿入しない（report.json は確定データのみ）。
  配信は既存方針（localhost バインド・パストラバーサル防止）を踏襲（前例 `CHART_TRADE_MARKERS` §6）。
- 監査ログ：該当なし（閲覧専用・状態変更なし）。
- データ安全（最重要）：C-1 read-only を設計で保証。生成物は新規パスのみへ出力し、
  既存データ（xlsx/CSV/marketdata/fixtures）への書込経路をモジュールに持たせない。

### 7.4 運用・保守性設計

- ログ設計：生成ツールは run 結果サマリ（trades 件数・net・balance）と JSON サイズを標準出力（試作 `prep_data.py` 同様）。
- 監視ポイント：report.json 生成成否・サイズ。
- 構成管理：report_ui は `simulator/report_ui/` 配下に集約（バックエンド・web・vendor・生成ツール）。
- 保守性（責務分離）：データ生成（UC/Presenter）と表示（front）を JSON 契約で分離。グラフ追加は
  agg の系列追加＋front の描画追加で完結（既存経路に分岐を足さない＝OCP）。
- バックアップ・リストア：report.json は再生成可能（bars CSV から）のためバックアップ不要。既存データの
  バックアップは本機能の対象外（C-1 で改変しない）。

  検証参照として用いる（xlsx の report 指標値との桁・丸め突合は詳細設計）。

### 8.3 テスト方針

- 単体：BuildReportPayload UC（FIFO ペア・agg 集計・degradation・verdict 閾値）／ReportUiPresenter（JSON 契約形状）。
- 結合：bars CSV → エンジン → UC → Presenter → report.json の形状・件数検証（confirmation 値と照合）。
- システム：ブラウザでの区間切替・双方向ハイライト・ヒートマップ・グラフ・判定の描画確認（試作 verify.py 同型の
  Playwright ヘッドレス検証を踏襲）。
- 受入：SPEC 4 点＋OOS 統合の UX が試作スクショ（`shots/`）と同等であること。

### 8.4 リリース・デプロイメント方針

- 環境構成：ローカル開発のみ（開発＝本番。外部デプロイ対象外）。
- デプロイ戦略：`simulator/report_ui/` 一式の配置＋簡易サーバ起動。既存環境への影響ゼロ（新規追加のみ）。

## 10. 付録

### 10.1 用語集

| 用語 | 定義 |
|---|---|
| IS / OOS | In-Sample（学習区間 04.01-14）／ Out-Of-Sample（検証区間 04.15-）。過剰最適化検証の 2 区間 |
| verdict | 過剰最適化判定（fail=優位性消失／warn=要注意／pass=合格） |
| degradation | 指標の IS→OOS 劣化（ratio=oos/is・delta=oos−is） |
| MFE / MAE | Maximum Favorable / Adverse Excursion（最大含み益/含み損。バー走査で算出） |
| BacktestResult | 既存エンジンの 1 run 出力（trades/deals/equity_curve/balance_curve/stats） |
| report.json | 本機能の生成物。ReportPayload（JSON 契約）の実体 |
| ReportPayload | 本機能の報告ドメインモデル（2 Segment＋summary/degradation/verdict） |

### 10.2 設計判断の根拠・トレードオフ

| 判断項目 | 採用 | 代替 | 根拠 | 出典区分 |
|---|---|---|---|---|
| 全体パターン | クリーンアーキ踏襲＋JSON 契約 front 疎結合 | front ロジック集約（試作）／BFF 新設 | 既存 simulator 整合・SRP・C-4 | 公式（Martin 2017）／規約 |
| データソース境界 | **案 b（エンジン run 出力消費）** | 案 a（xlsx 直読み） | reconcile bit-exact 一致で実現可と実証・SSOT 一元化・自動再生成性 | 実証＋実務的推奨／仮説 |
| 派生データ責務 | report_ui 新規 UC で BacktestStats＋trades から派生算出 | xlsx 転記 | エンジン出力が一次・xlsx 恒久依存回避 | 実務的推奨／仮説 |

## 設計検証（S-5 自己点検）

- 要求整合：SPEC 4 点（FR-01〜06）＋OOS 統合（FR-07〜09）を機能一覧（§4.1）に全マッピング。要件未対応の設計・
