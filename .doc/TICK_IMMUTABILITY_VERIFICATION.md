# 過去日ティックの不変性 実測検証

ロールアップ方式（確定分を畳んで再読しない forming／1W・1M 対応・長周期のコスト一定化）の
**唯一の未検証前提＝「過去 UTC 日のティックは不変か」を実測で確定させた記録。**

- 実施日: 2026-07-09（UTC）
- 対象: JP225（`E_N225Jap`）ティック
- 再現スクリプト: [`tools/verify_tick_immutability.py`](../tools/verify_tick_immutability.py)（読取のみ・保存 parquet 非上書き）

## 背景（なぜ検証したか）

「確定分（前日以前）をロールアップへ畳み、二度と読み直さず、当日テールだけライブ配信する」
方式は、`rollup.incremental_update` 等の既存機構の再利用でありコスト一定化・1W/1M 対応が可能。
ただし正しさは **「一度確定した過去日のデータは、後から訂正されない（不変）」** という前提に依存する。
この前提は当初「経験的（＝実測していない推論）」であったため、実装前に実測で確定させた。

## 方法（誤結論を避けるための設計）

保存済み parquet（過去 UTC 日）と、いま再取得した同一日を突合し、次を分離集計する。

- **訂正**: 同一 timestamp で値タプル（bid/ask/bidVol/askVol）の集合が異なる → 前提を**否定**。
- **欠落**: 保存にあり再取得に無い timestamp → 前提を**否定**。
- **追記**: 再取得のみの新規 timestamp → 遅延到着/欠損補完であり訂正ではない（前提と無関係）。

比較の頑健化: timestamp を int ns へ統一、価格/数量は許容誤差 `1e-6` で量子化（float 表現差を訂正と誤認しない）、
UTC 日境界で整合、齢の異なる複数日（D-1/D-3/D-7/D-30）を対象、最古日は 2 回再取得して応答の決定性も確認。

## 結果

| 対象日 | 齢 | 保存件数 | 再取得件数 | 完全一致 | 追記 | 欠落 | 訂正 | 判定 |
|---|---|---|---|---|---|---|---|---|
| 2026-07-08 | D-1 | 202,277 | 202,277 | 202,277 | 0 | 0 | 0 | 不変 |
| 2026-07-06 | D-3 | 135,196 | 135,196 | 135,196 | 0 | 0 | 0 | 不変 |
| 2026-07-02 | D-7 | 188,060 | 188,060 | 188,060 | 0 | 0 | 0 | 不変 |
| 2026-06-09 | D-30 | 180,354 | 180,354 | 180,354 | 0 | 0 | 0 | 不変 |

- 全4日で保存済み parquet と再取得が **bit 単位で完全一致**（訂正・追記・欠落すべて 0）。
- **安定性**: 最古日を 2 回再取得 → 相互一致（ベンダ応答は決定的）。

## 結論

**JP225 の過去 UTC 日のティックは不変（immutable）。** D-1〜D-30 で再取得＝保存に完全一致。
よって **「確定分（前日以前）はロールアップへ畳み、二度と読み直さない」というロールアップ方式の前提は
実測で支持された**（憶測ではなく実証済み事実）。

## 検証範囲の限定（誠実な明示）

- サンプルは JP225・4 日（D-1/3/7/30）・「保存スナップショット以降の不変性」。網羅ではない。
- **当日 UTC 内の暫定→確定の書き換えは対象外**（＝当日は可変。システムは `live_tick_watch` の
  毎分フル再取得で対処済み）。畳む対象は前日以前のため本結論に影響しない。
- 恒久運用で前提を担保するなら、本スクリプトを定期実行して差分 0 を継続監視するのが望ましい。
