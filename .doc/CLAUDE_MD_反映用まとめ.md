## A. 作業ルール（CLAUDE.md へ反映する — 15 件）

### A-1. 事実と根拠

**憶測で進めない**（厳命 2026-07-09）

実測・参照実装・コード/型の確認がない仮定を根拠に、設計判断・実装・断定説明をしてはならない。未検証事項は「未検証／推論」と明示し、事実（実測値・出典）と分離する。設計・実装の前提になる未検証事項は着手前に実測で確定させる。

**実測は数値だけでなく「構成・状態・理由」にも適用する**（厳命 2026-08-01・繰り返し指摘）

- 構成・状態・理由を述べる前に**権威ある出典を読み、出典を添える**（構成＝起動スクリプト／設定、状態＝稼働プロセス・bind アドレス・ログ、挙動＝コード）
- **記憶や過去の前提を出典にしない**（構成変更で陳腐化する）
- **計測前に「測る対象が現行コードか」を確認する**（`ps -o lstart` とファイル更新時刻の突き合わせ）
- **聞かれていない仮定の場面を持ち出さない**（起きない前提の説明はノイズ）

**ブラウザ検証は実 UI で必ず確認する**（厳命 2026-07-11）

実 UI・実データ・実リクエスト経路（フロント→HTTP→controller→描画）で確認する。compute 直叩き・合成データを不具合有無の判定根拠にしてはならない。

### A-2. 解決の質

**抜本的解決のみ提示する**（厳命 2026-08-01）

対策として提示してよいのは根本原因を除去するものだけ。応急処置は選択肢として並べることすら禁止、推奨案にするのは論外。

- **判別**: 「原因を除去したか」でなく「症状の出る条件を避けたか」で速くなった／直ったものは応急処置。処理量を減らす／回数を間引く／上限を下げる／**対象を外す**／閾値で回避する／リトライやタイムアウトで隠す
- **特に危険な形**: 品質（粒度・精度・網羅性）が入力次第で黙って劣化する仕組み
- **文書の禁止事項（例: 「src は一切変更しない」）を理由に、除去可能な原因を残す案を推奨してはならない**。優先順位は「抜本的に問題を解決すること」が最上位で、文書上の制約はその下。規約に触れるなら**その解決策を出したうえで承認を求める**
- 実測で「この対策は原因のどこを消したか」を言えないなら応急処置
- 過去に RESOLVED とした不具合が再発したら、前回の対策が応急処置だった可能性をまず疑う

**ビュー自動介入の禁止**（裁定 2026-07-23）

チャートのビュー状態（スクロール・ズーム・スケール）を書き換えてよいのはユーザーの明示イベントのみ。タイマー・データ到着・再計算起点の自動補正の同梱は禁止。バグ修正は原因コードの除去が原則で、ガード・条件分岐で症状を隠す案は「隠蔽」と明示して提案し、承認なしに採らない。

### A-3. 仕様と範囲

**承認仕様を勝手に狭めない**（厳命 2026-07-18）

承認された仕様の適用範囲を変える（限定・拡大とも）場合は実装前に必ず y/n。「安全側に絞る」判断も承認なしでは越権。完了報告時は指示文と実装仕様の差分ゼロを確認する。

**リプレイは参照実装＝ライブに厳密一致**（厳命 2026-07-19）

リプレイ側の設計・実装はすべてライブ側挙動への厳密一致が最優先。着手前にライブ側の該当経路（front 配線→compute→backend）を読み、粒度・条件・順序を一致させる。差分を作る場合は必ず事前承認。

**基本設計主体・主機能無改変の参照拡張（OCP）**（指示 2026-07-18）

新機能のために新モジュールを足すのでなく、主機能を改変せず参照して拡張する構造にする。着手前に「主機能のどの定義（現在時刻・カーソル・窓）に従うか」を確定し、適用範囲は主機能と常に対称にする。

### A-4. 設計の質

**認知負荷の最小化を最優先**（厳命 2026-07-30）

機能を全部出すのでなく、削る判断を先に行う。

- 命名は概念単位で統一し、**同一概念に複数の呼び名を作らない**
- 比喩を持ち込まない（`window` の直訳「窓」のように字面から実体を推測できない語を避ける）
- パラメータ名は、それが動かすチャート上の系列名と対応させる
- 根拠のない項目は出さない（実測で効果が無いものは内部固定）
- 迷ったら「消したら困るか」を先に問い、困らないなら消す

### A-5. 報告の作法

**用語定義から始める**（指摘 2026-08-01）

3 語以上の概念が絡む報告は冒頭に用語表（語 → 1 行の意味）を置く。同じ数値が何を含む／含まないかを明示し、機能名とその量を表す語を混ぜない。数値は内訳に分解して示す。ユーザーが使った語を勝手に別語へ置き換えない。

**次の一手まで書く**（指摘 2026-08-01）

「未実施」「残件」の列挙で終わらせない。次に何を・どの順で・どの条件で実施するかを、対象・パラメータ・判定基準まで具体化する。依存があれば「A が通れば B、落ちれば中止」と分岐を明示。判断が要る項目は選択肢と推奨（実測根拠付き）を添える。

**丸数字は絶対に使わない**（厳命 2026-07-23）

ユーザー環境では ①②③ 等の囲み数字・環境依存グリフが潰れて読めない。番号は「ステップ 1」「1.」「(1)」を使う。

### A-6. 運用（サーバ・ポート）

**公開は 8000 単一・起動は `unified_ui/serve.sh` のみ**

```
[公開 8000] router.py … 0.0.0.0 bind（VS Code に見えるのはここだけ）
   ├─ /live/*   → 127.0.0.1:8001  ライブ core（loopback 限定）
   └─ /replay/* → 127.0.0.1:8281  リプレイ core（loopback 限定）
```

- 8001/8281 が VS Code のポート欄に出ないのは正常（loopback bind）。「見えない＝落ちている」ではない
- **8280 は使わない**（単体起動時の既定ポート。一本化構成では不要）
- 各 core を手動起動すると unified_ui の管理外（PPID=1）になり停止時に残る。**必ず `unified_ui/serve.sh` 経由**
- `serve.sh` は 8000 が応答していると `既に起動済みです` で即終了する。**コードを反映するにはスタックを停止してから実行**
- 生 python 起動は禁止（serve.sh が併走させるデータ watch が無いと確定足が伸びず指標が止まる）

**実験後は正規構成へ戻す**（事故 2026-08-01）

調査のためサーバを直接起動したら、終了時に必ず `serve.sh` 管理下へ戻す。**プロセス停止は明示 PID で行う**（`pgrep -f "serve.sh 8001"` は自分のシェルにも一致し停止コマンド自身が kill される）。復旧後は 3 ポートの 200 と watch 2 本の生存を確認する。足が伸びていないときは市場休場を先に疑う。

### A-7. 統計検定の作法

**検定の不具合は校正を先に**（裁定 2026-07-11）

検定にバイアスを見つけたら、統計量を書き換える前に (1) 同じバイアス機序を持つ帰無分布をシミュレーションで構成（サロゲートごとに補助推定量を全て再推定・真のパラメータ使用禁止）→ (2) 校正後に H1 検出力を実測 → (3) 検出力不足の場合のみ統計量を放棄。共通項バイアスは参照点の調整では消えない。
