# 上位時間足指標のチャート投影 — 基本設計（案）

- 状態: **実装済み・実 UI 検証済み**（2026-08-06）。残件は §6.3（tick 粒度追従）。
- 起票: 2026-08-06
- 対象: `indigators/indicator_ui`（ライブ）／ `simulator/replay_ui`（リプレイ・同一 compute 経路）
- ユーザー確定事項（2026-08-06）: 配置＝**価格ペインに重ねる** ／ 対象範囲＝**全指標に配る**

---

## 0. 用語定義

| 用語 | 定義 |
|---|---|
| **チャート足 C** | 時間足セレクタで選択中の足。ローソク・時間軸の唯一の基準。 |
| **計算足 H** | 当該指標を計算する足（`params.timeframe`。`'chart'` は C に追従）。 |
| **上位足指標** | `barSec(H) > barSec(C)` の指標インスタンス。 |
| **投影** | H の時間軸で得た値列を、C の時間軸の値列へ写す操作。本設計の中心概念。 |
| **確定時刻** | ある H バーの値が確定する時刻。＝**次の H バーの開始時刻**（ISSUE-030 で確立した規約）。 |
| **前方保持** | C バー時刻 `t` の値 ＝ 確定時刻が `t` 以下である最後の H バーの値。 |
| **足内追従** | 形成中バーの間、tick 粒度で末尾値が動くこと（`/live_ticks` 同梱経路）。 |

---

## 1. 目的と非目的

**目的**: 上位足で計算した指標を、下位足チャート上に、下位足指標とまったく同じ規律
（時間軸不変・確定バー不変・足内追従・価格スケール非汚染）で描けるようにする。

**非目的**: 新しい指標の追加。描画プリミティブの追加。ペイン配置規約の変更
（オシレーター系が専用ペインに出る現行規約は不変）。

---

## 2. 現行実装の実測（根拠）

現行にも上位足 override は存在する（`moving_averages` の「計算.時間足」パラメータのみ）。
実 UI（`http://127.0.0.1:8000/` ・5m チャート・EMA9）で計測した結果、4 件の構造的欠陥を確認した。

| # | 事象（実測） | 直接原因 |
|---|---|---|
| D-1 | **時間軸が汚染される**。1D 計算にすると時間軸が 2020 年まで伸び、左スクロールでローソク不在の空白域が続く。価格軸は 23,520 まで引かれる。 | `limit=1500` を **H の本数**で数えるため、H=1D では 1500 日ぶんの点が返る。C に存在しない時刻が時間軸へ union される。 |
| D-2 | **直線補間で描かれる**。1h 計算では時刻間が直線で結ばれ、1D 計算ではほぼ一本の直線になり指標として読めない。 | H の点をそのまま line 系列へ渡すため、点間が線形補間される。上位足の値は次の足まで一定＝階段であるべき。 |
| D-3 | **右端が最大 1 上位足ぶん欠ける**。1D 計算時、系列は `1785974400` で止まりローソクは `1786010400`（10 時間先）まで伸びる。 | 最新 H バーの**ラベル時刻**に点が置かれ、それ以降に点が無い。 |
| D-4 | **足内追従から除外される**。上位足指標はライブの tick 粒度更新を受けず、バー確定時の full 再計算でしか動かない。 | `indicator_controller.js:293` が `params.timeframe` を持つインスタンスを `appliedComputeSpecs()` から明示的に除外している。 |

## 3. 根本原因

D-1〜D-5 はすべて**同じ 1 つの原因**から出ている。

> **上位足で計算した系列を、H の時間軸のままチャートへ渡している。**

チャートの時間軸は C ただ 1 つであり、そこへ H の時刻を混ぜた時点で、
軸（D-1）・補間（D-2）・端点（D-3）・追従経路（D-4）・因果（D-5）のすべてが同時に破れる。
個別に手当てすると 5 箇所へ別々の条件分岐が生えるが、原因は 1 つなので手当ても 1 つでよい。

---

## 4. 抜本策 — 投影段の単一化

**計算（H の時間軸）と描画（C の時間軸）の間に、投影段をただ 1 つ置く。**

```
[現行]  load(H) → compute → series(H の時刻)            → front → 描画 ✗
[本案]  load(H) → compute → series(H の時刻) → 投影(C) → front → 描画 ✓
                                              ↑ここだけが新規
```

投影を通過した時点で系列は「C の時間軸を持つ普通の系列」になる。よって**フロントの描画・
スタイル・足内追従・スケール・凡例・永続化の各経路は一切改変しない**（既存主機能を参照するだけの
加法的拡張＝OCP）。D-1〜D-4 は分岐を足すのではなく、原因が消えることで解消する。

### 4.1 投影段の配置

**バックエンド（`usecase/compute_indicators.py` の出力段）に置く。** 理由:

1. **足内追従と同じ関数を共有できる**。`/live_ticks` 同梱の末尾値算出もサーバ側にあるため、
   同一の投影を通せば D-4 の除外条件を撤廃できる。フロントに置くと 2 実装になる。
2. **リプレイと自動的に一致する**。リプレイは同じ `/compute` を叩く。サーバ側に置けば
   「リプレイはライブに厳密一致」という不変条件が構造的に保たれる。
3. **C のバー時刻の唯一源がサーバにある**。`/candles` と同じ `load_dataframe(ref, C)` を使えば、
   投影先の時刻集合はローソクの時刻集合と定義上完全一致する（D-1 の再発が構成上不可能になる）。

### 4.2 リクエスト契約の変更

現行は `timeframe` に**実効足**（override 済み＝H）を入れて送っており、C がサーバに伝わらない。
2 つを分けて送る。

| フィールド | 現行 | 本案 |
|---|---|---|
| `timeframe` | 実効足（H） | **チャート足 C**（＝時間軸・`/candles` と同じ値） |
| `computeTimeframe` | なし | **計算足 H**（未指定・`'chart'` は C と同義） |
| `limit` | H の本数 | **C の本数**（表示範囲。現行 `RECENT_BARS`=1500 と同義） |

`computeTimeframe` 未指定時は投影を行わず、現行と 1 バイトも変わらない挙動になる（後方互換）。

### 4.3 H の取得窓（実装時に簡素化）

当初案は「C の表示窓を覆う H の窓を逆算する」だったが、**逆算は不要**と判断した。

投影は `T_c` の各バーにしか点を出さないため、H を何本取ろうと応答の時刻集合は `T_c` の
部分集合に収まる。したがって H の窓は従来どおり `limit` 本の tail のままでよく、
`barSec(H) > barSec(C)` である以上「H を limit 本」は「C を limit 本」より必ず長い期間を覆う
＝ウォームアップは常に充足する。窓を逆算する分岐を足さずに済む。

D-1（時間軸の汚染）は「窓を絞ったから」ではなく「投影後の時刻が `T_c` の部分集合だから」
解消する。原因側を消しているため、窓の取り方には依存しない。

## 5. 投影の規約（決定論的定義）

### 5.1 入力・出力

- 入力: H 系列 `[(label_h, v)]`、C バー時刻列 `T_c`、`wait_for_close`
- 出力: `[(t_c, v)] for t_c in T_c`（**時刻集合は `T_c` の部分集合であることが不変条件**）

### 5.2 確定時刻（D-5 への対処）

各 H バーの**確定時刻**を、ラベルからではなく期間境界から求める。

```
confirm(label_h) = 次の H バーの開始時刻
                 = period_utc_start(H, next_label(label_h))
```

- 日中足（1m..4h）: ラベル＝始端なので `confirm = label + barSec(H)`。
- セッション足（1D/1W/1M）: `period_utc_start()` が唯一源。`barSec` を使った固定秒計算は**禁止**
  （1W/1M は floor 不可・ラベルは右端・暦月は 30/31 日で幅が変わる）。

**実測による裏付け（本規約で十分であることの確認）**: 隣接ラベルに対して
`period_utc_start(tf, next_label)` を評価すると、区間幅が 1D=1 日 / 1W=7 日 /
1M=30 日・31 日（暦月どおり）と一致した。次ラベルは resample 済みインデックスの隣接要素から
得られるため、**新しい境界計算は不要**で、既存の唯一源をそのまま参照すればよい。

### 5.3 値の写像

```
v(t_c) = confirm(label_h) <= t_c を満たす最後の H バーの値
```

- 材料不足（`t_c` がどの確定 H バーよりも前）の C バーには**点を出さない**
  （NaN/null を描かない＝既存 `applyFormingTails` と同じ規律）。
- 投影しないのは `H == C`（および未指定・`'chart'`）のときだけ。当初案は「`barSec(H) <= barSec(C)`
  なら投影しない」だったが、**下位足を選んだ場合こそ時間軸の汚染がひどい**（1m 計算を 1D チャートへ
  出すと膨大な時刻が軸へ混入する）。分岐を増やさず一律に投影する方が、条件も結果も単純になる。

この定義により、C の各バーに点が置かれるため描画は自動的に**階段**になる（D-2 解消）。
線種の変更は不要で、既存の line/histogram 描画をそのまま使う。

### 5.4 形成中の上位足の扱い

既存パラメータ `wait_for_close`（「時間足の確定を待つ」・既定 `false`）の意味をそのまま延長する。

| 設定 | 挙動 | リペイント |
|---|---|---|
| `true` | 確定した H バーのみを投影する。 | なし（過去・現在とも不変） |
| `false`（既定） | 上記に加え、**形成中の H バーの現在値**を、その H バー区間に属する C バー全体へ適用する。 | 形成中 H バー区間のみ可変。確定後は不変。 |

`false` を既定に据える根拠は既存 `moving_averages` の既定値と対称であること（＝参照実装に従う）。
可変範囲が「形成中の 1 本ぶん」に限定され確定後は不変である点は、既存の形成中バー規律と同型。

**注記（承認事項 A-3）**: `false` では可変範囲が最大 `barSec(H)` に広がる（例: 5m チャート＋1D 計算なら
直近 1 日ぶんの C バーが tick ごとに動く）。この見え方を許容するかはユーザー判断を要する。

## 6. 全指標への展開（ユーザー確定事項）

### 6.1 パラメータの配布

配るのは **「計算.時間足」だけ**にした。「時間足の確定を待つ」は `moving_averages` に既に
在るものを据え置く（全指標へ配ると、チャート足計算時にはほぼ効かない設定が全ダイアログへ
増える＝認知負荷に見合わない）。他指標の投影は既定 `wait_for_close=false` で動く。

配布は front / back とも **1 箇所からの注入**にする（22〜24 の定義へ同じリテラルを配らない）。

| 側 | 注入点 |
|---|---|
| front | `catalog.js` の `withCalcTimeframe`（REGISTRY 構築時）。選択肢は台帳 `TF_CODES` から導出。 |
| back | `call_binding.indicator_param_defaults()`（`PARAM_DEFAULTS` の導出時）。 |

対象外はアクター駆動型（`market_profile` / `tickvol_bands`）。`/compute` を持たず投影経路に
乗らないため、効かない設定を出さない。

### 6.2 配置（placement）

ユーザー確定は「価格ペインに重ねる」。本設計はこれを
**「上位足化は配置を変えない」** と解釈する。すなわち:

- `placement: 'overlay'` の指標（MA 等）→ 従来どおり価格ペインへ重ねる。
- `placement: 'pane'` の指標（RSI・ma_marod 等）→ 従来どおり専用ペインへ出す。

上位足であることを理由に配置を切り替える分岐は設けない（同一概念に 2 つの配置規約を作らない）。

**確認事項 Q-1**: 「価格ペインに重ねる」が「オシレーター系も含めて全部を価格ペインへ重ねる」という
指示であれば本節は誤りとなるため、着手前に確認を要する。

### 6.3 足内追従（D-4）— **実装済み**

除外条件を消すだけでは成立しない。`/live_ticks` 同梱の末尾値は「窓を 1 回ロードし、その
**末尾行**を tick の形成中 OHLC で差し替える」構造で、窓も形成中 OHLC もチャート足単位だった。
上位足指標に必要なのは「その tick 時点の **H 足の**形成中バー」であり、チャート足で畳んだ
形成中バーを H の窓へ差し込むと、上位足指標にチャート足の値が入る。

抜本策は **計算足ごとにグループ分けする**ことだけで済んだ。形成中バーの畳み方
（`forming_states`）は `bar_time_fn` 注入で**元から時間足非依存**に作られていたため、
渡す関数を H のものに替えるだけで H の形成中バーが得られる。

```
計算足ごとに:  窓(H) をロード → bar_time_fn(H) で tick を畳む → 末尾行を差し替えて計算
              ↓
        tick ごとに 1 本へマージ（merge_tail_batches）
```

同一計算足の spec は 1 グループにまとまるので、窓のロードも畳み込みも計算足の種類数ぶんだけ
増える（インスタンス数には比例しない）。

**残る制約（描画ライブラリ由来）**: lightweight-charts の `series.update()` は末尾より古い
時刻を拒否する（`Cannot update oldest data`）。よって tick で安く動かせるのは**末尾 1 点だけ**で、
現在の H 期間に属する他の C バーはバー確定時の full 再計算で追いつく。つまり現在の段の右端が
段本体より「1 チャート足ぶんの上位足指標の変動」だけ先行する。実測では 1h 計算で 5.4 ポイント
（65,478 に対し 0.008%）で、段の高さより小さく画面上では判別できない。段全体を毎 tick 動かすには
系列全体の `setData`（1500 点）を tick ごとに行う必要があり、費用に見合わない。
