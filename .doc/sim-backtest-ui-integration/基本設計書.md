## 2. プロジェクト概要

> 出力元：S-1 要件分析と設計方針決定

### 2.1 システム概要

- **位置付け**：`unified_ui` の公開 8000 上に、ライブ・リプレイと並ぶ第 3 のモード
  「シミュレーション」を追加する。本モードは「バックテストの実行を指示し、その結果を閲覧する」
  操作面を担う。バックテストの計算そのものは新設の sim コアサーバが子プロセスのジョブとして実行する。
- **解決する業務課題**：現状、戦略の検証操作は 3 つの独立した場所に分断されている。
  1. サイジング規則の検討＝単体 HTML の計算機（`integrated_position_sizing_calculator.html`・ISSUE-370）。
  2. バックテストの実行＝CLI（`simulator/main/__main__.py:23-33` の `argparse` 経路）。
  3. 結果の閲覧＝別ポートの独立ビューア（`simulator/report_ui/serve.py:12` の既定ポート 8770）。
  チャート（ライブ / リプレイ）で見つけた仮説を、同一画面のまま検証へ渡す経路が存在しない。
  本機能はこの 3 者を公開 8000 の 1 ページへ統合する。

### 2.2 開発目的・背景

- **背景**：
  - 統合 UI は既にルータ方式で 2 モードを収容済み（`unified_ui/router.py:52-55` の振り分け表・
    `.doc/LIVE_REPLAY_UNIFICATION_BASIC_DESIGN.md`）。第 3 モードの追加はこの機構の延長線上にある。
  - 口座規約（証拠金・ロスカット）の参照実装が ISSUE-369 で確定した
    （`simulator/usecase/account_engine.py:310-335` の `official_required_margin` /
    `official_losscut_price`）。サイジング規則を推測なしに UI へ結線する前提が揃った。
  - ISSUE-370（計算機のチャート統合）は「ISSUE-369 のエンジンが式の権威となること」を
    着手条件として保留されていた（ISSUE.md:6921・6947-6949）。本設計はその着手条件を満たす。
- **達成したい目標**：
  - G-1：チャートで観測した水準・指標構成から、サイジング規則と戦略規則を指定してバックテストを
    投入し、結果を同一ページで閲覧する経路を成立させる。
  - G-2：バックテスト計算をライブ core の request path に載せない（ISSUE-362 / ISSUE-364 の実測に整合）。
  - G-3：結果表示は `report_ui` の完全再現とする（パリティ検定で判定）。
  - G-4：既存モジュールは追加（OCP）で拡張する。2 値ハードコード箇所の 3 値化は
    「拡張点の欠如＝OCP 違反の是正」として表駆動化する。

#### 2.3.3 制約条件

- **C-1（設計原則）SOLID 厳守**：設計判断を 5 原則へ写像して示す（§10.4）。既存モジュールは追加で拡張し、
  無改変を優先する。2 値ハードコードの 3 値化は OCP 違反の是正として表駆動化する。
- **C-2（禁止）破壊的変更禁止**：データの不可逆削除・認証無効化・共有モジュールの破壊的変更を行わない。
- **C-3（固定）技術スタックのバージョン無断変更禁止**：lightweight-charts は統合側 v5.2.0
  （`indigators/indicator_ui/web/vendor/lightweight-charts.js:3` に版表記を実測）、`report_ui` 側 v4.1.3
  （`simulator/report_ui/web/vendor/lightweight-charts.standalone.js:3` に版表記を実測）。両者を同一ページへ
  同居させない。
- **C-4（固定）ポート**：公開 8000・ライブ core 8001・リプレイ core 8281。sim コアの内部ポートは
  新規採番を要する（§6.5・§9.3 TBD-03）。
- **C-5（単一ソース）共有 JS**：実体は `indigators/indicator_ui/web`。共有は相対 symlink のみ（絶対 symlink 禁止）。
  新規 web スイートは `tools/web_suites.txt`（実在確認済・4 件登録）へ登録する。
- **C-6（無改変）MT5 突合系**：`simulator/usecase/run_backtest.py` と `simulator/domain/account.py` は
  MT5 突合の正であり無改変で据え置く（依頼者裁定 2）。
- **C-7（単一ソース）式の再実装禁止**：ライブ指標の式を simulator 側で再実装しない（依頼者裁定 4）。
  口座規約の式は `account_engine` を唯一の権威とする（依頼者裁定 2）。
- **C-8（用語）**：「動的」という語を使用しない。丸数字を使用しない（番号は「1.」表記）。
  同一概念に複数の呼び名を作らない。
- **C-9（進め方）**：応急処置を提示しない。未検証事項は「未検証」と明示し事実と分離する。

#### 2.3.4 設計上の課題と技術的リスク（詳細は §9）

- **課題 1（最重要・依頼者裁定を要する）**：`StrategyPort` の唯一の消費者は
  `simulator/usecase/run_backtest.py` の `RunBacktestInteractor` である（grep 実測・§3.5.3）。
  したがって「`StrategyPort` を境界として FR-07 / FR-08 を追加する」と「C-6 run_backtest.py 無改変」は
  同時に成立しない。§3.5.3 で 3 案を比較し、採否を §9.3 TBD-01 として裁定に委ねる。
- **課題 2（上流前提の訂正）**：「v5.2.0 にマーカー hover 検出が存在するかは未検証」という前提は
  実測により反証された（§3.5.2）。真のリスクは hover 検出の有無ではなく、v4 → v5 の系列生成 API の
  破壊的差分にある（§3.5.1）。
- **課題 3（依頼者確認を要する）**：サイジング規則の権威が二重になる戦略が 1 件ある。
  `weekly_vol_band` は `N = f_risk · Capital / (O − S)` をドメイン層で既に実装している
  （`simulator/domain/volatility_band.py:6, 50`）。上流入力「全 6 戦略が固定値」はこの 1 件で成立しない。
  §9.3 TBD-13 で扱いを確認する。
- **課題 4**：ライブ指標を全バー分供給する際の計算量。因果順守の逐次呼出は 1 呼出あたり実測 6.6ms
  （`simulator/replay_ui/usecase/causal_compute.py:30-36` の記載値）。1 万バーで約 66 秒となる。
  一括計算で代替できるかは指標ごとの因果性に依存する（§3.5.4・§9.3 TBD-05）。

## 3. システムアーキテクチャ

> 出力元：S-1 採用パターン選定 ／ S-2 アーキテクチャ設計

### 3.1 全体構成図

```
[ブラウザ] ──8000──> [unified_ui/router.py（既存・振り分け表を 3 値へ表駆動化）]
     ├─ 静的 /                → unified_ui/web（統合エントリ・モードトグル 3 値）
     ├─ /live/*      （静的+API）→ 127.0.0.1:8001   ライブ core（indicator_ui・無改変）
     ├─ /replay/*    （静的+API）→ 127.0.0.1:8281   リプレイ core（serve_replay・無改変）
     └─ /sim/*       （静的+API）→ 127.0.0.1:[TBD-03] ★ sim コア（新規）
                                        ※内部ポートは loopback 限定・外部非公開

★ sim コア（新規・simulator/sim_ui/ = replay_ui と同型構成）
   framework  : static_file_server（shared_js_root フォールバック）＋ HTTP API
   main       : composition_root（DI 一括結線）
   adapter    : ジョブ台帳ゲートウェイ／指標供給ブリッジ／結果ペイロード読出
   usecase    : ジョブ受付 UC・ジョブ状態照会 UC・結果取得 UC
   domain     : ジョブ状態（受付/実行中/完了/失敗/取消）の遷移規則
        │
        │ 子プロセス起動（request path を占有しない＝NFR-01）
        ▼
★ バックテスト実行 CLI（新規・子プロセス）
        │   1. 指標供給: ライブ compute を因果順守で IndicatorPort へ（§3.5.4）
        │   2. 発注量決定: SizingPort ← account_engine の権威式（§3.5.5）
        │   3. 実行エンジン: §3.5.3 の裁定に従う（TBD-01）
        ▼
★ 結果ペイロード JSON（report_ui の JSON 契約と同形）
        │
        ▼ GET /sim/data/<job_id>/report.json
★ sim モードのフロント（unified_ui/web 配下・report_ui からの移植）
        ・純ロジック（linkage.js・balanceForwardFill 等）はそのまま流用
        ・vendor 層（系列生成・マーカー適用）のみ v4.1.3 → v5.2.0 へ移植（§3.5.1）
        ▼
[ブラウザ] 閲覧者
```

依存方向は既存 simulator のクリーンアーキテクチャを踏襲する
（framework → adapter → usecase → domain・内向き）。フロントは JSON 契約のみに依存する。

### 3.2 アーキテクチャパターン選択理由（プロセス構成）

- **採用：ルータ配下のプロセス分離（既存 2 モードのルータ方式へ第 3 上流を追加）**

| パターン | 概要 | NFR-01 負荷分離 | NFR-02 障害分離 | 既存改変量 | 採否 |
|---|---|---|---|---|---|
| 案 1：ルータ配下の別プロセス core（採用） | `/sim/*` を新設 core へプロキシ。計算はさらに子プロセスへ | 適合（ライブ core と別プロセス） | 適合（sim のみ 502） | 小（振り分け表の 1 行追加＋3 値化） | **採用** |
| 案 2：ライブ core に sim API を相乗り | indicator_ui のサーバへエンドポイント追加 | **不適合**（ISSUE-362 GIL 律速・ISSUE-364 単一ワーカー詰まりへ直撃） | 不適合（sim の重処理でライブが停止） | 中 | 棄却 |
| 案 3：リプレイ core に相乗り | serve_replay へエンドポイント追加 | 部分適合（ライブとは別プロセス） | 不適合（リプレイが sim の重処理で停止） | 中 | 棄却 |

- **採用根拠**（プロジェクト規約＋実測）：
  - 実測 1（ISSUE.md:6698・ISSUE-362・OPEN）：サーバ計算量が律速でありクライアント側の一括化だけでは
    1 秒保証に到達しない。重い計算をライブ core の request path へ追加する案 2 は、この実測と正面から矛盾する。
  - 実測 2（ISSUE.md:6782-6788・ISSUE-364・OPEN）：`/market_profile` は専用スレッド 1 本へ投函され
    `done.wait()` が無制限に待つ。一度冷えると以後すべてタイムアウトする。案 2 / 案 3 は同一の
    詰まり方を sim へ再現させる。
  - 前例：ルータの 502 隔離は `.doc/LIVE_REPLAY_UNIFICATION_BASIC_DESIGN.md` §1 で確立済み。
  - 棄却理由（案 2 / 案 3）：負荷分離・障害分離のいずれも満たさない。既存の実測済み障害を新モードへ
    複製することになる。

- **さらに sim コア内でも計算を子プロセスへ出す根拠**：sim コア自身も HTTP サーバであり、
  リクエスト処理スレッド上でバックテストを実行すると sim コア内で ISSUE-364 と同型の詰まりが再発する。
  ジョブを子プロセスへ出し、sim コアは台帳の読み書きのみを行う（依頼者裁定 5 に整合）。

### 3.3 アーキテクチャパターン選択理由（sim コア内部構造）

- **採用：クリーンアーキテクチャ（`simulator/replay_ui/` と同型）**

| パターン | 概要 | 採否 |
|---|---|---|
| 案 A：`replay_ui` 同型のクリーンアーキ（採用） | framework / main（composition_root）／adapter／usecase／domain の 5 層。static_file_server の shared_js_root フォールバックを踏襲 | **採用** |
| 案 B：単一モジュールの薄い HTTP サーバ | ジョブ起動と JSON 返却のみの最小実装 | 棄却 |

- **採用根拠**（プロジェクト規約 `BACKTEST_CLEAN_ARCH.md`／公式設計原則 Martin 2017『Clean Architecture』）：
  - 実測：`simulator/replay_ui/` は framework（`static_file_server.py`・`serve_replay.py`）／
    main（`composition_root.py:30` の `build_replay_app`）／adapter（10 モジュール）／usecase（8 モジュール）／
    domain（3 モジュール）の構成で実在し、同型を採ることで構造の学習コストと審査コストが増えない。
  - 実測：`static_file_server.py:90-103` の `resolve()` は web_dir を優先し miss で shared_js_root へ
    同一 rel でフォールバックする。共有 JS が sim 配下に物理不在でも配信できる（C-5 の単一ソース維持に必須）。

     二重に適用され、どちらが権威か決まらない。**Decorator の適用は戦略ごとの明示指定とし、
     全戦略へ一律に適用しない**。既存のサイジングを持つ戦略を sim モードの対象に含めるか、

     実証 6 により実際の建値はエンジン内部の `derive_quotes` が決め、Decorator へは渡らない。

     推定値である**。この差の許容範囲は §9.3 TBD-14。ティック経路（`on_tick`）は bid / ask が
     引数で渡るため、この差は生じない。

## 5. データ設計

> 出力元：S-3 データ設計

### 5.1 データモデル概要

概念モデルは 2 系統に分かれる。系統 1 は「実行の管理」、系統 2 は「結果の表示」である。
系統 2 は移植元 `report_ui` の JSON 契約と同形とし、フロントの純ロジックを流用可能にする（NFR-05）。

```
系統 1（実行の管理）
  SimulationJob (1)
   ├─ 識別子・投入時刻・状態（受付 / 実行中 / 完了 / 失敗 / 取消）・終了時刻・失敗理由
   ├─ StrategySpec       戦略項目の指定（entry / SL / TP・将来 トレーリング / 部分決済）
   ├─ SizingSpec         資金管理項目の指定（口座条件とサイジング規則）
   └─ DataSpec           対象シンボル・時間足・期間（IS / OOS の分割点を含む）

系統 2（結果の表示・移植元と同形）
  ReportPayload (1)
   ├─ Meta
   ├─ Segment[is] / Segment[oos]  （各: Meta / Report / Bars / Trades / Orders / Agg）
   ├─ Summary{is,oos}
   ├─ Degradation{metric → {is,oos,ratio,delta}}
   └─ Verdict{result, reasons[]}
```

### 5.2 主要エンティティ定義

| エンティティ | 概要 | 主要属性 | 関連エンティティ |
|---|---|---|---|
| SimulationJob | 1 回のバックテスト実行の管理単位 | 識別子, 状態, 投入時刻, 終了時刻, 失敗理由 | StrategySpec, SizingSpec, DataSpec, ReportPayload |
| StrategySpec | 戦略項目の指定 | 使用指標と設定値, entry 条件, SL 条件, TP 条件, 建玉変更条件（TBD-01 依存） | SimulationJob |
| SizingSpec | 資金管理項目の指定 | 初期残高, 証拠金率, ロスカット維持率, 単位あたり価値, サイジング規則と設定値 | SimulationJob |
| DataSpec | 対象データの指定 | シンボル, 時間足, 開始, 終了, IS/OOS 分割点 | SimulationJob |
| ReportPayload | 表示用の結果全体 | meta, segments, summary, degradation, verdict | SimulationJob, Segment |
| Segment | 1 区間（IS または OOS）の完全データ | label, meta, report, bars, trades, orders, agg | Trade, Bar, Agg |
| Trade | 確定トレード 1 件 | id, side, entry/exit の時刻・価格, profit, volume, sl, tp, hold_sec, balance | Segment |
| Agg | 区間集計（グラフ・ヒートマップ・接点の源） | entries 系, pl 系, balance_curve, heat, contacts | Segment |

> 系統 2 のキー構成は移植元 `report_ui` の JSON 契約と同一とする。契約の詳細キー一覧は
> `.doc/sim-report-ui/基本設計書.md` §5.2 を参照し、本書では再定義しない（単一ソース・C-8）。
> `Agg.contacts`（接点）は移植元 `chart.js:88-102` が消費する系列であり、本機能でも同名・同形とする。

### 5.3 データフロー図

- 生成：DataSpec（対象データ）→ 指標供給（因果順守）→ 戦略 → SizingPort Decorator → 実行エンジン →
  結果 → ReportPayload → JSON（ジョブごとの新規パス）。
- 消費：JSON → フロント → 多窓チャート・テーブル・ヒートマップ・比較判定。
- 既存データ（marketdata・fixtures・confirmation）は読み取り専用であり、本機能は書き込まない。

### 5.4 データライフサイクル

- ジョブ台帳と結果ペイロードは、ジョブごとの新規パスに生成する。既存データを上書きしない。
- 結果ペイロードは同一の指定から再生成可能であるため、バックアップの対象としない。
- 保持期間・削除方針は未確定（§9.3 TBD-10）。無制限に蓄積すると容量を消費するため、
  上限件数または保持日数のいずれかを定める必要がある。

### 6.4 通信プロトコル・データ形式

- プロトコル：HTTP（公開 8000 のみ外部公開。内部ポートは loopback 限定）。
  選定理由：既存 2 モードと同一機構を用いるため（C-3）。
- データ形式：JSON。選定理由：移植元 `report_ui` の契約と同形にすることが NFR-05 の前提であり、
  形式を変えると純ロジックの流用ができなくなる。Protobuf / MessagePack は新規依存であり C-3 に反する。
- 状態通知の方式：ポーリング（1 秒間隔）を採用する。

  | 案 | 概要 | 既存機構との整合 | 採否 |
  |---|---|---|---|
  | 案 P：ポーリング（採用） | クライアントが 1 秒間隔で状態を取得 | 既存 core は全て GET / POST のみで構成され、Service Worker のリライト機構も同期要求を前提とする | **採用** |
  | 案 Q：Server-Sent Events / WebSocket | サーバから状態を送出 | Service Worker のリライト対象外となり、ルータのプロキシ実装（`router.py` は `do_GET` / `do_POST` のみ実装・実測 :305-309）も対応していない | 棄却 |

  - 採用根拠（依頼者裁定 5＋実測）：`router.py:305-309` が `do_GET` / `do_POST` のみを実装しており、
    長時間接続の中継機構を持たない。案 Q はルータの大幅改変を要し NFR-06 に反する。

### 7.1 性能設計・スケーラビリティ対策

| 要件 | 数値目標 | 設計対策 | 測定方法 |
|---|---|---|---|
| NFR-01 負荷分離 | ライブ core の request path 占有 0 秒 | sim コアを別プロセス化し、さらに計算を子プロセスへ出す（§3.2） | ジョブ実行中に `/live/candles` の応答時間を実測し、非実行時との差が計測誤差内であることを確認 |
| NFR-03 投入応答 | 1 秒以内 | 投入 API は受理と台帳登録と子プロセス起動のみを行い、計算完了を待たない | 実 HTTP で投入から応答までを実測 |
| NFR-04 状態取得 | 100ms 以内・ポーリング間隔 1 秒 | 状態照会は台帳の読み出しのみ。結果ペイロードを読み込まない | 実 HTTP で連続 100 回の応答時間分布を実測 |
| 指標供給の計算量 | 1 万バーで 1 秒以内 | 全期間 1 回計算（案 ii・§3.5.4）を既定とする。逐次計算（案 i・実測 6.6ms/回＝1 万バーで約 66 秒）は照合基準としてのみ使う | 両案の所要時間と系列一致を実測 |
| 描画性能 | 移植元と同等（数千件規模の取引で操作可能） | 移植元の可視レンジ絞り込みと上限（`chart.js:20` の上限 700・`:310-314` の可視レンジ絞り）をそのまま流用 | ブラウザで hover 応答を実測 |

### 7.2 可用性設計・障害対策

| 要件 | 数値目標 | 設計対策 | 測定方法 |
|---|---|---|---|
| NFR-02 障害分離 | sim コア停止時、ライブ・リプレイの成功率 100% | ルータ配下のプロセス分離。sim のみ 502 | sim コアを停止させ、`/live/*` と `/replay/*` の応答を実測 |
| ジョブ異常時の整合 | 部分的な結果ペイロードの公開 0 件 | 子プロセスの正常終了時のみ結果を公開状態にする（fail-stop） | 異常終了を起こす入力でジョブを投入し、結果が公開されないことを確認 |
| ジョブの取り残し | 孤児プロセス 0 件 | sim コア停止時に実行中ジョブの子プロセスを終了させる。停止は明示的な操作で行う（detached 起動をしない） | 停止後にプロセス一覧を実測 |

> 本機能はローカル開発用途であり、稼働率（99.9% 等）の対象外である。該当なしを明示する。

### 7.3 セキュリティ設計

- 認証・認可：ローカル開発用途のため認証を設けない。内部ポート（ライブ・リプレイ・sim コア）は
  loopback 限定とし外部公開しない（既存方針を踏襲・`router.py:366-373` の既定値が `127.0.0.1`）。
- 通信暗号化：localhost のため TLS を用いない（該当なし）。
- 入力検証：ジョブ投入の入力（戦略項目・資金管理項目・期間）は sim コアの受付 UC で検証する。
  検証を通らない入力は受理せず、ジョブを作らない。
- パストラバーサル対策：静的配信は既存 `static_file_server` の dual-root ガードを用いる。
  同実装は `Path.is_relative_to` による区切り境界一致で CWE-22 を封じる（`static_file_server.py:80-88` に
  実装意図と根拠が記載されている）。sim コアはこの実装を再利用し、独自の解決処理を書かない。
- 子プロセス起動：起動引数にユーザー入力を文字列連結で埋め込まない（シェル経由の起動をしない）。
  入力は台帳のファイルとして渡し、子プロセスがそれを読む。
- 監査ログ：ジョブの投入・状態遷移・失敗理由を記録する（§7.4）。

### 7.4 運用・保守性設計

- ログ設計：sim コアはジョブ投入・状態遷移・子プロセスの終了コードを記録する。
  子プロセスの標準出力・標準エラーはジョブごとのファイルへ保存し、失敗理由の追跡に用いる。
- 監視ポイント：ジョブの状態分布（実行中の滞留件数）・子プロセスの終了コード・結果ペイロードのサイズ。
- 構成管理：sim コアは `simulator/sim_ui/` 配下に集約する（`replay_ui` / `report_ui` と同じ粒度）。
  フロントの新規スイートは `tools/web_suites.txt` へ登録する（C-5・未登録のスイートは
  `tools/tests/test_web_suites_ledger.py` が検出する仕組みが既に存在する）。
- 保守性（責務分離）：実行の管理（系統 1）と結果の表示（系統 2）を JSON 契約で分離する。
  指標の追加は指標供給の登録追加で完結し、モードの追加はモード定義表への追加で完結する（OCP）。
- バックアップ・リストア：結果ペイロードは再生成可能であるためバックアップ対象としない。

### 8.4 リリース・デプロイメント方針

### 10.1 用語集

| sim コア | シミュレーションモードのバックエンド。ルータ配下の別プロセス |
| ジョブ | 1 回のバックテスト実行の管理単位。受付 / 実行中 / 完了 / 失敗 / 取消 の状態を持つ |

| 表駆動 | 分岐を定義表の走査へ置換し、要素追加時に本体を変更しない構造 |
| IS / OOS | In-Sample（学習区間）／ Out-Of-Sample（検証区間） |
| 接点マーカー | 指標と価格の交差点を示すマーカー。売買マーカーとは別概念・別配色 |

## 設計検証（S-5 自己点検）

- **要求整合**：FR-01〜FR-20 を §4.1 の機能一覧へ全マッピングした。要件未対応の設計要素・
  設計未対応の要件はない。ただし FR-07 / FR-08 は実現方式が TBD-01 に依存する状態であり、
  「設計済み」ではなく「裁定待ち」として明示した。
- **技術的実現性**：Phase 1〜6 の実現性は実測で確認した。ルータの表駆動化・core の同型新設・
  Decorator による発注量差替・純ロジックの流用は、いずれも既存の実在物を根拠とする。
  Phase 7 の実現性は TBD-01 の裁定に依存し、本書では確定していない。
- **非機能対応**：NFR-01〜NFR-09 に設計対策と測定方法を記載した。NFR-03 / NFR-04 の数値は
  実務的推奨（仮説）であり、Phase 2 の実測で確定する（TBD-09）。
- **セキュリティ網羅**：ローカル用途のため認証・暗号化は該当なしを明示した。パストラバーサルは
  既存ガードの再利用、子プロセス起動はシェル非経由と入力のファイル受け渡しで対処する。
- **保守性・拡張性**：モード追加は定義表への追加、指標追加は登録追加、サイジング規則の追加は
  `SizingPort` の実装追加で完結する。いずれも本体コードを変更しない（OCP）。
- **残課題**：§9.3 に TBD-01〜TBD-14 を集約した。実証で解決できない前提（文言の意図・
  指標の因果性・v5 のマーカーハンドル仕様・性能数値・サイジング権威の所在・建値の乖離許容）は
  所与とせず、裁定または実測へ委ねた。
- **上流入力の検証**：15 件を実証し、採用 11 件・条件付き採用 2 件・棄却 2 件と判定した（§10.5）。
  棄却した 2 件（v5.2.0 の hover 未検証・座標近接の代替案）は実測により反証されたものであり、
  未検証事項として残すと実証済みの事実を未確定として扱う誤りになるため、本書では訂正して採用した。
