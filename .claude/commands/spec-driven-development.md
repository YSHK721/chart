# 仕様駆動開発プロセス仕様書 v2.1

## 0. 用語集と前提定義

本文書中の用語・分類・時間計測の標準起点は本節のみが正となる。
本文以降のすべての参照は本節を出典とする。

### 0.1 Phase 定義（エスカレーション階層）

エスカレーションは Phase 1 → Phase 2 → Phase 3 の三段階で構成される。
v1.0 で混在していた「Level」表記は廃止し、すべて「Phase」に統一する。

| Phase | 名称 | 起動条件 | 参加者 | 必須出力 | 終了条件 | 次 Phase への遷移条件 |
|-------|------|---------|--------|---------|---------|--------------------|
| Phase 1 | 単一管理者再判定 | (a) 単一エージェントの判断時間が §0.5 上限を超過、または (b) §0.4 の品質チェックを不合格 | 該当エージェント 1 名 + EscalationProcedure-executor | 再判定結果ログ（§0.6 スキーマ準拠） | 再判定文書取得 または t0+30 分経過 | t0+30 分以内に §0.4「解決」要件未充足の場合、Phase 2 |
| Phase 2 | 管理者間協議 | 2 エージェント以上が §0.4「対立」要件を満たす | 対立側全エージェント + EscalationProcedure-executor | 全参加者署名付き合意文書 | §0.4「解決」要件充足 または t0+60 分経過 | t0+60 分以内に未解決、または §0.3 影響範囲「高」が残存する場合、Phase 3 |
| Phase 3 | 統合判断 + 人間介入 | Phase 2 で未解決、または §0.3 影響範囲「高」 | 全関連エージェント + EscalationProcedure-executor + 人間判断者 1 名以上 | 確定判断文書（人間判断者署名付き） | 人間判断者の承認 または t0+24 時間経過 | Phase 3 不調時の動線は §5.6 に従う |

### 0.2 エージェント領域マトリクス

「管理者専門領域」とは下表の各エージェントの担当領域を指す。
「複数領域に跨る判断」とは、本表の異なる行のエージェントが 2 つ以上関与する判断項目を指す。

| エージェント | 担当領域 | 専門スコープ | 参照規格・文献 |
|------------|---------|------------|--------------|
| SystemBasicDesigner-executor | 基本設計 | 機能要件分類、制約条件整理 | — |
| Security-executor | セキュリティ | OWASP Top 10 (2021 版)、脅威モデリング | OWASP Foundation, "OWASP Top 10:2021" |
| SystemBasicDesigner-executor | 内部設計 | モジュール分割、データフロー設計 | — |
| Architecture-executor | アーキテクチャ | 依存関係・レイヤー分離・境界整合性 | Robert C. Martin, "Clean Architecture", 2017 |
| Document-executor | 文書化 | API 仕様書、コードコメント、決定記録 | — |
| TDD-executor | テスト駆動 | テスト設計、Red-Green-Refactor サイクル | Kent Beck, "Test-Driven Development", 2002 |
| Git-executor | 版管理 | ブランチ戦略、コミット粒度 | — |
| CodeReview-executor | コードレビュー | 静的品質、可読性、保守性 | — |
| Coding-executor | 実装 | コード生成、リファクタリング | — |
| EscalationProcedure-executor | エスカレーション統制 | フェーズ間調整、対立解消、ログ管理 | — |

### 0.3 リスク・困難度分類

| 区分 | 高 (High) | 中 (Medium) | 低 (Low) |
|------|----------|------------|---------|
| セキュリティリスク | OWASP Top 10 該当かつ攻撃成立確率 ≥ 30%、または機密情報漏洩可能性あり | OWASP Top 10 該当かつ攻撃成立確率 5–30% | OWASP Top 10 非該当または攻撃成立確率 < 5% |
| 実装困難度 | 既存コードベースに前例なし、または専門家見積で 40 時間以上 | 専門家見積で 10–40 時間 | 専門家見積で 10 時間未満 |
| テスト困難度 | 外部依存・非決定的振る舞い・分散環境を含み単独テスト不可 | モック / スタブで対応可能 | 純粋関数または単一プロセス内で完結 |
| 影響範囲 | データモデル・主要 API・認証認可機構（= プロジェクト根幹） | 単一モジュール内 | 単一関数内 |

「プロジェクト根幹」は「影響範囲：高」と同義とする。

### 0.4 主要状態語の操作的定義

| 用語 | 定義 |
|------|------|
| 解決 (resolved) | 当該 Phase の参加者全員が合意文書に署名し、合意内容が次フェーズの入力として確定された状態 |
| 未解決 (unresolved) | 上記「解決」要件のいずれかが未充足の状態 |
| 対立 | 2 エージェント以上が、同一判断項目に対して論理的に両立しない判定（例：「A = 実施必須」vs「A = 実施不可」）を出力した状態 |
| 領域に跨る | §0.2 の異なる行のエージェントが 2 つ以上関与する判断項目を含む状態 |
| 困難度「高」 | §0.3 の各分類軸で「高」に該当する状態 |
| 品質チェック不合格 | エージェント出力が §0.6 ログスキーマの必須フィールドを欠く、または §0.3 のいずれかの分類で根拠不明と判定された状態 |
| 対立可能性スコア | 検出された潜在対立項目数 / 全判断項目数（0.0–1.0） |

#### 0.4.1 対立可能性スコアの傾斜閾値

単一閾値 0.3 を以下の 4 段階傾斜に置換する。
**いずれの閾値も初期値であり、§0.4.2 校正プロトコルに従って実プロジェクトログから再校正する。**

| スコア帯 | 区分 | 動作 |
|---------|------|------|
| 0.00 – 0.10 | 低 | 動作なし |
| 0.10 – 0.30 | 中 | §0.6 ログスキーマに `trigger = "preconflict_warning"` で警告レコードのみ記録 |
| 0.30 – 0.50 | 高 | 事前協議を関連エージェント間で実施。t0+15 分以内に協議結論が得られない場合 Phase 2 起動 |
| 0.50 – 1.00 | 危機的 | Phase 2 を即時自動起動 |

#### 0.4.2 校正プロトコル

閾値の実証的根拠を確立するため、以下の手順を実施する。

1. プロジェクトごとに全判断項目のスコアと、その後の対立発生有無を §0.6 ログスキーマに全件記録する
2. 累計判断項目が 1,000 件に到達した時点で統計分析を実施：
   - 真陽性率（高スコア時に対立発生）
   - 偽陽性率（高スコア時に対立未発生）
   - 真陰性率（低スコア時に対立未発生）
   - 偽陰性率（低スコア時に対立発生）
3. ROC 曲線分析により偽陽性率 ≤ 0.05 を満たす最小スコアを「危機的」閾値の候補とする
4. 半年ごとに再校正を行う

**現時点では §0.4.1 の閾値はすべて作業仮説（暫定値）であり、実証的根拠は未確立。**

### 0.5 時間計測の標準起点

すべての時間制約は (起点イベント t0, 終点イベント, 上限) の三項で定義する。
時刻はすべて UTC で記録する。

| 制約 | 起点イベント (t0) | 終点イベント | 上限 |
|------|-----------------|------------|------|
| 要件分類完了 | SystemBasicDesigner-executor がタスクを受領した時刻 | 機能要件・非機能要件・制約条件への分類完了出力 | 15 分 |
| セキュリティ判定完了 | Security-executor が要件書を受領した時刻 | OWASP Top 10 分析結果出力 | 20 分 |
| Phase 1 完了 | Phase 1 起動条件成立時刻 | 再判定結果ログ出力 | 30 分 |
| Phase 2 協議完了 | Phase 2 起動条件成立時刻 | 全参加者署名付き合意文書出力 | 60 分 |
| Phase 3 統合判断完了 | Phase 3 起動条件成立時刻 | 人間判断者署名付き確定判断文書出力 | 24 時間 |
| 監視サイクル | 直前の監視サイクル完了時刻 | 次の監視サイクル完了時刻 | 5 分 |
| TDD Red-Green サイクル | 失敗テスト作成完了時刻 | 当該テスト成功確認時刻 | 30 分 |
| ユーザー確認応答 | プロンプト送信時刻 | ユーザー入力受領時刻 | 60 分 |
| 事前協議結論（§0.4.1 高帯） | 事前協議招集時刻 | 全参加者の結論出力 | 15 分 |

### 0.6 ログスキーマ

エスカレーションログは以下の JSON Schema に準拠する。

```json
{
  "log_id": "string (UUID v4)",
  "phase": "1 | 2 | 3 | preconflict",
  "trigger": "string (起動条件の識別子)",
  "t0": "string (ISO 8601, UTC)",
  "participants": ["string (エージェント名)"],
  "input_artifacts": ["string (参照 URI)"],
  "output_artifact": "string (合意文書 URI)",
  "resolution_status": "resolved | unresolved | escalated | timeout",
  "duration_seconds": "integer",
  "next_action": "string",
  "conflict_score": "number (0.0–1.0, optional)",
  "conflict_actually_occurred": "boolean (校正用、後追い記録)"
}
```

- 保存先：`escalation_logs/{YYYY-MM}/{log_id}.json`
- 保持期間：プロジェクト終了後 365 日

### 0.7 トレードオフ優先順位マトリクス（v2.1 新設）

以下は v2.0 §4.2 で部分定義されていたトレードオフ優先順位を全面化したもの。
個別プロジェクトで本既定値を上書きする場合は、Phase 3 にて確定判断文書を発行する。

| 軸 | 既定優先 | 根拠 / 出典 |
|---|---------|------------|
| 速度 vs 正確性 | 正確性 > 速度 | データ整合性損失は不可逆である一方、性能は事後最適化可能（実証根拠：プロジェクト依存のため一般化困難。本既定は安全側基準） |
| 可用性 vs 一貫性 | プロジェクト分類による（下表） | CAP 定理（Brewer 2000）— ネットワーク分断時にいずれかを犠牲にする必要がある |
| コスト vs パフォーマンス | パフォーマンス基準達成後にコスト最適化 | 性能問題の事後修正コストはアーキテクチャ依存で高額化しうる |
| セキュリティ vs ユーザビリティ | セキュリティ > ユーザビリティ | OWASP セキュア設計原則（Defense in Depth） |
| 保守性 vs パフォーマンス最適化 | 保守性 > パフォーマンス（プロファイリングでボトルネック特定後のみ最適化） | Knuth, "Structured Programming with go to Statements" (1974) における "premature optimization" 警告 |
| メモリ vs 計算 | プロファイリング結果に従う | 一般則なし。プロジェクト固有 |
| レイテンシ vs スループット | プロジェクト分類による（下表） | 一般則なし。SLA 要件に依存 |
| 開発速度 vs テストカバレッジ | テストカバレッジ ≥ 80%（行カバレッジ） | カバレッジ閾値は作業仮説。業界慣行的に 70–85% が頻用される（実証根拠：プロジェクト依存） |

#### プロジェクト分類による既定優先（CAP・レイテンシ系）

| プロジェクト分類 | 可用性 vs 一貫性 | レイテンシ vs スループット |
|----------------|----------------|--------------------------|
| 金融・決済・医療 | 一貫性 > 可用性 | レイテンシ > スループット |
| SNS・コンテンツ配信 | 可用性 > 一貫性 | スループット > レイテンシ |
| 業務系（一般） | 一貫性 > 可用性 | プロジェクト個別判断 |
| バッチ処理 | 一貫性 > 可用性 | スループット > レイテンシ |

**注**：本マトリクスの各既定は「安全側」または「業界慣行」に基づく。各プロジェクトのドメイン要件により上書きされうる。上書き時は Phase 3 確定判断文書として記録する。

### 0.8 メトリクスカタログ（v2.1 新設）

§0.6 ログスキーマでは最小フィールドのみを定義していた。
本節は収集すべきメトリクスの全体像を 5 区分で列挙する。
実装時にすべての収集を強制するものではないが、収集省略の判断は Phase 1 以上で記録する。

## 1. 要件フェーズ

### 実行体制
- 主導：SystemBasicDesigner-executor
- 連携：Security-executor
- 統制：EscalationProcedure-executor

### 1.1 要件収集と初期分析

#### デフォルト動作
1. SystemBasicDesigner-executor が `/spec-driven-development [タスク]` を受領（t0 確定、§0.5）
2. EscalationProcedure-executor がプロジェクト監視を開始し、§0.6 ログスキーマに `trigger = "project_baseline"` のレコードを登録
3. 機能要件・非機能要件・制約条件への分類を実施

#### 自動エスカレーション条件
- 上記 3 が t0+15 分以内に完了出力されない場合 → Phase 1 起動
- 複数要件間に技術的矛盾（§0.4「対立」）が検出された場合 → Phase 2 起動

### 1.2 セキュリティ要件統合

1. Security-executor が要件書を受領後、OWASP Top 10 (2021 版) 分析を並行実行
2. EscalationProcedure-executor が §0.5「セキュリティ判定完了」タイマーを起動

#### 自動エスカレーション条件
- セキュリティリスク「高」（§0.3）かつ実装困難度「高」が共起 → Phase 1 起動
- Security-executor 判定が t0+20 分超過 → Phase 1 起動
- Security-executor「実装必須」と SystemBasicDesigner-executor「実装不可」の §0.4 対立成立 → Phase 2 起動

### 1.3 要件検証ループ

1. SystemBasicDesigner-executor が要件書を提示
2. EscalationProcedure-executor が以下を順次実施：
   - 過去エスカレーションログ（§0.6）の全件照合
   - §0.4 対立可能性スコアの算出
   - §0.4.1 傾斜閾値に従い該当帯の動作を実行
3. ユーザー確認プロンプト：「要件に問題はありませんか？(y/n)」
   - `y`：次フェーズへ遷移
   - `n`：修正要求受領、§1.4 へ
   - 60 分以内に応答なし：§5.2 に従う

### 1.4 修正要求の処理

| 修正区分 | 判定基準 | 動作 |
|---------|---------|------|
| 軽微な修正 | 単一エージェント領域内かつ §0.3 影響範囲「低」 | 該当エージェントが直接対応 |
| 中規模修正 | 単一領域だが影響範囲「中」 | Phase 1 起動 |
| 領域跨ぎ修正 | §0.4「領域に跨る」要件充足 | Phase 2 起動 |
| 根幹修正 | §0.3 影響範囲「高」 | Phase 3 起動 |

## 2. 設計フェーズ

### 実行体制
- 主導：SystemBasicDesigner-executor
- 承認：Architecture-executor
- 支援：Document-executor
- 統制：EscalationProcedure-executor（監視サイクル：5 分間隔、§0.5）

### 2.1 基本設計から内部設計への展開

1. SystemBasicDesigner-executor が要件を実装仕様へ分解
2. EscalationProcedure-executor が監視サイクル毎に以下を実施：
   - 実装可能性チェック（§0.3 実装困難度の判定）
   - アーキテクチャ整合性事前評価
   - §1.3-2 と同一手順での対立可能性検出（§0.4.1 傾斜閾値適用）

#### 自動エスカレーション条件
- §0.4「領域に跨る」要件で 5 エージェント以上が関与 → Phase 2 起動
- データフロー設計でセキュリティリスク「中」以上（§0.3） → Phase 1 起動
- 単一モジュール内のクラス数が 20 を超え、かつ public メソッド総数が 100 を超える場合 → Phase 1 起動

### 2.2 アーキテクチャ検証

検証は Stage 1 → Stage 2 → Stage 3 の順で実行する。

#### Stage 1：事前調整
1. EscalationProcedure-executor が Architecture-executor と SystemBasicDesigner-executor の見解を事前確認
2. §0.4.1 傾斜閾値に従い該当帯の動作を実行

#### Stage 2：通常検証

| チェック項目 | 違反時の動作 |
|------------|-------------|
| 依存関係方向性（外側 → 内側のみ） | 違反検出 → Phase 1 起動 |
| レイヤー責任分離 | 境界曖昧 → Phase 2 起動 |
| インターフェース境界 | 複数解釈可能 → Phase 2 起動 |

#### Stage 3：対立発生時の即時対応

| 対立パターン | 対応 |
|------------|------|
| Architecture-executor「承認不可」vs SystemBasicDesigner-executor「変更困難」 | Phase 2 起動 |
| パフォーマンス vs アーキテクチャ整合性 | Phase 2 起動 + §2.4 独立検証セッション並行実行（既定優先順位は §0.7 を参照） |
| 実装コスト vs 設計品質 | Phase 3 起動 + コスト影響分析を並行実行 |

### 2.3 設計文書化

Document-executor は以下を出力：

1. 通常文書：API 仕様書、データモデル定義、処理フロー図
2. エスカレーション統合記録（§0.6 ログ ID と相互参照）：
   - 設計決定の背景
   - 検討した代替案と却下理由
   - 保守・拡張時の注意点
   - 類似問題の予防策

#### 文書品質エスカレーション基準
- 実装困難度「高」相当の理解困難度（§0.3） → Phase 1 起動
- 複数エージェント見解の文書反映が欠落 → Phase 2 起動

### 2.4 独立検証セッション

- 定義：本セッションとは独立した別 Claude セッションを起動し、本セッションの判定文書のみを入力として、本セッション履歴を渡さずに盲検評価を取得する手順
- 利用条件：Stage 3 の「パフォーマンス vs アーキテクチャ整合性」対立時のみ
- 出力：独立評価文書（§0.6 スキーマの `output_artifact` として記録）
- 利用不可時の動線：§5.5 に従う

## 3. 実装計画フェーズ

### 実行体制
- 主導：TDD-executor
- 連携：Git-executor, CodeReview-executor
- 統制：EscalationProcedure-executor

### 3.1 TDD 計画策定

1. TDD-executor が最小実装単位ごとのテスト計画を作成
2. EscalationProcedure-executor が以下を評価：
   - テスト困難度（§0.3）の事前評価
   - Git 戦略との整合性
   - レビュー負荷予測（変更行数 × 影響モジュール数）

#### 自動エスカレーション条件
- テスト困難度「高」が 3 件以上 → Phase 1 起動
- 実装単位間に循環依存が検出 → Phase 2 起動

### 3.2 Git 戦略立案

1. Git-executor がブランチ戦略を策定
2. EscalationProcedure-executor が以下を評価：
   - 並行作業時の競合リスク（§0.3 影響範囲基準）
   - rollback 戦略の妥当性（rollback 後にテストが通るか）
   - コミット粒度（1 コミットあたりの変更行数 ≤ 200 を目安）

#### 並行作業エスカレーション
- feature ブランチ細分化と統合効率の対立 → §0.4.1 傾斜閾値適用
- 1 日 3 回以上の rollback が必要と予測される場合（過去類似プロジェクトでの実績平均が 3 回以上） → Phase 1 起動
- コミット粒度に対する CodeReview-executor の見解との差異 → 事前協議、未解決時に Phase 2 起動

## 4. 実装フェーズ

### 実行体制
- 主導：Coding-executor
- 品質保証：TDD-executor, CodeReview-executor, Security-executor
- 版管理：Git-executor
- 統制：EscalationProcedure-executor（監視サイクル：5 分間隔、§0.5）

### 4.1 段階的実装

実装サイクル：

1. TDD-executor が失敗するテストを作成
   - EscalationProcedure-executor はテスト妥当性を次回監視サイクルで評価
2. Coding-executor が最小限実装
   - EscalationProcedure-executor は実装方針整合性を次回監視サイクルで評価
3. TDD-executor がテスト成功確認
   - 失敗継続時：§0.5「TDD Red-Green サイクル」上限 30 分超過で Phase 1 起動
4. Coding-executor がリファクタリング
   - EscalationProcedure-executor はアーキテクチャ整合性を次回監視サイクルで評価
5. Git-executor が原子的コミット
   - EscalationProcedure-executor はコミット粒度（§3.2 基準）を次回監視サイクルで評価

#### 自動エスカレーション条件
- TDD Red-Green サイクル §0.5 上限超過 → Phase 1 起動
- リファクタリング後のアーキテクチャ整合性違反 → Phase 2 起動
- 連続 3 回のテスト失敗 → Phase 1 起動。原因がアーキテクチャ起因の場合は Phase 2 へ昇格

### 4.2 継続的品質チェック

並行監視：

| エージェント | チェック内容 | 頻度 |
|------------|------------|------|
| CodeReview-executor | 実装品質（静的解析、可読性） | 監視サイクル毎 |
| Security-executor | セキュリティチェック（§0.3） | 監視サイクル毎 |
| EscalationProcedure-executor | 並行処理結果統合 | 監視サイクル毎 |

#### 複合問題発生時の優先順位

§0.7 トレードオフ優先順位マトリクスに従う。
特に頻出する複合問題のうち、セキュリティ・ビルド・コード品質の 3 軸については以下の固定優先順位を適用：

セキュリティ > ビルドエラー > コード品質

複数問題同時発生時の処理：
1. 全問題を Phase 2 単一協議に統合招集
2. 解決策の相互影響評価を並行実施
3. 解決時間予測（過去同種事例の所要時間中央値）に基づく分岐：
   - 予測 ≤ 30 分：並行協議
   - 予測 > 30 分：順次協議

### 4.3 文書更新

1. 通常更新：コードコメント、API 仕様の同期
2. エスカレーション記録統合（§0.6 ログ ID と相互参照）：
   - 実装中の判断背景
   - パフォーマンス / セキュリティのトレードオフ記録（§0.7 既定値からの逸脱は明記）
   - 技術的負債の明記

#### 自動文書化
- エスカレーション発生時：§0.6 ログスキーマで自動記録
- 解決後：Document-executor が文書統合を実施
- 月次（毎月 1 日 00:00 JST）：EscalationProcedure-executor が §0.8 メトリクスを集計し改善分析を実施

## 5. 例外処理動線

### 5.1 EscalationProcedure-executor 自身の応答不能
- 検出条件：監視サイクル上限の 3 倍（15 分）応答なし
- 動作：(a) 該当フェーズの主導エージェントが直接 §0.6 ログ出力、(b) 全エージェントを一時停止状態へ移行、(c) プロジェクトオーナー（人間）へ通知

### 5.2 ユーザー確認プロンプトへの応答なし
- 検出条件：プロンプト送信後 60 分応答なし（§0.5）
- 動作：プロジェクトを「ユーザー応答待機」状態へ移行、エージェント処理を停止

### 5.3 複数 Phase 2 の同時発生
- 検出条件：未解決の Phase 2 が 2 件以上
- 動作：先行 Phase 2 を優先処理。後続は待機列に格納し、先行 Phase 2 解決後に順次処理

### 5.4 検証ループの無限再試行
- 検出条件：同一判断項目への Phase 1 起動回数が 3 回到達
- 動作：Phase 2 へ自動昇格

### 5.5 §2.4 独立検証セッション利用不可
- 検出条件：別 Claude セッション起動失敗
- 動作：Phase 3 へ昇格し、人間判断者が直接判断

### 5.6 Phase 3 不調
- 検出条件：Phase 3 制限時間 24 時間超過、または人間判断者が確定判断文書への署名を拒否
- 動作：(a) プロジェクトを凍結状態（全エージェント停止）へ移行、(b) プロジェクトオーナーへ最終エスカレーション、(c) プロジェクトオーナーの裁定後、再開条件確定後に解凍

## 共通プロシージャ集

本文では各フェーズに同一パターンを反復記述している。
パターンを共通プロシージャとして抽出した結果を以下に示す。本案は本文の各記述を共通プロシージャ呼び出しに置換する形で適用予定。

### P1：対立可能性スコア算出
- 入力：判断項目リスト、関連エージェント出力
- 処理：潜在対立項目数 / 全判断項目数を計算
- 出力：スコア (0.0–1.0)
- 参照：§0.4

### P2：傾斜閾値判定
- 入力：スコア
- 処理：§0.4.1 傾斜閾値表に従い該当帯を判定
- 出力：実行すべき動作（無動作 / 警告 / 事前協議 / Phase 2 起動）

### P3：タイマー起動・監視
- 入力：制約名、t0、上限時間
- 処理：§0.5 表から該当行を参照、上限超過時にイベント発火
- 出力：超過イベント または 完了イベント

### P4：§0.6 ログ記録
- 入力：phase, trigger, t0, participants, input_artifacts
- 処理：§0.6 スキーマでレコード生成、保存先へ書き込み
- 出力：log_id

### P5：フェーズ遷移判定
- 入力：現Phase、参加者出力、経過時間
- 処理：§0.4 解決要件を判定
- 出力：解決 / 未解決 / 次Phase へ遷移

### P6：ユーザー確認プロンプト
- 入力：プロンプト文
- 処理：表示、応答待機（§0.5「ユーザー確認応答」上限 60 分）
- 出力：y / n / タイムアウト

#### 本文側からの呼び出し例

```
§1.3 要件検証ループ：
  1. SystemBasicDesigner-executor が要件書提示
  2. P1 を呼び出し → スコア取得
  3. P2 を呼び出し → 動作決定
  4. 動作が「事前協議」の場合：P3 で 15 分タイマー起動
  5. P6 を呼び出し → ユーザー確認
```
