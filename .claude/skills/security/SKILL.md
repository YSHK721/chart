# 目的

脅威に強い構造を設計する。

## §0. 仮説と事実の区別

| 区分 | 取り扱い | 表記 |
|---|---|---|
| OWASP Top 10:2025 / OWASP LLM Top 10 2025 / Verizon DBIR 2025 / Sonatype 2026 SoSC で公表された統計・カテゴリ・推奨対策 | そのまま採用する | 出典名と公開年を併記する |
| プロジェクト規約（言語選択・フレームワーク・運用環境・組織成熟度区分） | プロジェクト内で適用する | 「プロジェクト規約より」と明示する |
| 実務派生（ツール選択・運用手順・組織別カスタマイズ） | 推奨は仮説扱い | 「（実務的推奨／仮説）」と明示する |
| 不明（出典バージョン未確認・統計値の最新化未確認） | TBD として未解決事項に記録する | 「TBD: 確認要」と明示する |

## §1. 定義

**脅威に強い構造とは、最新の実証された脅威カテゴリに対して、組織成熟度に応じた最小権限の対策を多層に配置することである。** 本スキルは対象システム・機能を入力とし、(1) 脅威識別、(2) リスク評価、(3) 対策選定、(4) ツール選択、(5) レビュー判定、(6) 観測・更新計画の各段階を経て、出典に紐付いた対策一覧と判定済みレビュー結果を出力する一連の認知手順である。

## §2. 原理原則

- **実用的セキュリティ**：実装可能で効果が計測可能な対策を、理論的完璧性に優先する。
- **継続的改善**：単発の実装ではなく、継続的な計測と再評価を伴うプロセスとして運用する。
- **リスクベースアプローチ**：組織のリスク許容度とリソース配分に応じた対策を選択する。
- **多層防御 (Defense in Depth)**：単一の対策に依存せず、複数の防御層を構築する。
- **最小権限**：認証・認可・LLM ツール許可・CI 実行権限は必要最小範囲に限定する。
- **出典の鮮度維持**：脅威情報は年版を持つ出典に基づき、差分検出基準により陳腐化を検出する。

## §3. 用語定義

| 用語 | 定義 |
|---|---|
| アクター | 攻撃者・内部不正者・悪性パッケージ作者などの脅威主体。脅威モデリングの起点 |
| 攻撃面 (Attack Surface) | 外部から接触可能なエンドポイント・依存関係・公開資産の総体 |
| 多層防御 | 認証・認可・暗号化・入力検証・ログ監査などを独立した防御層として配置する設計原則 |
| ゼロトラスト | すべてのリクエストに対して認証・認可を実施する原則 |
| SBOM | Software Bill of Materials。CycloneDX または SPDX 形式で全依存関係を可視化したもの |
| SCA | Software Composition Analysis。依存パッケージの既知脆弱性検出 |
| SAST | Static Application Security Testing。ソースコードの静的解析 |
| DAST | Dynamic Application Security Testing。実行中アプリケーションへの動的攻撃検証 |
| IAST | Interactive Application Security Testing。実行時計装による継続的検出 |
| CSPM | Cloud Security Posture Management。クラウド設定誤りを継続検出する仕組み |
| CISA KEV | Known Exploited Vulnerabilities。CISA が公開する実害確認済み脆弱性カタログ |
| CVSS | Common Vulnerability Scoring System。脆弱性の重大度数値化指標 |
| Sigstore | OSS パッケージの署名・検証基盤 |
| プロンプトインジェクション | LLM への悪意ある入力でシステムプロンプトを上書き・抽出する攻撃 |
| 組織成熟度 | Startup（無料・OSS 中心）/ Mid（OSS + 商用併用）/ Enterprise（包括ガバナンス）の 3 区分 |

## §4. 強制ルール

| ルール | 内容 |
|---|---|
| 出典明示 | すべての脅威・対策・統計値に OWASP / DBIR / Sonatype / プロジェクト規約 / 仮説 のいずれかを併記する |
| 仮説明示 | 実務派生（ツール選択・運用手順・組織別カスタマイズ）は「（実務的推奨／仮説）」と注記する |
| 曖昧表現禁止 | 「適切に」「効率的に」「柔軟に」「適宜」「一般的に」「速やかに」「リアルタイム」を使用しない |
| 数値強制 | CVSS スコア・パッチ期限・有効期限・cost パラメータは数値で明示する |
| 主観禁止 | 「強固な対策」「優れたツール」等の感想を出力しない |
| 禁止アルゴリズム | MD5・SHA-1・DES・3DES・RC4・TLS 1.1 以前を必須対策の選択肢から除外する |
| 修正方法必須 | レビュー不合格項目には具体的な修正手順を併記する |
| 出力テンプレート参照 | 成果物出力時は必ず `${CLAUDE_SKILL_DIR}/output.md` を読み込み、その構造に従う。読み込みを省略した出力生成を禁止する |
| 完了基準遵守 | §6 完了基準（DoD）の全項目をチェックしてから報告する |
| 思考代替防止 | 各 step の「手順」は必ず「ユーザーからの問い」「根拠」と併記する。手順単独記述を禁止する（思考代替リスク防御 D1：原理ラッピング） |
| 判定基準優先 | 各 step で「手順」と「問い・根拠」が衝突した場合は「問い・根拠」を優先する。手順への機械的従属を禁止する（思考代替リスク防御 D10：メタルール） |

## §5. 実行プロセス

判断は以下の順序で行う：
**入力定義 → 脅威識別 → リスク評価 → 対策選定 → ツール選択 → レビュー → 観測・更新計画**

各ステップ本文は「ユーザーからの問い／根拠／手順／出力」の 4 要素プロトコルで構成する（プロジェクト規約 B.6 重複適用回避：T1+T2 ステップ詳細化要素は適用しない）。

4 要素プロトコルにおいて「ユーザーからの問い」と「根拠」は判定基準層を構成し、「手順」を原理的に拘束する（思考代替リスク防御 D1：原理ラッピング）。手順単独の記述は §4「思考代替防止」ルールで禁止される。手順は問い・根拠を達成する手段であり、両者衝突時は問い・根拠が優先される（§4「判定基準優先」ルール）。

### 着手前ゲート（入力検証）

設計に着手する前に以下を確認する。1 つでも未充足なら作業を中断し、ユーザーに確認する。

| 項目 | 確認事項 | 未充足時の対応 |
|---|---|---|
| 対象範囲 | 分析・レビュー対象（システム名 / コンポーネント / コミット範囲）が明示されているか | ユーザーに対象を質問する |
| 組織成熟度 | Startup / Mid / Enterprise のいずれかが識別可能か | プロジェクト規約・運用情報から推定。不明なら質問する |
| 出典バージョン | 最新出典（OWASP 2025 / DBIR 2025 / Sonatype 2026 SoSC / LLM Top 10 2025）であるか | TBD として記録し、`references/threat-info-update.md` の差分検出基準を後続で適用する |
| LLM 連携の有無 | システムが LLM を呼び出すか／LLM 出力を実行系に渡すか | 「あり」の場合のみ S-2 で OWASP LLM Top 10 2025 をマッピング対象に追加する |

### step S-1: 入力定義・組織成熟度確定

- **ユーザーからの問い**：対象システム・組織成熟度・現状の防御層は何か？
- **根拠**：組織成熟度別アプローチ（`references/tool-matrix.md`）。Startup と Enterprise では推奨ツール・運用負荷が大きく異なるため、初段で確定しなければ後続の対策・ツール選定が成立しない。
- **手順**：
    1. 対象範囲（システム / コンポーネント / 機能 / コミット差分）を確定する
    2. 組織成熟度を Startup / Mid / Enterprise の 3 区分から判定する
    3. 攻撃面（公開エンドポイント数・依存関係数・LLM 連携の有無・外部公開資産）を列挙する
    4. 既存防御層（認証・認可・暗号化・監査ログ・WAF・SCA 導入状況）を確認する
- **出力**：output.md §1 に記載。対象範囲・組織成熟度・攻撃面・既存防御層を明記する。

### step S-2: 脅威識別（OWASP / Supply Chain / LLM マッピング）

- **ユーザーからの問い**：対象に該当する脅威カテゴリはどれか？ 該当根拠は何か？
- **根拠**：OWASP Top 10:2025 全 10 カテゴリ、OWASP LLM Top 10 2025 全 10 カテゴリ、Verizon DBIR 2025 で確認された脆弱性悪用・エッジ機器・ランサムウェア、Sonatype 2026 SoSC のサプライチェーン統計。出典詳細は `${CLAUDE_SKILL_DIR}/references/threat-catalog.md` を参照する。
- **手順**：
    1. `${CLAUDE_SKILL_DIR}/references/threat-catalog.md` を読み込む
    2. S-1 で列挙した機能（認証・API・永続化・外部依存・LLM 連携）を脅威カテゴリにマッピングする
    3. 該当しないカテゴリは対象外として明記する（一律全件適用を禁止する）
    4. LLM 連携が無い場合は OWASP LLM Top 10 2025 を対象外とする
- **出力**：output.md §2 に記載。機能 × カテゴリ × 該当根拠の表を作成する。

### step S-3: リスク評価

- **ユーザーからの問い**：各脅威の影響度・発生確率・優先順位はどうなるか？
- **根拠**：CVSS v3.1 / v4.0 のスコア、Verizon DBIR 2025 の侵害経路統計（盗難クレデンシャル 22% / 第三者経由 30% / 脆弱性悪用 20% / エッジ機器 22% / ランサムウェア 44%）、Sonatype の高 CVSS リリース割合（Maven Central 40% / NuGet 39%）。
- **手順**：
    1. S-2 で識別した各脅威に CVSS スコア（既知脆弱性がある場合）または DBIR 統計値を当てる
    2. 影響度（Critical / High / Medium / Low）と発生確率（High / Medium / Low）を決定する
    3. リスクレベル（Critical / High / Medium / Low）を確定し、対応優先順位を付与する
    4. プロジェクト固有要因（規制業種・PII 取扱・公開範囲）でリスクレベルを補正する
- **出力**：output.md §3 に記載。脅威 × CVSS/統計値 × 影響度 × 発生確率 × リスクレベル × 優先順位の表を作成する。

### step S-4: 対策選定（必須対策マッピング）

- **ユーザーからの問い**：各脅威に対する必須対策は何か？ 多層防御をどこに配置するか？
- **根拠**：`${CLAUDE_SKILL_DIR}/references/threat-catalog.md` 各節の「必須対策」行は OWASP / DBIR / Sonatype の出典に紐付いて定義されている。原理原則「多層防御」により、単一カテゴリに対して認証層・API 層・永続化層・CI/CD 層など複数層に対策を配置する。
- **手順**：
    1. S-2 で識別した脅威カテゴリそれぞれについて、`references/threat-catalog.md` の「必須対策」を引用する
    2. 各対策の配置層（認証 / 認可 / API / 永続化 / 通信 / CI/CD / LLM ガードレール）を確定する
    3. 既存防御層（S-1 で確認）との重複を識別し、新規追加対策と既存対策を区別する
    4. 禁止アルゴリズム（§4）を選択肢から除外する
- **出力**：output.md §4 に記載。脅威カテゴリ × 必須対策 × 配置層 × 出典の表を作成する。

### step S-5: ツール選択（成熟度マトリックス適用）

- **ユーザーからの問い**：S-4 の対策実装に使うツールは何か？ 偽陽性対策・CI/CD 統合点はどこか？
- **根拠**：`${CLAUDE_SKILL_DIR}/references/tool-matrix.md` の組織成熟度別マトリックス。Startup → 無料・OSS / Mid → OSS + 商用 / Enterprise → 包括ガバナンスの方針に基づく。
- **手順**：
    1. S-1 で確定した組織成熟度に従い、SCA / SAST / DAST / IAST 各カテゴリのツールを選定する
    2. 偽陽性対策（抑制ファイル / インテリジェントフィルタ / カスタマイズポリシー）を併記する
    3. CI/CD パイプラインへの統合点（PR チェック / 夜間スキャン / リリースゲート）を確定する
    4. 成熟度を超えた高度ツール選択（実務的推奨／仮説）が必要なら根拠を併記する
- **出力**：output.md §5 に記載。カテゴリ × 選定ツール × 採用理由 × 偽陽性対策 × CI/CD 統合点の表を作成する。

### step S-6: レビュー実施（優先度付きチェックリスト）

- **ユーザーからの問い**：実装は Critical / High / Medium 各基準を満たすか？ 不合格項目の修正手順は何か？
- **根拠**：`${CLAUDE_SKILL_DIR}/references/review-checklist.md` の 3 段階チェックリスト。Critical 4 項目（マージブロッカー）/ High 4 項目（必須修正）/ Medium 4 項目（推奨修正）。
- **手順**：
    1. `references/review-checklist.md` を読み込み、🔴 Critical 4 項目を全件検証する
    2. 続いて 🟡 High 4 項目を検証する
    3. 続いて 🟢 Medium 4 項目を検証する
    4. 不合格項目は §4「修正方法必須」ルールに従い具体的な修正手順を併記する
    5. Critical 不合格が 1 件でもあれば「マージ不可」と判定する
- **出力**：output.md §6 に記載。3 段階それぞれの検出項目 × 判定基準充足 × 修正内容を表形式で記載する。

### step S-7: 観測・更新計画

- **ユーザーからの問い**：脅威情報・対策の陳腐化をいつ・どう検出するか？
- **根拠**：`${CLAUDE_SKILL_DIR}/references/threat-info-update.md` の差分検出基準（カテゴリ番号変更 / 統計値 ±5pt / 新規カテゴリ / 必須対策の陳腐化 / 新興マルウェア確認）。OWASP / DBIR / Sonatype は年版を持ち、本スキルが採用した 2025 年版は 2026 年以降に改訂される可能性がある。
- **手順**：
    1. 監視対象（OWASP 改訂 / DBIR 公開 / Sonatype SoSC 公開 / CISA KEV 重大追加 / OWASP LLM 改訂）を確定する
    2. 差分検出基準を `references/threat-info-update.md` から引用して適用する
    3. 更新トリガ（年次 / 重大事象発生時 / 統計値 ±5pt 変動時）を確定する
    4. 出典バージョンの記録方法（リリースタグ / commit ID / 文書末尾の出典欄）を決定する
- **出力**：output.md §7 に記載。監視対象 × 差分検出基準 × 更新トリガ × 適用規則の表を作成する。

### ステップ完了判定（思考代替リスク防御 D6：完了判定ゲート）

各 step（S-1〜S-7）の「手順」完了後、次の step に進む前に以下を検証する：

- [ ] 「ユーザーからの問い」への回答が「出力」に明示的に含まれているか
- [ ] 「根拠」が成立する条件下で「出力」が成立しているか（OWASP / DBIR / Sonatype / プロジェクト規約 / 仮説のいずれかに紐付くか）
- [ ] 着手前ゲートの 4 項目（対象範囲 / 組織成熟度 / 出典バージョン / LLM 連携の有無）と矛盾する結果が生じていないか
- [ ] 「出力」が次 step の入力として整合するか（例：S-2 識別された脅威 → S-3 リスク評価の入力）
- [ ] 曖昧表現（§4 禁止語）・主観表現が混入していないか

**充足しない場合の対応**：

1. 手順を機械的に再実行しない。問い・根拠に立ち返り、別経路を検討する
2. 別経路でも充足しない場合、最大 3 回まで再試行する
3. 3 回失敗時は §6「異常時の出力」フォーマットで `[SECURITY-DESIGN-HALT]` を発行する

**注意**：手順完了 ≠ ステップ完了。本ゲートを通過して初めてステップ完了とみなす。

## §6. 結果出力

### 通常時の出力

S-7 完了後、以下の手順で成果物を出力する。

1. `${CLAUDE_SKILL_DIR}/output.md` を読み込む
2. output.md に記載されたテンプレート構造に従って、S-1〜S-7 の出力を集約する
3. テンプレートの各章を、対応する S-X の出力で埋める

**注意**：output.md の読み込みを省略して出力を生成することは禁止する。テンプレート構造の整合性を保証するため、必ず読み込みを行う。

### 異常時の出力

着手前ゲートで未充足項目があった、または分析途中で前提が成立しないと判明した場合、成果物を出力せず以下のフォーマットで中断を報告する。

```
[SECURITY-DESIGN-HALT]
段階: <S-X / 着手前ゲート>
原因: <対象範囲不明 / 組織成熟度不明 / 出典バージョン未確認 / LLM 連携不明 / その他>
詳細: <具体的な不足情報>
推奨アクション: <ユーザーが取るべき次のステップ（例：対象システムの確認 / 出典の最新化チェック）>
```
