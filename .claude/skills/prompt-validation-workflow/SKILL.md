## 目的

LLMの出力が直前の合意形成に過度に同調する傾向(追従性)を、構造的に遮断する。

## 絶対遵守事項

- 本タスクは努力レベル `${CLAUDE_EFFORT}` で実行する。
- このレベルで追随バイアスを抑制して、自己レビューを実行する。
- 自己レビューの結果を `${CLAUDE_SKILL_DIR}/output.md` のフォーマットに遵守して出力する。

## 用語定義

| 用語 | 定義 |
|---|---|
| 実証的証拠 | テスト結果・ログ出力・静的解析結果・コード差分・CI 実行結果など、第三者が検証可能な客観的データ |
| Pre-mortem(想定失敗分析) | 成果物が本番で失敗したと仮定し、最も可能性の高い失敗原因を能動的に推定する作業 |
| 証拠先行 | 判定（合格・棄却）より先に実証的証拠を提示する順序規律 |

## 自己レビューの手順

**この出力が本番で失敗したと仮定する。最も可能性の高い失敗原因を実証的証拠と照らして検証せよ。**

### 実施手順

1. **Pre-mortem**: 成果物が失敗したと仮定し、最も可能性の高い失敗原因を 1 件以上推定する。視点を「擁護」から「死因究明」に固定する。
2. **証拠先行**: 推定した失敗原因について、判定より先に実証的証拠（テスト結果・ログ・差分・静的解析）を提示する。証拠を後付けする順序は禁止する。
3. **検証**: 提示した証拠と照らして、推定原因が成立するか棄却されるかを判定する。
4. **反映**: 成立した原因については、判断を撤回するか、または成果物を修正する。すべて棄却された場合、または成立した原因が反映済みの状態で、完了を報告する。
5. **残存リスク特定**: 本タスクの範囲外で後続作業に委ねるべき項目を列挙する。該当がない場合は「なし」を明示する。

### 立証責任の非対称性

| 主張 | 必要なもの |
|---|---|
| 合格主張 | 実証的証拠の提示が必須 |
| 棄却・疑問提起 | 証拠不要（疑問の指摘で成立） |

デフォルトを慎重側に倒し、「証拠不在＝棄却」を構造化する。

### 完了条件

| 項目 | 基準 |
|---|---|
| Pre-mortem | 最も可能性の高い失敗原因が 1 件以上特定されている |
| 証拠先行 | 判定より前に実証的証拠が提示されている |
| 反映 | 成立した原因は撤回または修正に反映済み |
| 残存リスク | 後続作業に委ねる項目が列挙されている、または「なし」が明示されている |

## 追従性バイアスの典型アンチパターン

Pre-mortem 段階で **以下のパターンが含まれていないか必ず確認する**。該当するときは追従性バイアスが疑われるため、対応する検証を pre-mortem に強制的に追加する。

### A. 軽量検証の落とし穴

「軽量検証」「軽量レビュー」「簡易チェック」「quick / light verification」等の名称は **検証対象の範囲を限定する意味** であって、判断強度を下げる意味ではない。以下の混同が頻発する。

| 誤った理解（追従性バイアス） | 正しい理解 |
|---|---|
| 軽量 = 検証対象を絞る + 肯定的結論を急ぐ | 軽量 = 最重要 1〜数件を **厳密に** 検証する |
| 部分的な肯定的証拠 → 全体肯定の結論 | 部分的証拠は **部分的結論のみ** 支持する |
| 構造的検証の名称（triangulation 等）から「やった気」になる | 検証の名称が意味する **構造的要件**（例: 3 辺すべて）を満たすまで未完了 |
| 「ユーザーが軽量と承認した」=「結論を急いで良い」と解釈 | ユーザーの承認は **検証範囲の合意** であり、結論の質を下げる承認ではない |

#### Pre-mortem に強制追加する自己質問

- 「軽量 / 簡易 / 部分 / quick / light」と称した検証で、結論ありきになっていないか
- 「N 辺三角検証」等の構造的命名で、N 辺すべてを実施したか
- 「Theorem / Lemma / Specification 引用」で、定理の射程外に拡大解釈していないか
- ユーザーの承認語彙（"案 X 承認"）に対して、**承認範囲を超えた結論を付与** していないか

### B. 用語拡大解釈

引用した定理・仕様・先行事例の **射程（適用条件）** を確認せずに、自分の主張に都合よく拡大する。

| 観察 | 拡大解釈の例 |
|---|---|
| 「Theorem 1 は stack=4000 で 86o が mix 必須」と証明 | 「全 stack で minimax は mixed を要求」（射程外、stack=4000 specific） |
| 「論文 Figure 5 で複数 stack に mix hand が観測」と記述 | 「すべての stack で必ず mix が必要」（観測 → 必然性の論理飛躍） |
| 「仕様書に X と記載」 | 「X を含むすべての類似ケース」（仕様外への拡大） |

#### 検出方法

引用元の **適用条件 / 前提条件 / 範囲** を明示的に列挙し、自分の主張がその範囲内かを確認する。範囲外なら「extrapolation である」と明示する。

## 多辺検証の事前列挙（Triangulation Checklist）

3 辺以上の構造的検証（triangulation / cross-validation / multi-source comparison 等）を実施する際は、**Pre-mortem の前に検証対象 N 辺を列挙し、checklist として提示する**。

### 列挙の構造

```markdown
## 検証する N 辺（事前列挙）

| # | 辺 | 検証内容 | 実施状態 | 証拠強度 |
|---|----|---------|----------|---------|
| 1 | A vs B | ... | □ pending / ☑ done | ★ / ★★ / ★★★ |
| 2 | A vs C | ... | □ pending / ☑ done | ★ / ★★ / ★★★ |
| 3 | B vs C | ... | □ pending / ☑ done | ★ / ★★ / ★★★ |
```

### 完了基準

| 状態 | 判定 |
|---|---|
| 全辺 ☑ done かつ証拠強度 ≥ ★★ | **完了**（結論を全面採用可） |
| 全辺 ☑ done だが一部 ★ のみ | **条件付き完了**（弱辺の不確実性を残存リスクに転記） |
| 一部の辺が pending | **部分検証**（"triangulation 完了" と称してはならない）|
| 部分検証で結論を出す場合 | 未実施の辺による不確実性を **明示的にラベリング** し、残存リスクに転記 |

### 違反例（本ワークフロー実施履歴より、2026-05-16）

ISSUE-014 Phase 3a「軽量三角検証」の失敗:

| # | 辺 | 検証内容 | 実施状態 | 結果 |
|---|----|---------|----------|------|
| 1 | CandyPoker vs Theorem 1 | minimally-mixed = non-minimax と判定 | ☑ done | CandyPoker は非 minimax 設計と確定 |
| 2 | **our_solver vs M-S 2007** | **academic gold standard との直接比較** | **□ skipped** | **未検証**（自己レビューで露呈） |
| 3 | our_solver vs CandyPoker at stack_bb=15 | 14 hand 系統的乖離を観測 | ☑ done | 乖離原因の片側のみ判明 |

**結果**: 辺 #2 の skip により「our_solver = academic 整合」を過大評価。後の自己レビューで独立検証を実施した結果、stack_bb=7 で我々 66.3% jam vs M-S 57% jam の ~10 pp 系統的乖離が判明し、ISSUE-015 として独立調査を起票することになった。

**再発防止**: 事前に 3 辺を checklist 化していれば、辺 #2 の skip が pre-mortem 段階で明示的に検出され、判断強度を「部分検証」として正しくラベリングできた。
