# 目的

変更に強い構造を設計する。

## §0. 仮説と事実の区別

| 区分 | 取り扱い | 表記 |
|---|---|---|
| Clean Architecture 原典で定義された原則（DIP・SRP・4 レイヤー・境界） | そのまま採用する | 出典なしで断定する |
| プロジェクト規約（言語・フレームワーク・命名） | プロジェクト内で適用する | 「プロジェクト規約より」と明示する |
| 実装上の選択（ディレクトリ名・ファイル分割粒度・DI 手法） | 推奨は仮説扱い | 「（実務的推奨／仮説）」と明示する |

## §1. 定義

**変更に強い設計とは、変更の影響が波及しないように局所的に止めることが設計することである。** 本スキルは仕様・要件を入力に、依存方向と境界によって変更影響を局所化するレイヤー構造（domain / usecase / adapter / framework）を設計する一連の認知手順である。

## §2. 原理原則

- **SRP**：アクターの責務を明確化し分離する。
- **DIP**：依存関係の方向性を逆転させる。
- 偶有的性質は、本質的性質から分離する。
- 本質的性質は、内側に設計する。
- 偶有的性質は、外側に設計する。
- 変更の影響を局所的に止める。
- 制約の明確化により設計可能領域を画定する。

## §3. 用語定義

| 用語 | 定義 |
|---|---|
| アクター | システムに独立して変更要求を出す主体（人・部門・上位システム）。SRP の責務分割単位 |
| ユースケース | Application Business Rules 層を担う。アクターの目的を実現する手順とその Input／Output Model を定義 |
| エンティティ | Enterprise Business Rules 層を担う。アプリケーションが存在しなくても成り立つ不変ルールと公開振る舞いを持つ |
| Input Boundary | ユースケース層に置かれ Controller から呼び出されるインターフェース |
| Output Boundary | ユースケース層に置かれ Presenter / Repository / Gateway によって実装されるインターフェース |
| Controller | UI／API リクエストを Input Model に変換し Input Boundary を呼び出すアダプター |
| Presenter | Output Model を ViewModel／レスポンス DTO に変換するアダプター |
| Repository / Gateway | 永続化・外部 API への抽象。Output Boundary を実装する |
| Composition Root | main モジュール。全層を import し DI を組み立てる |
| Dependency Rule | ソースコード依存は内側を指さなければならない（Martin 2017） |
| 本質的性質 | ドメイン固有のビジネスルール（変更頻度低） |
| 偶有的性質 | フレームワーク・DB・UI 等の技術選択（変更頻度高） |
| YAGNI | You Aren't Gonna Need It。現存しない要求のための抽象化を避ける原則 |

## §4. 強制ルール

| ルール | 内容 |
|---|---|
| 出典明示 | 設計判断には Martin (2017) の章番号 / プロジェクト規約 / 仮説 のいずれかを併記する |
| 仮説明示 | ディレクトリ構造・実装着手順序などの実務派生は「（実務的推奨／仮説）」と注記する |
| 曖昧表現禁止 | 「適切に」「効率的に」「柔軟に」「適宜」「一般的に」を使用しない |
| YAGNI 強制 | S-9 を必ず実行し、変更要因が実在しない境界は削除候補として明示する |
| 主観禁止 | 「良い設計」「美しい構造」等の感想を出力しない |
| 修正方法必須 | 依存方向違反を検出したら、DIP による解消方法を併記する |
| 出力テンプレート参照 | 成果物出力時は必ず `${CLAUDE_SKILL_DIR}/output.md` を読み込み、その構造に従う。読み込みを省略した出力生成を禁止する |
| 完了基準遵守 | §6 完了基準（DoD）の全項目をチェックしてから報告する |
| 思考代替防止 | 各 step の「手順」は必ず「ユーザーからの問い」「根拠」と併記する。手順単独記述を禁止する（思考代替リスク防御 D1：原理ラッピング） |
| 問い・根拠優先 | 各 step で「手順」と「問い・根拠」が衝突した場合は「問い・根拠」を優先する。手順への機械的従属を禁止する（思考代替リスク防御 D10：メタルール） |

## §5. 実行プロセス

設計判断は以下の順序で行う：
**Purpose → Change factors → Responsibility → Dependency direction → Boundary → Implementation → Verification**

各ステップは原理原則のうちどれを実装するかを示す。各ステップ本文は「ユーザーからの問い／根拠／手順／出力」の 4 要素プロトコルで構成する（プロジェクト規約 B.6 重複適用回避：T1+T2 ステップ詳細化要素は適用しない）。

4 要素プロトコルにおいて「ユーザーからの問い」と「根拠」は判定基準層を構成し、「手順」を原理的に拘束する（思考代替リスク防御 D1：原理ラッピング）。手順単独の記述は §4「思考代替防止」ルールで禁止される。手順は問い・根拠を達成する手段であり、両者衝突時は問い・根拠が優先される（§4「問い・根拠優先」ルール）。

### 着手前ゲート（入力検証）

設計に着手する前に以下を確認する。1 つでも未充足なら設計を中断し、ユーザーに確認する。

| 項目 | 確認事項 | 未充足時の対応 |
|---|---|---|
| 仕様確定 | 処理・エンティティ・入出力・制約・例外が明示されているか | spec-items-clarifier スキルで仕様を先に確定する |
| アクター情報 | システムに変更要求を出す主体（人・部門・外部システム）が識別可能か | ユーザーに質問する（最大 3 項目） |
| 入出力境界 | システムが受ける入力・返す出力が定義されているか | 仕様の Input／Output 項目を確認する |
| 制約条件 | 性能・セキュリティ・運用・既存資産との接続制約が明示されているか | 制約不明として記録し、後続ステップで仮置きする |

### step S-1: アクター特定 (SRP)

- **ユーザーからの問い**：このモジュールに対して **独立して変更を要求する主体** は誰か？
- **根拠**：Martin (2017)「モジュールは唯一のアクターに対してのみ責務を負う」。アクター混在は変更時の予期しない副作用の主因となる。
- **手順**：
    1. 仕様書・ステークホルダー一覧から変更要求の起点を抽出する
    2. 「同じデータを使うが、変更要求が独立している主体」を分離する
    3. アクター × 関心事 のマトリクスを作成する
- **出力**：

    ```
    | アクター | 関心事 | 想定される変更要求例 |
    |---------|--------|---------------------|
    | [名称] | [何の決定権を持つか] | [この主体が次に出しそうな仕様変更] |
    ```

### step S-2: ユースケース抽出 (UC 層)

- **ユーザーからの問い**：各アクターはシステムに何をさせるか？ その入出力は何か？
- **根拠**：Martin (2017) ユースケース層は "Application Business Rules" を担い、エンティティ層 ("Enterprise Business Rules") を編成する。これは Clean Architecture の公式レイヤー名である。
- **手順**：
    1. アクター × 目的 = ユースケース候補を列挙する
    2. 各ユースケースに対し Input Model と Output Model を定義する
    3. Input／Output Model はプレーンなデータ構造とする（フレームワーク型・DB 型を含めない）
- **出力**：

    ```
    ## UC-XXX: [ユースケース名]
    - アクター: [アクター名]
    - 目的: [このユースケースが達成する目標]
    - Input Model: { field1: [型], field2: [型] }
    - Output Model: { field1: [型], field2: [型] }
    - 関連エンティティ: [S-3 で抽出するエンティティ名]
    - 例外ケース: [入力不正・制約違反・外部依存失敗]
    ```

### step S-3: エンティティ抽出 (Entity 層)

- **ユーザーからの問い**：複数ユースケースに横断する不変ルールは何か？
- **根拠**：Martin (2017) エンティティ層 "Enterprise Business Rules" は「アプリケーションが存在しなくても成り立つ不変ルール」を担い、最も内側に配置される。
- **手順**：
    1. 仕様書（特に Entities 項目と Processing 項目）から「アプリケーションを跨いで成立する不変ルール」を抽出する
    2. 単一ユースケースでしか使わないルールはユースケース層に置き、エンティティに昇格させない（YAGNI）
    3. エンティティが持つ振る舞い（メソッド）を定義する。データ構造のみのクラスは Value Object とする
- **出力**：

    ```
    ## E-XXX: [エンティティ名]
    - 担う不変ルール: [何を保証するか]
    - 不変条件 (invariant): [常に成立すべき条件]
    - 公開振る舞い: method1(args) -> ReturnType
    - 利用するユースケース: [UC-XXX, UC-YYY]
    ```

### step S-4: 境界（ポート）特定 (DIP)

- **ユーザーからの問い**：内側（ユースケース）が外側（UI／DB／外部 API）に依存しないために、どこにインターフェースを置くか？
- **根拠**：Martin (2017) Use Case Interactor は Input Boundary を実装し、Output Boundary に依存する。Output Boundary の実装は外側にある。これにより依存方向が「外側 → 内側」に統一される。
- **境界の種類**：

    | 境界 | 配置 | 実装側 | 呼び出し側 |
    |------|------|--------|-----------|
    | Input Boundary | ユースケース層 | UseCase Interactor（内側） | Controller（外側） |
    | Output Boundary（Presenter） | ユースケース層 | Presenter（外側） | UseCase Interactor（内側） |
    | Output Boundary（Repository / Gateway） | ユースケース層 | Repository 実装 / Gateway 実装（外側） | UseCase Interactor（内側） |

- **手順**：
    1. 各ユースケースに対し Input Boundary を定義する
    2. ユースケースが必要とする外部依存（永続化・外部 API・通知・時刻取得・乱数）を列挙する
    3. それぞれを Output Boundary（インターフェース）として定義する
- **出力**：

    ```
    ## Input Boundary: [UseCaseName]InputBoundary
    - execute(request: [InputModel]) -> [OutputModel]

    ## Output Boundary: [UseCaseName]OutputPort
    - present(response: [OutputModel]) -> void  # Presenter 用
    - find(id: ID) -> Entity | null              # Repository 用
    - send(message: Message) -> void             # Gateway 用
    ```

### step S-5: アダプター設計

- **ユーザーからの問い**：外部世界とユースケースの間で、データ形式の変換と制御の橋渡しをどう行うか？
- **手順**：
    1. Controller：UI／API リクエストを Input Model に変換し、Input Boundary を呼び出す
    2. Presenter：Output Model を ViewModel／レスポンス DTO に変換し、Output Boundary（Presenter 用）を実装する
    3. Repository / Gateway 実装：Output Boundary を実装し、ORM・DB ドライバ・HTTP クライアント等の外側技術にアクセスする
    4. アダプターは内側のドメイン例外を外側の応答形式（HTTP ステータス・エラーコード）に翻訳する。逆向きのフレームワーク例外漏出を禁止する
- **出力**：

    ```
    ## Adapter: [UseCaseName]Controller
    - 入力: [HTTP Request / CLI Args / GUI Event]
    - 変換: [Input Model 構築手順]
    - 委譲先: [InputBoundary 名]

    ## Adapter: [UseCaseName]Presenter
    - 実装する Output Boundary: [Boundary 名]
    - 出力先: [ViewModel / HTTP Response / 通知]
    - 変換: [Output Model → 出力形式の手順]

    ## Adapter: [EntityName]Repository
    - 実装する Output Boundary: [Repository Boundary 名]
    - 永続化先: [DB / ファイル / キャッシュ]
    - 例外翻訳: [外側例外 → 内側ドメイン例外 のマッピング]
    ```

### step S-6: フレームワーク配置

- **ユーザーからの問い**：どの技術選択を最外層に隔離するか？
- **根拠**：Martin (2017) フレームワーク・ドライバー層は最も変更されやすい。内側はこの層を「知らない」。これは原理原則「偶有的性質は外側に設計する」の実装である。
- **手順**：
    1. Web フレームワーク（Express／Spring／FastAPI 等）の選択を記録する
    2. ORM／DB ドライバ／メッセージング／外部 API クライアントを記録する
    3. これらは S-5 のアダプター実装の中だけで使用される。内側層への侵入を禁止する
- **出力**：

    ```
    ## Framework & Drivers
    - Web: [選択技術と理由]
    - DB: [選択技術と理由]
    - 外部 API クライアント: [選択技術と理由]
    - 隔離方針: [どのアダプターでのみ使われるか]
    ```

### step S-7: 依存方向検証

- **ユーザーからの問い**：すべての import／依存関係が「外側 → 内側」に向かっているか？
- **根拠**：Martin (2017) Dependency Rule。「ソースコード依存は内側を指さなければならない」。
- **手順**：
    1. 各モジュールの import を列挙する
    2. 「内側のモジュール（domain／usecase）が外側のモジュール（adapter／framework）を import している」箇所を検出する
    3. 検出された場合は DIP（Output Boundary 追加 + 依存逆転）で解消する
    4. Composition Root（main）のみ全層を import してよい
- **出力**：

    ```
    ## 依存方向検証結果
    - 内側 → 外側 への違反: [なし / 以下に列挙]
        - [モジュール A] → [モジュール B] : 解消方法 [Output Boundary 追加]
    - Composition Root: [main モジュール名と組み立て対象一覧]
    ```

### step S-8: パッケージ構造

> **注記**：以下のディレクトリ構造は Martin の原典に直接の図解として掲載されたものではなく、実務派生の慣行に基づく仮説である。プロジェクト規約・言語慣行と整合する形で調整してよい。

- **ユーザーからの問い**：S-1〜S-7 の決定を物理配置にどうマッピングするか？
- **手順**：以下のベース構造をプロジェクト規約・言語慣行に合わせて調整する。
- **ベース構造**：

    ```
    src/
      domain/         # エンティティ（最内側、依存ゼロ）
      usecase/        # ユースケース、Input/Output Boundary（domain のみ参照）
      adapter/        # Controller, Presenter, Repository 実装（usecase 参照）
      framework/      # Web, DB, 外部 API（adapter 参照）
      main/           # Composition Root（全層を import し DI 組み立て）
    ```

- **依存方向**：

    ```mermaid
    graph LR
      main --> framework
      main --> adapter
      main --> usecase
      main --> domain
      framework --> adapter
      adapter --> usecase
      usecase --> domain
    ```

- **出力**：

    ```
    ## ディレクトリ構造（提案）
    [上記構造をプロジェクト規約に合わせて調整したもの]

    ## 各パッケージの import ルール
    - domain: 自パッケージ内のみ
    - usecase: domain のみ
    - adapter: usecase, domain
    - framework: adapter, usecase, domain（設定／実装組み立てのため）
    - main: 全層
    ```

### step S-9: YAGNI 検証

- **ユーザーからの問い**：導入した境界・抽象化のうち、変更要因が実在しないものはあるか？
- **根拠**：Martin (2017)「Software architecture is the art of drawing lines that I call boundaries.」境界には「変更を許容するべき箇所」のみに引くべきであり、それ以外は YAGNI 違反となる。
- **手順**：各境界・抽象化について以下を判定する。

    | 抽象化 | 変更要因の実在 | 複数実装の現実性 | 採否 |
    |--------|---------------|-----------------|------|
    | [Output Boundary 名] | [実在 / 仮想] | [複数実装あり / 単一のみ] | [維持 / 削除] |

- **判定基準**：
    - 変更要因が **仕様書・既知のロードマップ・現実の運用要求** に存在する → 維持
    - 「将来必要かもしれない」のみが根拠 → 削除候補
    - 単一実装しかなく、テスト用モック以外に差し替え予定がない → 削除候補（テスト用モックは除外）
- **出力**：

    ```
    ## YAGNI 検証結果
    - 維持された境界: [列挙、根拠とともに]
    - 削除推奨された境界: [列挙、削除根拠]
    ```

### ステップ完了判定（思考代替リスク防御 D6：完了判定ゲート）

各 step（S-1〜S-9）の「手順」完了後、次の step に進む前に以下を検証する：

- [ ] 「ユーザーからの問い」への回答が「出力」に明示的に含まれているか
- [ ] 「根拠」が成立する条件下で「出力」が成立しているか（Martin 原典・プロジェクト規約・仮説のいずれかに紐付くか）
- [ ] 着手前ゲートの 4 項目（仕様確定 / アクター情報 / 入出力境界 / 制約条件）と矛盾する結果が生じていないか
- [ ] 「出力」が次 step の入力として整合するか（例：S-1 アクター → S-2 ユースケース抽出の入力）

**充足しない場合の対応**：

1. 手順を機械的に再実行しない。問い・根拠に立ち返り、別経路を検討する
2. 別経路でも充足しない場合、最大 3 回まで再試行する
3. 3 回失敗時は §6「異常時の出力」フォーマットで `[CLEAN-ARCH-DESIGN-HALT]` を発行する

**注意**：手順完了 ≠ ステップ完了。本ゲートを通過して初めてステップ完了とみなす。

## §6. 結果出力

### 通常時の出力

S-9 完了後、以下の手順で成果物を出力する。

1. `${CLAUDE_SKILL_DIR}/output.md` を読み込む
2. output.md に記載されたテンプレート構造に従って、S-1〜S-9 の出力を集約する
3. テンプレートの各章を、対応する S-X の出力で埋める

**注意**：output.md の読み込みを省略して出力を生成することは禁止する。テンプレート構造の整合性を保証するため、必ず読み込みを行うこと。

### 異常時の出力

入力検証で未充足項目があった、または設計途中で前提が成立しないと判明した場合、設計成果物を出力せず以下のフォーマットで中断を報告する。

```
[CLEAN-ARCH-DESIGN-HALT]
```
