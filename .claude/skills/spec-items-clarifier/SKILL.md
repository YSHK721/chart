# 目的

仕様 9 項目を一意に確定する。

## §1. 定義

**仕様の一意性とは、別の実装者が読んでも同じ実装が組み上がる水準で、曖昧性が排除された状態である。** 本スキルは曖昧な機能説明を入力として、9 項目（Objective / Scope / Assumptions / Constraints / Input / Processing / Entities / Output / Exception）それぞれについて、設計トレードオフを代表する 3 つのオプション（A / B / C）を提示しユーザー選択を確定することで、決定論的な仕様書を生成する一連の認知手順である。

## §2. 原理原則

- 各オプションは「実装が一意に決まる」水準であること（オプション内に曖昧語を含めない）
- 3 つのオプションは「判断軸」の上で互いに異なること（表現違いの類似品を提示しない）
- 1 ターンに提示する項目数は最大 2 項目（同時並行で全項目を提示しない）
- 文脈不足時のみ事前確認質問を 1 問だけ行う（オープンエンドの自由回答は禁止する）
- 推測補完を排除し、すべての設計判断はユーザー選択を経由する

## §3. 用語定義

| 用語 | 定義 |
|---|---|
| Item | 仕様 9 項目（Item1〜Item9）のうちの 1 項目 |
| 判断軸 | 各 Item における 3 オプションを差別化する設計トレードオフの軸 |
| アーキタイプ | 各 Item で典型的に成立する 3 つの設計選択肢の類型（A / B / C） |
| 完了基準 | 各 Item が「実装一意決定可能」と見做される最低条件チェックリスト |
| 確定済み | 該当 Item の完了基準を全て充足し、ユーザー選択（A / B / C）が完了した状態 |
| 事前確認質問 | 文脈不足時にオプション生成前に行う 1 問だけの確認質問 |
| TBD | ユーザーが「未定」と回答した場合の暫定マーキング（決定者・期限を併記する） |

## §4. 強制ルール

| ルール | 内容 |
|---|---|
| 改変禁止 | 指示以外の改変は絶対に禁止する |
| 主観禁止 | 主観・感想・印象の出力は絶対に禁止する |
| オプション内の曖昧語禁止 | 提示するオプションに「適切に」「高速に」「なるべく」を含めない。数値・条件式に置換する |
| 推測補完の禁止 | 選択されていない項目の値を推測で補完しない。確定はユーザー選択を経由する |
| 3 択の差別化の徹底 | 3 つのオプションが同じ判断軸上で明確に異なることを確認してから提示する |
| TBD の明示 | ユーザーが「未定」「わからない」と回答した場合は TBD として記録し決定者・期限を求める |
| 選択サマリーの必須出力 | 最終仕様書に「選択サマリー」セクションを必ず含める（設計判断の根拠を残すため） |
| 1 ターン 2 項目上限 | 1 回の応答でオプションを提示できる項目は最大 2 項目まで |
| 出力テンプレート参照 | 成果物出力時は必ず `${CLAUDE_SKILL_DIR}/output.md` を読み込み、その構造に従う。読み込みを省略した出力生成を禁止する |
| Item 詳細参照 | 各 Item のオプション生成時は必ず `${CLAUDE_SKILL_DIR}/references/items.md` の該当章を読み込む |
| 思考代替防止 | 各 step の「手順」は必ず「判定基準」と併記する。手順単独記述を禁止する（思考代替リスク防御 D1：原理ラッピング） |
| 判定基準優先 | 各 step で「手順」と「判定基準」が衝突した場合は判定基準を優先する。手順への機械的従属を禁止する（思考代替リスク防御 D10：メタルール） |

## §5. 実行プロセス

実行は以下の順序で行う：

**入力分析 → 未確定項目選定 → オプション提示 → 選択確定 → 仕様書出力**

各 step の「手順」は「判定基準」と必ず併記し、判定基準が手順を原理的に拘束する（思考代替リスク防御 D1：原理ラッピング）。手順単独の記述は §4「思考代替防止」ルールで禁止される。手順は判定基準を達成する手段であり、両者衝突時は判定基準が優先される（§4「判定基準優先」ルール）。

### step S-1: 入力分析と項目状態判定

- **判定基準**：各 Item の完了基準（`references/items.md` 各章の「完了基準」セクション）を全充足するか否かで「確定済み / 未確定」を判定する。1 項目でも未充足なら当該 Item は「未確定」とする。
- **アンチパターン**：完了基準を読まずに記述量だけで確定済みと誤判定する／曖昧語が残っているのに確定済みと判定する。
- **手順**：
    1. ユーザー入力（機能説明・既存仕様）を読み取る
    2. `${CLAUDE_SKILL_DIR}/references/items.md` を読み込む
    3. 9 項目それぞれについて、対応する完了基準を逐一突合する
    4. 各 Item の状態（確定済み / 未確定）を内部に保持する

### step S-2: 未確定項目の選定

- **判定基準**：未確定項目を以下の優先順位で並べ、上位最大 2 項目を「今ターンの提示対象」として選定する。優先順位：**Item5 > Item6 > Item9 > Item2 > Item4 > Item1 > Item7 > Item8 > Item3**。
- **アンチパターン**：3 項目以上を一度に提示する／優先順位を無視して提示順を恣意的に変える／全項目確定済みなのに S-3 へ進む。
- **手順**：
    1. S-1 で「未確定」とされた項目を抽出する
    2. 上記優先順位に従いソートする
    3. 上位 2 項目を提示対象として確定する
    4. 全項目が確定済みの場合は S-5 へ直行する

### step S-3: オプション生成とユーザー提示

- **判定基準**：オプション生成は (a) 各 Item の判断軸が明示されている (b) A/B/C が判断軸上で互いに異なる (c) 曖昧語を含まない、の 3 条件を全充足する。文脈が不足し条件 (b) を充足できない場合のみ事前確認質問を 1 問行う。
- **アンチパターン**：表現違いの類似 3 択を提示する／オプション内に「適切に」「高速に」を残す／文脈十分な状況で確認質問を挟む／事前確認質問を 2 問以上行う。
- **手順**：
    1. 対象 Item について `references/items.md` の判断軸・完了基準・アーキタイプ表・出力形式を参照する
    2. 文脈の十分性を評価する：(i) アーキタイプ表の 3 オプションが本文脈に適合するか (ii) ユーザー入力からオプションを区別できる情報が得られるか
    3. 不十分な場合：事前確認質問を 1 問のみ行い、回答を待つ（このターンを中断する）
    4. 十分な場合：A/B/C 各オプションを「名称・仕様テキスト・メリット・デメリット」の形式で生成する
    5. ターン冒頭に「確定済み（X/9）: [項目名 ...]」を表示し、続けて対象 Item のオプションを提示する

### step S-4: ユーザー選択の確定

- **判定基準**：ユーザーが A / B / C のいずれかを選択した時点で確定する。「両方」「カスタム」等の非標準回答が来た場合は、新しい第 4 オプションとして仕様テキストを再生成し再提示する。「未定」回答時は TBD として記録し決定者・期限を求める。
- **アンチパターン**：ユーザー選択前に確定扱いする／選択を受けて他項目の値を勝手に補完する／TBD 回答時に決定者・期限を求めずに次へ進む。
- **手順**：
    1. ユーザー応答（A / B / C / カスタム / 未定）を受け取る
    2. 確定値を内部状態に書き込む（対応する仕様テキストを完全な形で保存する）
    3. 状態が「全 9 項目確定済み」になったか判定する
    4. 未確定が残る場合は S-2 へ戻る／全確定の場合は S-5 へ進む

### step S-5: 仕様書出力

- **判定基準**：全 9 項目が確定済みであること、TBD が存在する場合は決定者・期限が併記されていること、`output.md` のテンプレート構造に従って出力されていること。
- **アンチパターン**：output.md を読まずに出力フォーマットを再現で書く／「選択サマリー（設計判断の記録）」を省略する／TBD 表を空にしたまま出力する。
- **手順**：
    1. `${CLAUDE_SKILL_DIR}/output.md` を読み込む
    2. テンプレート構造に従って各 Item の確定値を埋める（`references/items.md` の Item ごと出力形式に準拠する）
    3. 「選択サマリー（設計判断の記録）」表に Item ごとの選択（A/B/C）と判断要約を記録する
    4. TBD が存在する場合は「未確定事項（TBD）」表に決定者・期限を記録する。存在しない場合も「該当なし」と明示する

### ステップ完了判定（思考代替リスク防御 D6：完了判定ゲート）

各 step（S-1〜S-5）の「手順」完了後、次の step に進む前に以下を検証する。

- [ ] 「判定基準」を満たす出力が得られているか（手順を踏襲しただけで終わっていないか）
- [ ] 入力前提と矛盾する結果が出ていないか（例：ユーザーが選んでいないのに確定済みになっていないか）
- [ ] 「出力」が次 step の入力として整合するか（例：S-3 のオプション提示が S-4 の選択受付の入力として成立するか）

**充足しない場合の対応**：

1. 手順を機械的に再実行しない。判定基準に立ち返り、別経路を検討する
2. 別経路でも充足しない場合、最大 3 回まで再試行する
3. 3 回失敗時は §6「異常時の出力」フォーマットで `[SPEC-CLARIFY-HALT]` を発行する

**注意**：手順完了 ≠ ステップ完了。本ゲートを通過して初めてステップ完了とみなす。

## §6. 結果出力

### 通常時の出力

S-5 完了後、以下の手順で成果物を出力する。

1. `${CLAUDE_SKILL_DIR}/output.md` を読み込む
2. output.md に記載されたテンプレート構造に従って、9 項目の確定値を集約する
3. 「選択サマリー」と「未確定事項（TBD）」を必須セクションとして含める

**注意**：output.md の読み込みを省略して出力を生成することは禁止する。テンプレート構造の整合性を保証するため、必ず読み込みを行うこと。

### 異常時の出力

S-3 で 3 回連続して判定基準を充足できない、または前提が成立しないと判明した場合、仕様書を出力せず以下のフォーマットで中断を報告する。

```
[SPEC-CLARIFY-HALT]
段階: <S-1〜S-5>
原因: <文脈不足 / 前提衝突 / ユーザー応答不能 / その他>
詳細: <具体的な不足情報>
推奨アクション: <ユーザーが取るべき次のステップ（例：要求元との合意取得、上位仕様の確認）>
```

### 完了基準（Definition of Done）

- [ ] §5 S-1〜S-5 をすべて実行した
- [ ] 9 項目すべてが「確定済み」または「TBD（決定者・期限併記）」になっている
- [ ] `output.md` のテンプレート構造に従って成果物を出力した
- [ ] 「選択サマリー」セクションに 9 項目分の選択（A/B/C）と判断要約が記録されている
- [ ] 「未確定事項（TBD）」セクションが存在し、TBD が無い場合も「該当なし」と明示されている
