# 目的

SOLID で構造設計する。

## §0. 仮説と事実の区別

| 区分 | 取り扱い | 表記 |
|---|---|---|
| SOLID 原典で定義された原則（SRP / OCP / LSP / ISP / DIP の定義） | そのまま採用する | 出典なしで断定する |
| プロジェクト規約（命名・パッケージ階層・DI 手法） | プロジェクト内で適用する | 「プロジェクト規約より」と明示する |
| 観察可能事実（仕様・要件・既存契約から直接読み取れる情報） | 設計判断の根拠として採用する | そのまま記述する |
| 仮説（観察外の推測） | 採用は任意。動機を併記する | 「仮説：」プレフィックスを付す |
| 不明 | TBD として未解決事項に記録する | 「TBD: 確認要」と明示する |

## §1. 定義

本スキルは、入力として与えられた仕様・要件のみを対象に、SOLID 5 原則（SRP / OCP / LSP / ISP / DIP）に基づきクラス・インターフェース粒度の設計判断（責務分割／変更軸特定／契約定義／インターフェース分離／依存方向確定）を構造化し、各判断の動機・採用理由・代替案を記録する一連の認知手順である。コード実装前の構造設計フェーズを対象とする。レイヤー間構造設計（clean-architecture）および設計書文書化（system-design）とは責務を分離する。

## §2. 原理原則

- SRP（単一責任）：アクターの責務を明確化し分離する。
- OCP（開放閉鎖）：変更軸を特定し、変動点を抽象化する。
- LSP（リスコフ置換）：契約（事前条件・事後条件・不変条件）を明示し、置換可能な階層を設計する。
- ISP（インターフェース分離）：クライアントごとに必要最小のインターフェースを設計する。
- DIP（依存性逆転）：依存方向を抽象に向けて設計する。
- 観察可能性：設計判断は仕様・要件・既存契約から直接導かれる事実のみに基づく。
- 根拠明示：各設計判断に動機（変更想定／契約／クライアント要件）を併記する。
- 代替案併記：採用案と棄却した代替案を併記し、選定理由を残す。
- YAGNI 遵守：将来想定だけで抽象化を導入しない（現存する変更要求が存在する場合に限り抽象化する）。

## §3. 用語定義

| 用語 | 定義 |
|---|---|
| アクター | システムに変更要求を出す主体（人・部門・上位システム）。SRP の責務分割単位 |
| 責務 | あるアクターのために果たす機能の集合 |
| 変更軸 | 拡張が予見される変動次元（例：通貨種別・支払方式・通知チャネル） |
| 抽象化点 | OCP のために挿入する抽象（インターフェース／抽象クラス）の位置 |
| 契約 | メソッドが満たすべき事前条件・事後条件・不変条件の集合 |
| クライアント | あるインターフェースを利用する側のクラス・モジュール |
| 設計判断 | クラス／インターフェース／依存方向の決定事項 |
| 代替案 | 検討の上で棄却された設計選択肢 |
| 観察可能事実 | 入力された仕様・要件・既存契約から直接読み取れる情報 |
| 仮説 | 観察外の推測。出力時に「仮説：」プレフィックスを付して区別する |
| YAGNI | You Aren't Gonna Need It。現存しない要求のための抽象化を避ける原則 |

## §4. 強制ルール

| ルール | 内容 |
|---|---|
| 改変禁止 | 指示以外の改変は絶対に禁止する |
| 主観禁止 | 主観・感想・印象の出力は絶対に禁止する |
| 推測禁止 | 観察外の事項は「仮説：」プレフィックスなしで記述してはならない |
| 根拠必須 | すべての設計判断に動機（変更想定／契約／クライアント要件）を併記する |
| 代替案必須 | すべての設計判断に検討した代替案と棄却理由を併記する |
| 曖昧表現禁止 | 「適切に」「効率的に」「一般的に」「可能な限り」等の曖昧語を使用しない |
| 出力順序固定 | §6 が指す出力テンプレートの項目順序を変更しない |
| YAGNI 遵守 | 現存する変更要求がない抽象化を導入してはならない |
| 範囲限定 | 設計対象は入力として明示された仕様・要件のみとする |
| スコープ分離 | レイヤー設計は clean-architecture スキル、文書化は system-design スキルに委譲する |

## §5. 実行プロセス

> 各ステップに付随する **判定基準 / 出力先 / アンチパターン** は template.md 末尾「ステップ詳細化要素」に定義される選択適用要素（プロジェクト規約 B.6）。本スキルは 3 要素を以下の方針で適用する：
> - **判定基準（T1）**：全ステップに適用（各ステップに判断要素が存在するため）
> - **出力先（T2）**：全ステップに適用（外部 output.md テンプレートが存在するため）
> - **アンチパターン（T2）**：S-2〜S-6 の SOLID 原則適用ステップのみ適用。S-1（仕様確定）は spec-items-clarifier 委譲で代替されるため、S-7（パッケージ整理）/ S-8（記録）はマッピング・記録タスクで既知失敗パターンが蓄積されていないため、それぞれ省略する

### step S-1: 仕様・前提の確定
- **判定基準**：仕様の Objective / Scope / Assumptions / Constraints / Input / Processing / Entities / Output / Exception の 9 項目が揃っているか確認。未充足なら spec-items-clarifier スキルへ委譲する
- **出力先**：output.md §1（仕様・前提の確定）

### step S-2: SRP アクター責務分割
- **判定基準**：独立して変更要求を出す主体ごとにアクターを分離する（変更タイミング・変更動機の独立性で判断）
- **出力先**：output.md §2（アクター × 責務マトリクス, A-N）→ §3（クラス責務割当, C-N）
- **アンチパターン**：機能区分（CRUD 別・画面別）でアクターを分割しない。"Manager" "Service" 等の無責任名称を避ける

### step S-3: OCP 変更軸と抽象化
- **判定基準**：現存する変更要求が出典（仕様 / Issue / 既存実装）付きで存在する変動軸のみ抽象化する（YAGNI 遵守）
- **出力先**：output.md §4（変更軸と抽象化点, AB-N）
- **アンチパターン**：「将来必要になりそう」のみを根拠とした抽象化を導入しない。具象への直接依存より複雑な構造を採用する場合は必ず現存要求を引用する

### step S-4: LSP 階層と契約定義
- **判定基準**：派生型は基底型の事前条件を強化せず、事後条件を弱化せず、例外型を同等以下に保つ（共変・反変則）
- **出力先**：output.md §5.1（基底型契約）+ §5.2（派生型と置換性）
- **アンチパターン**：テンプレートメソッド過剰使用を避ける。継承で実現困難ならコンポジションへの切替を検討する

### step S-5: ISP クライアント別分割
- **判定基準**：クライアントを先に列挙し、各クライアントが必要とする最小メソッドのみを切り出す（クライアントが不要メソッドの実装を強要されない）
- **出力先**：output.md §6（クライアント別インターフェース, I-N）
- **アンチパターン**：「便利だから」のメソッド集積でファットインターフェースを作らない。逆に 1 メソッド 1 インターフェースの過剰分割もしない（クライアント実需に合わせる）

### step S-6: DIP 依存方向の確定
- **判定基準**：上位モジュールは AB-N / I-N の抽象に依存させ、§7.1 依存方向図に循環参照（cyclic dependency）が存在しないことを確認する
- **出力先**：output.md §7.1（Mermaid 依存方向図）+ §7.2（依存規則・注入方式）
- **アンチパターン**：抽象を「下位モジュール」と同じパッケージに配置しない（DIP の意義喪失）。上位から具象クラスへの直接 new / import を行わない

### step S-7: 設計図とパッケージ整理
- **判定基準**：S-2〜S-6 で発行した全 ID（A-N / C-N / AB-N / I-N）を物理配置（パッケージ・ディレクトリ）にマッピングする
- **出力先**：output.md §8（パッケージ・ディレクトリ構造）

### step S-8: 判断根拠と代替案記録
- **判定基準**：§3〜§7 で発行した全判断 ID（C-N / AB-N / I-N）を §9 に集約し、採用理由・代替案・棄却理由の 3 列を空欄なく記入する
- **出力先**：output.md §9（設計判断インデックス）+ §10（未解決事項）

## §6. 結果出力

### 通常時の出力

1. `${CLAUDE_SKILL_DIR}/output.md` に記載されたテンプレート構造に従って出力する。
2. テンプレートの読み込みを省略した出力生成を禁止する。

### 異常時の出力

入力検証で未充足項目があった、または設計途中で前提が成立しないと判明した場合、設計成果物を出力せず以下のフォーマットで中断を報告する。

```
[CODING-DESIGN-HALT]
段階: <S-X / 入力検証>
原因: <仕様未確定 / アクター不明 / 契約矛盾 / 循環依存 / その他>
詳細: <具体的な不足情報・矛盾箇所>
推奨アクション: <ユーザーが取るべき次のステップ（例：spec-items-clarifier 適用 / clean-architecture スキルへの委譲）>
```

### 完了基準（Definition of Done）

- [ ] §5 ステップ S-1〜S-8 をすべて実行した
- [ ] output.md §1〜§10 の全項目を空欄なく埋めた（該当なしは「該当なし」と明記）
- [ ] S-2〜S-6 で発行した全 ID（A-N / C-N / AB-N / I-N）が §9 設計判断インデックスに集約されている
- [ ] 各設計判断に動機・採用理由・代替案の 3 列が空欄なく記入されている
- [ ] §7.1 依存方向図に循環参照が 0 件、または DIP で解消済み
- [ ] 観察外の主張に「仮説：」プレフィックスが付与されている
