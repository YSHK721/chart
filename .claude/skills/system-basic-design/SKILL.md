# 目的

要件から基本設計書を生成する。

## §0. 仮説と事実の区別

| 区分 | 取り扱い | 表記 |
|---|---|---|
| 公式設計原則（SOLID / Clean Code / DRY / YAGNI / 関心の分離 等の原典定義） | そのまま採用する | 出典名を併記する |
| プロジェクト規約（基本設計書の章構成・必須チェック項目・出力テンプレート） | プロジェクト内で適用する | 「プロジェクト規約より」と明示する |
| 実務派生（アーキテクチャパターン選定根拠・技術スタック選定理由） | 推奨は仮説扱い | 「（実務的推奨／仮説）」と明示する |
| 不明（要件未確定・制約条件未確定） | TBD として未解決事項に記録する | 「TBD: 確認要」と明示する |

## §1. 定義

**基本設計とは、要件文書を入力として、システム全体のアーキテクチャ・機能構成・データ構造・インターフェース・非機能要件への対応を、実装に依存しない粒度で文書化する設計工程である。** 本スキルは要件文書を入力とし、(1) 要件分析と設計方針決定、(2) アーキテクチャ設計、(3) 機能・データ・インターフェース設計、(4) 品質特性担保、(5) 設計検証 の各段階を経て、output.md に規定する 10 章構成の基本設計書を出力する一連の認知手順である。

実装詳細（クラス構成・物理 DB 設計・API 実装仕様・画面コンポーネント設計）は内部設計の対象であり、本スキルは扱わない。

## §2. 原理原則

- **根拠主義**：すべての設計判断には技術的根拠と代替案比較を併記する。単一案のみの提示を禁止する。
- **要件分離**：機能要件・非機能要件・制約条件を明示的に分離して扱う。
- **トレーサビリティ**：要件と設計要素の対応関係を保つ。要件未対応の設計要素・設計未対応の要件を残さない。
- **抽象度維持**：基本設計の粒度を実装依存に踏み込ませない。クラス名・物理テーブル名・実装ライブラリ詳細は内部設計に委譲する。
- **下流引き渡し情報の完全性**：内部設計が必要とする設計情報（責務分担・データモデル・I/F 仕様・制約）を欠落させない。

## §3. 用語定義

| 用語 | 定義 |
|---|---|
| 機能要件 | システムが提供する具体的な振る舞いの要求 |
| 非機能要件 | 性能・可用性・セキュリティ・保守性・拡張性等の品質特性要求 |
| 制約条件 | 技術・予算・期限・運用・法規制等の不変条件 |
| アーキテクチャパターン | レイヤード／クリーン／ヘキサゴナル／マイクロサービス／イベント駆動 等の構造選択肢 |
| レイヤー責務 | 各層が担うべき関心事の境界（プレゼンテーション／アプリケーション／ドメイン／インフラ等） |
| 概念データモデル | 実装に依存しないエンティティと関連の表現 |
| 基本設計書 | output.md の 10 章構成テンプレートに従う成果物 |
| トレーサビリティ | 要件 → 設計要素 → 検証項目 の対応関係 |

## §4. 強制ルール

| ルール | 内容 |
|---|---|
| 改変禁止 | 指示以外の改変は絶対に禁止する |
| 主観禁止 | 主観・感想・印象（「優れた構成」「良い設計」等）の出力は絶対に禁止する |
| 根拠必須 | すべての設計判断に技術的根拠を併記する |
| 代替案比較必須 | アーキテクチャパターン・技術スタックの選定には 2 案以上を提示し採用理由を明記する |
| 抽象度維持 | クラス名・物理テーブル名・SQL DDL・実装コードは出力に含めない（内部設計の対象） |
| 出典明示 | 公式設計原則・プロジェクト規約・実務的推奨・不明 のいずれかを設計判断ごとに併記する |
| 仮説明示 | 実務派生の推奨は「（実務的推奨／仮説）」と注記する |
| 曖昧表現禁止 | 「適切に」「効率的に」「柔軟に」「適宜」「一般的に」「速やかに」を使用しない |
| 数値化必須 | 性能要件・可用性要件・スケーラビリティ要件は数値（応答時間・スループット・SLO 等）で記述する |
| 出力テンプレート参照 | 成果物出力時は必ず `${CLAUDE_SKILL_DIR}/output.md` を読み込み、その章構造に従う。読み込みを省略した出力生成を禁止する |
| 完了基準遵守 | §6 完了基準（DoD）の全項目をチェックしてから報告する |
| 思考代替防止 | 各 step の「手順」は必ず「判定基準」と併記する。手順単独記述を禁止する（思考代替リスク防御 D1：原理ラッピング） |
| 判定基準優先 | 各 step で「手順」と「判定基準」が衝突した場合は判定基準を優先する。手順への機械的従属を禁止する（思考代替リスク防御 D10：メタルール） |

## §5. 実行プロセス

判断は以下の順序で行う：
**入力検証 → 要件分析 → アーキテクチャ設計 → 機能/データ/IF 設計 → 品質特性担保 → 設計検証**

各ステップは「判定基準・出力先・アンチパターン・手順」の 4 要素で構成する。「判定基準」と「出力先」は手順を原理的に拘束する判定基準層であり、手順単独の遂行は §4「思考代替防止」ルールで禁止される。手順は判定基準を達成する手段であり、両者が衝突した場合は判定基準が優先される（§4「判定基準優先」ルール）。

### 着手前ゲート（入力検証）

設計に着手する前に以下を確認する。1 つでも未充足なら作業を中断し、ユーザーに確認する。

| 項目 | 確認事項 | 未充足時の対応 |
|---|---|---|
| 要件文書 | 機能要件・非機能要件・制約条件が文書化されているか | ユーザーに要件文書の所在を質問する |
| スコープ | 設計対象システム／サブシステムの境界が明示されているか | ユーザーに対象範囲を質問する |
| 設計レベル | 「基本設計」であることが確定しているか（内部設計・要件抽出ではないか） | 内部設計要請なら system-design スキル等へ誘導 |
| 制約条件 | 技術スタック制約・運用環境制約・法規制制約が確認可能か | 不明項目は TBD として記録し、推定根拠を併記する |

### step S-1: 要件分析と設計方針決定

- **判定基準**：要件を機能要件／非機能要件／制約条件 の 3 区分に漏れなく分類できているか。設計上の課題と技術的リスクが列挙されているか。
- **出力先**：output.md §2「プロジェクト概要」／ §3.2「アーキテクチャパターン選択理由」／ §9「リスク・課題」
- **アンチパターン**：要件区分の混同（非機能を機能として扱う等）／単一案のみの提示／選定根拠の未記述／リスクの楽観視
- **手順**：
    1. 提供された要件を機能要件・非機能要件・制約条件の 3 区分に分類する
    2. 設計上の課題および技術的リスクを列挙する
    3. アーキテクチャパターンの選択肢を 2 つ以上提示する
    4. 採用案を選択し、選択根拠（技術的・運用的・組織的）と棄却理由を明記する

### step S-2: システムアーキテクチャ設計

- **判定基準**：レイヤー責務・データフロー・技術スタックが S-1 の選定方針と整合し、相互に矛盾しないか。
- **出力先**：output.md §3「システムアーキテクチャ」（3.1 全体構成 ／ 3.3 技術スタック ／ 3.4 レイヤー構成）
- **アンチパターン**：レイヤー責務の越境（ドメイン層が UI に依存する等）／技術スタック選定根拠の不在／依存方向の循環
- **手順**：
    1. レイヤー構造とコンポーネント分割を定義する（責務境界を明示する）
    2. データフロー・プロセスフローを図式化する
    3. 技術スタックを選定し、依存関係と依存方向を明示する
    4. 採用技術と代替技術の比較結果（評価軸：要件適合 / 学習コスト / 運用コスト / コミュニティ）を併記する

### step S-3: 機能・データ・インターフェース設計

- **判定基準**：要件と設計要素のトレーサビリティが取れているか。設計要素間の重複・抜けがないか。
- **出力先**：output.md §4「機能設計」／ §5「データ設計」／ §6「インターフェース設計」
- **アンチパターン**：要件未対応の機能／設計未対応の要件／実装詳細への踏み込み（クラス設計・物理 DDL）／外部連携仕様の欠落
- **手順**：
    1. 機能を業務ユースケース単位／モジュール単位に分割し、機能一覧と優先度を策定する
    2. データモデルを概念レベル（エンティティ・関連・カーディナリティ）で定義する
    3. インターフェース仕様（API 概要 / 画面構成 / 外部システム連携 / 通信プロトコル）を策定する
    4. 各機能に対する要件 ID とのトレーサビリティを記録する

### step S-4: 品質特性の担保

- **判定基準**：すべての非機能要件に対して、設計上の対策と測定方法が定義されているか。
- **出力先**：output.md §7「非機能設計」／ §8「開発・運用方針」
- **アンチパターン**：非機能要件の数値化欠落（「高速」等の曖昧記述）／セキュリティ対策の未対応／品質メトリクス未定義／運用考慮の欠落
- **手順**：
    1. 各非機能要件（性能 / 可用性 / セキュリティ / 保守性 / 拡張性 / 運用性）に対する設計対策を定義する
    2. セキュリティ設計および脅威対策を組み込む（詳細脅威分析が必要なら security スキルを参照する）
    3. 保守性および拡張性を確保する構造（責務分離・拡張点・設定外部化）を設計する
    4. 品質メトリクス（応答時間・可用性％・MTTR 等）と測定方法を数値で定義する

### step S-5: 設計検証（基本設計チェック）

- **判定基準**：基本設計書チェック項目（要求整合 / 技術的実現性 / 非機能対応 / セキュリティ網羅 / 保守性・拡張性）すべてに合格するか。
- **出力先**：output.md §9「リスク・課題」／ §10「付録」（設計判断根拠）
- **アンチパターン**：チェック項目の自己評価省略／要求仕様との突き合わせ未実施／技術的実現性の未検証／TBD 項目の未記録
- **手順**：
    1. 要求仕様との整合性を機能要件 ID 単位で確認する
    2. 採用技術スタックでの技術的実現可能性を検証する
    3. すべての非機能要件に対する設計対策の有無を確認する
    4. セキュリティ要件の網羅性を確認する（OWASP 等の参照は security スキルへ委譲）
    5. 保守性・拡張性を確保する構造が組み込まれているか確認する
    6. 未解決項目・残課題を §9 に記録する

### ステップ完了判定（思考代替リスク防御 D6：完了判定ゲート）

各 step（S-1〜S-5）の手順完了後、次の step に進む前に以下を検証する：

- [ ] 「判定基準」を充足する記述が「出力先」に含まれているか
- [ ] 着手前ゲートの 4 項目（要件文書 / スコープ / 設計レベル / 制約条件）と矛盾する結果が生じていないか
- [ ] 出力が次 step の入力として整合するか（例：S-1 採用パターン → S-2 レイヤー構造の前提となるか）
- [ ] 「アンチパターン」のいずれにも該当していないか
- [ ] 曖昧表現（§4 禁止語）・主観表現が混入していないか
- [ ] 公式設計原則の引用には出典名を、実務派生には「（実務的推奨／仮説）」を併記しているか

**充足しない場合の対応**：

1. 手順を機械的に再実行しない。判定基準に立ち返り、別経路を検討する
2. 別経路でも充足しない場合、最大 3 回まで再試行する
3. 3 回失敗時は §6「異常時の出力」フォーマットで `[BASIC-DESIGN-HALT]` を発行する

**注意**：手順完了 ≠ ステップ完了。本ゲートを通過して初めてステップ完了とみなす。

## §6. 結果出力

### 通常時の出力

S-5 完了後、以下の手順で成果物を出力する。

1. `${CLAUDE_SKILL_DIR}/output.md` を読み込む
2. output.md に記載されたテンプレート構造（10 章）に従って、S-1〜S-5 の出力を集約する
3. テンプレートの各章を、対応する S-X の出力で埋める。該当情報がない章は「該当なし」と明記する

**注意**：output.md の読み込みを省略して出力を生成することは禁止する。テンプレート構造の整合性を保証するため、必ず読み込みを行う。

### 異常時の出力

着手前ゲートで未充足項目があった、または分析途中で前提が成立しないと判明した場合、成果物を出力せず以下のフォーマットで中断を報告する。

```
[BASIC-DESIGN-HALT]
段階: <S-X / 着手前ゲート>
原因: <要件文書未確認 / スコープ不明 / 設計レベル不一致 / 制約条件不明 / 判定基準充足不能 / その他>
詳細: <具体的な不足情報・矛盾内容>
推奨アクション: <ユーザーが取るべき次のステップ（例：要件文書の提示 / スコープの確定 / 内部設計スキルへの切替）>
```

### 完了基準（Definition of Done）

- [ ] §5 着手前ゲートの入力検証 4 項目をすべて確認した
- [ ] §5 のステップ S-1〜S-5 をすべて実行した
- [ ] output.md の 10 章をすべて埋めた（該当なしの場合は「該当なし」と明記）
- [ ] 各設計判断に「公式設計原則 / プロジェクト規約 / 実務的推奨（仮説）/ TBD」のいずれかが併記されている
- [ ] アーキテクチャパターン・技術スタック選定で 2 案以上の比較が記述されている
- [ ] 非機能要件に対応する設計対策が数値メトリクス付きで記述されている
- [ ] 曖昧表現（§4 禁止語）・主観表現が出力に含まれていない
- [ ] クラス名・物理 DDL・実装コード等の内部設計領域が出力に混入していない
- [ ] 要件 ID と設計要素のトレーサビリティが §4 機能設計に記録されている
