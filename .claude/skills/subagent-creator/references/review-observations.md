## 観点 1：frontmatter 必須項目の充足

- `name` `description` の両方が存在し、空でないこと
- `name` が小文字とハイフンのみで構成されていること
- references/official-spec.md §A.1 に列挙されない未定義フィールドが含まれていないこと

## 観点 2：description のトリガー具体性（自動委譲発火条件）

- 動詞ベースのトリガー条件が列挙されているか
- 「いつ使わないか」の除外条件があるか
- 1 文だけ・名詞句のみの説明は不合格（Claude が委譲判断できない）
- プロアクティブ起動意図がある場合に冒頭に `PROACTIVELY` または「use proactively」相当の表現があるか

## 観点 3：ツール権限の最小性

- `tools` が明示されているか、または `disallowedTools` で制限されているか
- 暗黙の全ツール継承で必要以上の権限が付与されていないか
- `Edit` / `Write` / `Bash` を持つ必要が本文の責務から立証できるか

## 観点 4：モデル選択の妥当性

- 読み取り専用探索なのに `opus` が指定されていないか（コスト過剰）
- 複雑な推論が必要なのに `haiku` が指定されていないか（能力不足）
- 公式仕様外の値（例：`claude-3-opus-2024`）が指定されていないか

## 観点 5：権限モードの整合

- `permissionMode` が公式列挙値（`default` / `acceptEdits` / `auto` / `dontAsk` / `bypassPermissions` / `plan`）のいずれかか
- `bypassPermissions` を選択している場合、本文に運用上の警告があるか
- 親が `bypassPermissions` / `acceptEdits` / `auto` のとき子の `permissionMode` は親に上書きされる（references/official-spec.md §A.5）ことを前提に設計しているか

## 観点 6：プラグイン配布制約の遵守

- プラグイン配布予定の場合、`hooks` / `mcpServers` / `permissionMode` を使用していないか（公式：プラグインから読み込むときに無視される）

## 観点 7：メモリスコープと用途の整合

- `memory: project` をバージョン管理に含めるべきでない情報に使っていないか
- `memory: local` を全プロジェクト共通の知識に使っていないか
- メモリディレクトリパス（references/official-spec.md §A.3）を本文記述で前提にしていないか

## 観点 8：システムプロンプト本文の独立性

- 親会話の context（変数・ファイル・状態）への暗黙参照がないか
- 「先ほどの会話で…」「上記の…」等、独立コンテキストで動作する subagent には不適な表現がないか
- 作業ディレクトリ前提（`cd` の永続性）に依存していないか

## 観点 9：曖昧表現の排除

以下の禁止語リストに該当する表現がないか：

```
適切に / 可能な限り / 高速に / なるべく / 効率的に /
合理的な / 柔軟に / 適宜 / 一般的な / 標準的な /
通常の / 速やかに / 早期に / リアルタイム
```

## 観点 10：ネスト不可性の遵守

- 本文中で「別の subagent を呼び出す」「Agent ツールで他エージェントを生成する」等の指示がないか（公式：「サブエージェントは他のサブエージェントを生成できません」）
- v2.1.63 で Task ツールは Agent に名称変更されたが、`Task(...)` も引き続きエイリアスとして機能する旨を踏まえているか

## 観点 11：観測可能性

- 異常時の出力フォーマット（エラーメッセージ・ログ形式）が定義されているか
- 完了基準（Definition of Done）が呼び出し側から検証可能か
- メイン会話に返却する「概要」が何を含むか明示されているか
