# frontmatter 任意フィールド決定要素（推奨／仮説・選択適用）

§A.1 に列挙された 14 フィールド（うち `skills` はプロジェクト規約により必須、残り 13 は任意）それぞれについて、step S-4 で「指定する／省略する」を決定する。
任意フィールドは一律指定不要。省略時は理由（公式デフォルトで十分・該当しない等）を output.md §A 表「4. 任意フィールド決定記録」に残す。`skills` は必須のため省略不可。

| フィールド | 指定すべき条件 | 省略してよい条件 |
|-----------|--------------|----------------|
| `tools` | 最小権限が必要（Edit/Write/Bash 等の強権限ツールを制限したい） | 親の全ツール継承で問題ない場合（観点 3 不合格リスクあり） |
| `disallowedTools` | ブラックリスト方式の方が記述量が少ない（特定ツールのみ禁止） | `tools` で必要分のみ列挙する場合（排他関係） |
| `model` | コスト最適化が必要／タスクが特定モデル能力に依存する | セッションモデル継承で問題ない場合（既定 `inherit`） |
| `permissionMode` | `bypassPermissions` 等の特殊運用を意図する | 既定 `default` で問題ない場合 |
| `maxTurns` | 暴走防止のターン上限が必要 | 制限なしで問題ない場合 |
| `skills` | （プロジェクト規約により必須）`prompt-validation-workflow` を既定スキルとして常に含める。追加の処理スキルが必要な場合は併記する | （省略不可：プロジェクト規約） |
| `mcpServers` | 親継承では不足／プラグイン配布以外で MCP 構成を上書きする | 親継承で十分な場合 |
| `hooks` | Stop / PostToolUse 等のフック動作が必要 | フック不要な場合（プラグイン配布時は無視されるため省略推奨） |
| `memory` | 呼び出しを跨ぐ永続記憶が必要 | 単発実行で完結する場合 |
| `background` | 長時間タスクをバックグラウンド実行する | 同期実行で問題ない場合 |
| `effort` | セッション既定と異なる思考努力レベルを強制したい | セッション継承で問題ない場合 |
| `isolation` | git worktree 分離が必要（破壊的編集の隔離等） | 分離不要な場合 |
| `color` | UI 上の視認性を上げたい | 既定で問題ない場合 |
| `initialPrompt` | 起動直後に追加指示を注入したい | description + 本文で十分な場合 |

決定不能な場合は TBD として未解決事項に記録し、確認すべき情報源（公式仕様 §A.X / プロジェクト規約 §B.X / ユーザー）を併記する。

# description 構造仕様（公式準拠）

description は自動委譲発火条件である。以下の構造を満たさない場合、Claude が委譲判断不能になり observation 2「description のトリガー具体性」で 🔴 CRITICAL 判定となる。

## 必須構造

| 位置 | 内容 | 例 |
|-----|------|----|
| 1 文目 | このサブエージェントの役割（What） | 「Claude Code カスタムサブエージェントの設計・…を行う専用スキル」 |
| 2 行目以降 | 動詞ベースのトリガー条件列挙（When） | 「- 〜したい / されている / 必要な場合」形式の箇条書き |
| 末尾 | 除外条件（When NOT） | 「使用しないケース：…」または「単発の指示・…には使用しない」 |

## 禁止形式

- 名詞句のみで終える（例：「サブエージェント設計支援ツール」）
- トリガー列挙なしの 1 文説明（例：「サブエージェントを作るためのスキル」）
- 除外条件の省略（誤発火の温床となる）

## PROACTIVELY ラベル適用条件（推奨／仮説）

| 適用条件 | 該当例 |
|---------|--------|
| 親会話のあらゆる文脈で自律的に介入してほしい | TDD-executor / Coding-executor 等の品質ゲート系 |
| プロジェクト規約 §B.3 で `PROACTIVELY` 表記が定着している領域 | spec-driven-development.md 配下の `*-executor` 系 |

不適用例：
- 明示的な指示のみで起動させたい subagent（過剰委譲を避けたい場合）
- ユーザーが起動条件を逐次判断する設計（単発・希少タスク）

公式ドキュメントの「use proactively」と機能的に等価だが、プロジェクト内で表記を統一する目的で採用する（推奨／仮説：プロジェクト規約 §B.3）。

# システムプロンプト本文構造（推奨／仮説）

frontmatter 配下の Markdown 本文は、独立 context で動作する subagent のシステムプロンプトとして注入される。以下構造を推奨する（推奨／仮説：観点 8 独立性 + 観点 11 観測可能性の同時充足）。

## 必須セクション（推奨／仮説）

想定セクション番号順序：`# 役割` → `§1 責務` → `§2 入力` → `（§3 プロセス：処理スキル 2 個以上採用時のみ任意挿入）` → `§4 出力` → `§5 完了判定（DoD）`。プロセスセクションを挿入しない場合も §出力 = §4 / §完了判定 = §5 として番号付けを固定する。

| 想定番号 | セクション | 目的 | 観点との対応 |
|---------|-----------|------|------------|
| — | `# 役割` | 親会話状態への参照を排除した独立宣言 | 観点 8 独立性 |
| §1 | `## §1. 責務` | subagent が担う単一責務の宣言 | 観点 8 独立性 |
| §2 | `## §2. 入力` | 親会話から受け取る情報構造の明示（暗黙参照防止） | 観点 8 独立性 / 観点 11 観測可能性 |
| §4 | `## §4. 出力` | 親会話に返却する概要の構造・内容の明示（追従性検証は `prompt-validation-workflow` が担うため本セクションでは扱わない） | 観点 11 観測可能性 |
| §5 | `## §5. 完了判定（DoD）` | 呼び出し側から検証可能な完了基準 | 観点 11 観測可能性 |

## 任意セクション（適用条件に該当する場合のみ）

| セクション | 適用条件 |
|-----------|---------|
| `## §3. プロセス` | frontmatter `skills:` に 2 個以上の処理スキル（`prompt-validation-workflow` を除く）を宣言した場合（後述「プロセスオーケストレーションパターン」を参照） |
| `## §{連番}. ログ記録` | spec-driven-development.md §0.6 ログスキーマ準拠が必要な場合（プロジェクト規約 §B.2） |
| `## §{連番}. 強制ルール` | 観点 9 曖昧表現禁止等の subagent 固有メタルールを明示する場合 |

## 禁止表現（観点 8 / 観点 9 / 観点 10 由来）

| 種別 | 禁止表現例 | 違反観点 |
|-----|----------|---------|
| 親 context への暗黙参照 | 「先ほどの会話で…」「上記の…」「先程指定された…」 | 観点 8 独立性 |
| 曖昧表現 | 「適切に」「可能な限り」「効率的に」「速やかに」「リアルタイム」 | 観点 9 曖昧表現排除 |
| 他 subagent 呼び出し指示 | 「他の subagent を起動する」「Agent ツールで別エージェントを生成する」 | 観点 10 ネスト不可 |
| 作業ディレクトリ前提 | 「`cd` でディレクトリを移動した後…」（呼び出し間で永続化されない） | 観点 8 / §A.5 構造的制約 |

# プロセスオーケストレーションパターン（複数 skill 採用時）

frontmatter `skills:` に 2 個以上の処理スキルを宣言する subagent では、subagent 本文 `## §3. プロセス` に「どのスキルを・どの順で・どの条件で起動するか」をオーケストレーション情報として明示する。記述しない場合、subagent の LLM 判断が非決定的となり、同時複数発火・抜け漏れ・順序破綻が発生する。

`prompt-validation-workflow`（プロジェクト規約による既定スキル）は出力検証用のオーバーレイであり、処理スキル数のカウントから除外する。処理スキル 1 個の subagent ではオーケストレーション情報は不要（subagent 起動 = 唯一の処理プロセスが自明）であり、プロセスセクション自体を省略する。

## 適用判定

| 処理スキル数（`prompt-validation-workflow` を除く） | プロセスセクション | 記述内容 |
|---------|------------------|---------|
| 0 個 | 削除 | validation のみで処理を持たない subagent（極稀）|
| 1 個 | 削除 | subagent 起動 = 唯一の処理プロセスが自明のため記述不要 |
| 2 個以上 | 必須 | 以下 4 パターンのいずれかでオーケストレーションを記述 |

## パターン 1：責務分岐型

入力種別を責務に分類し、責務ごとに対応スキルへルーティングする。

**適用条件**：subagent が複数の独立した責務を持ち、入力ごとに 1 つの責務のみが該当する場合。

**記述例**：

```
## §3. プロセス

入力を以下のルーティング表に従って責務分類し、対応スキルを起動する。

| 入力分類条件 | 起動スキル | 対応する責務 |
|------------|----------|------------|
| {新規作成系トリガーに該当}   | {skill-creator}  | 責務 1 |
| {レビュー系トリガーに該当}   | {skill-reviewer} | 責務 2 |
| {委譲先選定系トリガーに該当} | {skill-router}   | 責務 3 |

複数分類に該当する場合は中断する。
```

## パターン 2：シーケンシャル型（パイプライン）

複数スキルを固定順序で起動し、前段の出力を後段の入力に渡す。

**適用条件**：スキル間にデータ依存があり、起動順序が一意に決まる場合。

**記述例**：

```
## §3. プロセス

以下の順序でスキルを起動し、各段の出力を次段の入力に渡す。

| 段 | スキル | 入力 | 出力 |
|---|-------|-----|-----|
| 1 | {skill-extract}  | 親会話からの自然言語指示 | 構造化要件 |
| 2 | {skill-design}   | 段 1 の構造化要件        | 設計仕様 |
| 3 | {skill-validate} | 段 2 の設計仕様          | 検証結果 |

中断条件：いずれかの段の出力が次段入力スキーマと整合しない場合は中断する。
```

## パターン 3：条件分岐型

入力属性（ファイル拡張子・データ型・パラメーター値等）に応じて起動スキルを選択する。

**適用条件**：入力の属性値に基づく決定的な分岐ロジックが定義可能な場合。

**記述例**：

```
## §3. プロセス

入力属性に従い、以下の分岐表で起動スキルを決定する。

| 分岐属性 | 値の範囲 | 起動スキル |
|--------|---------|----------|
| {入力ファイル拡張子} | `.py`            | {skill-python-analyzer}     |
| {入力ファイル拡張子} | `.ts` / `.tsx`   | {skill-typescript-analyzer} |
| {入力ファイル拡張子} | 上記以外         | 中断 |

複数分岐条件を同時に満たす入力は中断する。
```

## パターン 4：フェーズベース型

subagent が保持する状態（フェーズ）に応じて起動スキルを切り替える。

**適用条件**：処理が複数フェーズで構成され、現在のフェーズが入力または subagent 内部状態から判定可能な場合。

**記述例**：

```
## §3. プロセス

現在のフェーズを判定し、対応スキルを起動する。フェーズは入力中の `phase` フィールドまたは前段成果物の存在状況から決定する。

| フェーズ | 判定基準 | 起動スキル |
|---------|---------|----------|
| Phase 1（要件確定中） | 設計成果物が未生成 | {skill-spec-clarifier} |
| Phase 2（設計中）     | 要件成果物が存在し設計成果物が未生成 | {skill-design} |
| Phase 3（実装中）     | 設計成果物が存在し実装が未完了       | {skill-tdd} |

フェーズ判定不能な入力は中断する。
```

## パターン選択フロー

| 質問 | Yes | No |
|-----|-----|-----|
| Q1：スキル間にデータ依存があり順序が一意か？ | パターン 2 | Q2 へ |
| Q2：入力属性で決定的に分岐できるか？ | パターン 3 | Q3 へ |
| Q3：subagent が保持するフェーズ状態に依存するか？ | パターン 4 | パターン 1 |

複数パターンを混在させる場合（例：パターン 4 で各フェーズ内にパターン 2 のシーケンス）は、外側パターン → 内側パターンの順で記述する。

## 共通遵守事項

- 起動スキルは frontmatter `skills:` で宣言済みのものに限定する（未宣言スキルの起動禁止）
- 分類・分岐の不能ケースは必ず中断条件として扱う
- スキル間のデータ受け渡しスキーマは入力セクション / 出力セクションで間接的に整合させる

# 思考代替リスク防御（推奨／仮説・skill 側で適用）

subagent 本文には順序付き処理手順を記述しない設計（処理は frontmatter `skills:` で宣言したスキルに委譲する）のため、思考代替リスク防御セット（D1 原理ラッピング / D6 完了判定ゲート / D10 メタルール）は subagent 本文ではなく **各スキル側** で適用する。

各スキルの SKILL.md §5 実行プロセスに防御セットを併設する具体手順は skill-designer template.md「手順 T3 採用時の思考代替リスク防御」を参照する。

## subagent 側の責務

- frontmatter `skills:` で宣言したスキルが防御セットを併設しているかを step S-2（委譲先妥当性確認）で検証する
- 防御セット未併設のスキルを参照する場合は、スキル側に防御セット追加を求めるか別スキルへの差し替えを検討する
