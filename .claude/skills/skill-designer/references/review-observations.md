## 観点 1：frontmatter 仕様適合
- 公式定義済みのフィールド（§2.2 の 15 項目）のみを使用しているか
- `name` は小文字・数字・ハイフンのみ、64 文字以内か
- 値の型（string / boolean / enum 等）が公式仕様に合致しているか

## 観点 2：description のトリガー具体性（自動発火条件）
- 動詞ベースのトリガー条件が列挙されているか
- 主要ユースケースが冒頭にあるか（1,536 文字短縮時に削られないため）
- 「いつ使わないか」の除外条件があるか
- 1 文だけ・名詞句のみの説明は不合格（Claude が判断できない）

## 観点 3：description 文字数
- description と when_to_use の合算が 1,536 文字以内か
- 多数のスキルが共存する環境では `SLASH_COMMAND_TOOL_CHAR_BUDGET` でさらに短縮される可能性がある

## 観点 4：呼び出し制御の妥当性
- 副作用がある処理（デプロイ・コミット・送信・公開）に `disable-model-invocation: true` が付いているか
- バックグラウンド知識のみで `user-invocable: false` にすべきか

## 観点 5：ツール権限の最小性
- `allowed-tools` が必要ツールのみか
- `Bash(...)` の引数パターンが必要範囲に絞られているか（例：`Bash(git add *) Bash(git commit *)`）
- 不要な `Edit` / `Write` / `Bash` の事前承認を含んでいないか

## 観点 6：モデル・努力レベルの妥当性
- 軽量タスクに opus が指定されていないか（コスト過剰）
- 重い推論に haiku が指定されていないか（能力不足）
- `effort` の指定値が公式列挙値（`low` / `medium` / `high` / `xhigh` / `max`）か

## 観点 7：進歩的開示の設計
- SKILL.md が 500 行以下を目安として収まっているか（公式は「500 行以下に保ちます」と推奨表現）
- 500 行を超える場合、`references/` への分割または即時参照付録の内蔵根拠が明示されているか
- 大規模リファレンス（>300 行）に目次があるか
- `references/` `scripts/` `assets/` が SKILL.md から「いつ読むか・実行するか」と共に参照されているか

## 観点 8：`context: fork` の使用妥当性
- フォーク使用時、SKILL.md 本体が「実行可能なタスク」を記述しているか（リファレンスのみではないか）
- `agent` フィールドが目的に合っているか（読み取り専用なら `Explore`、計画なら `Plan`）

## 観点 9：スタンディング指示形式
- 「次のターンで…」「最初に…」等の段階的・1 回限り指示が、スキル本体が再読込みされない前提を破っていないか
- タスク全体に常時適用される指示として書かれているか

## 観点 10：動的コンテキスト注入の安全性
- `` !`command` `` の出力が信頼できる前提で本文が書かれているか
- コマンド失敗時のフォールバックが明示されているか
- `disableSkillShellExecution: true` の管理設定下では `[shell command execution disabled by policy]` に置換される旨を考慮しているか

## 観点 11：曖昧表現の排除

以下の禁止語リストに該当する表現がないか：

```
適切に / 可能な限り / 高速に / なるべく / 効率的に /
合理的な / 柔軟に / 適宜 / 一般的な / 標準的な /
通常の / 速やかに / 早期に / リアルタイム
```

## 観点 12：観測可能性
- 異常時の出力フォーマット（エラーメッセージ・ログ形式）が定義されているか
- 完了基準（Definition of Done）が呼び出し側から検証可能か
- 自動コンパクション後に効果が薄れた可能性を検知する手段（再呼び出しの指針）があるか

## 観点 13：ステップ詳細化要素の選択適用妥当性（推奨／仮説）
- §5 実行プロセスの各ステップにおいて、template.md「ステップ詳細化要素」の適用条件に従って 3 要素（判定基準 / 出力先 / アンチパターン）が選択適用されているか
- 該当ステップで省略されていないか（適用漏れ検出）
- 該当しないステップに無理に付与されていないか（過剰適用検出）
- 既存の豊富プロトコル（clean-architecture の「ユーザーからの問い／根拠／手順／出力」等）を持つスキルで重複適用していないか

## 観点 14：§0「仮説と事実の区別」章の選択適用妥当性（推奨／仮説）
- template.md「§0 仮説と事実の区別 章」の適用条件に従って §0 章が設置されているか
    - 適用条件：(1) 外部権威からの引用と実務派生の推奨が混在する / (2) 主張の出所種別が複数ある / (3)「（推奨／仮説）」マーキングが本文に頻出する
- 該当スキルで §0 が省略されていないか（適用漏れ検出）
- 機械的処理中心スキル（mcp-serena-tools / update-config 等）に §0 が無理に設置されていないか（過剰適用検出）
- §0 設置スキルでは、4 区分（公式仕様 / プロジェクト規約 / 推奨（仮説） / 不明）が明示されているか
- §0 で宣言した区分マーカー（「（推奨／仮説）」「プロジェクト規約より」「TBD」等）が本文中で一貫して適用されているか（§0 単独では誤読防御は完成せず、本文中の個別マーキングと両輪で機能する）

## 観点 15：手順 T3 + 思考代替リスク防御セットの選択適用妥当性（推奨／仮説）

### 15.0 T3 該当性判定（前置き）

「順序付き手順がある = T3」ではない。以下のすべてを満たす場合のみ T3 として扱う：

- §5 実行プロセス章または同等の中核フロー章に配置されている
- スキル本体の主目的を達成するための中核フローの構成要素である

以下は T3 対象外と判定する：

- 異常時例外回復手順・フォールバック条件分岐
- 前提条件確認手順・初期化手順
- 出力フォーマットの記述順序

T3 不該当と判定した場合、15.1 以降のチェックは省略する（過剰適用回避）。判定結果と根拠（どの T3 対象外区分に該当するか）はレビュー結果に明記する。

### 15.1 防御セット併設チェック（T3 該当時のみ適用）

- 手順 T3 採用ステップで判定基準が併記されているか（D1 原理ラッピング充足 / 手順単独記述の禁止）
- §4 強制ルールに「思考代替防止」「判定基準優先」相当のルールが含まれているか（D10 メタルール充足）
- §5 末尾にステップ完了判定（D6 完了判定ゲート）が定義されているか
- 判定基準より手順が長くなっていないか（過剰仕様化検出 / F1 機械的踏襲リスク）
- 手順サブステップが 5 件以下に保たれているか（分解過剰防止）
- 出力テンプレート（output.md）に手順自体がコピーされていないか（F4 冗長模倣検出）
- 手順 T3 不採用スキルに防御セットが過剰追加されていないか（過剰適用検出）
- 既存豊富プロトコル保有スキル（clean-architecture 等）の場合、4 要素プロトコル内で T3 + 判定基準層を内包しているか（重複適用回避）
