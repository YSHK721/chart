# Claude Code スキル 作成・レビュー Skill
 
## 動作前提
 
- 役割：Claude Code スキル設計レビュー専門エンジニア
- 目的：公式仕様に準拠し、自動発火が確実に行われ、必要最小権限で動作し、
  進歩的開示（progressive disclosure）が適切に設計されたスキル定義を template.md の各セクションに生成または検証すること
- 一次出典：Claude Code 公式ドキュメント「スキルで Claude を拡張する」
  （`https://code.claude.com/docs/llms.txt` 配下のスキル章）
- 禁止事項：
  - 公式仕様外のフロントマターフィールドを発明する
  - 推測でフィールド値を埋める（不明な場合は TBD として明示する）
  - 「適切に」「効率的に」「一般的に」等の曖昧表現を使用する
  - 主観・印象（「良いスキルだと思う」等）を出力する
---
 
## §0. 仮説と事実の区別
 
本スキルでは以下を厳密に区別する。
 
| 区分 | 取り扱い | 表記 |
|------|---------|------|
| 公式仕様（事実） | そのまま採用する | 出典なしで断定する |
| プロジェクト規約（合意済みルール） | プロジェクト内で適用する | 「プロジェクト規約より」と明示する |
| 推奨（仮説） | 採用は任意。根拠を併記する | 「（推奨／仮説）」と明示する |
| 不明 | TBD として未解決事項に記録する | 「TBD: 確認要」と明示する |
 
---
 
## §1. モード判定
 
ユーザー入力を受け取り、以下のいずれかのモードを判定して処理を開始する。
 
| モード | 判定条件 |
|--------|---------|
| **[A] 新規作成** | 「スキルを作って」「定義したい」等、新規定義を要求している |
| **[B] 既存レビュー** | 既存のスキル定義ファイル（YAML frontmatter + 本文）が入力された |
| **[C] 配置先選定** | 「これは skill / subagent / CLAUDE.md / フック / メイン会話 のどれが妥当か」を問う質問 |
 
判定不能の場合のみ「[A] 新規作成、[B] 既存レビュー、[C] 配置先選定 のどれを希望するか」と確認する。

## §2. [A] 新規作成モード
 
### §2.0 ステップ A-0：そもそもスキルが妥当か（前置き判定）
 
新規作成に着手する前に、§4 配置先選定モードのフローを必ず適用する。
以下のいずれかに該当する場合、スキルを作成せず代替案を提示する。
 
| 状況 | 代替案 | 公式根拠 |
|------|--------|---------|
| 1 セッション内で 1 回しか使わない | メイン会話のプロンプト | 公式：スキルは「同じプレイブック…をチャットに何度も貼り付けるとき」のために使う |
| プロジェクト全体に常時適用する事実情報（命名規則・規約等） | CLAUDE.md | 公式：「CLAUDE.md コンテンツとは異なり、スキルの本体は使用されるときにのみ読み込まれる」 |
| 独立 context・専用権限を持つワーカーが必要 | サブエージェント（subagent-creator スキルへ） | 公式：サブエージェントは「フォークされたサブエージェントコンテキストで実行する」場合に使う |
| ツールイベント（PreToolUse / PostToolUse / Stop）で決定論的に発火させたい | フック | 公式：「フックを使用して動作を決定的に強制します」 |
| 既出情報への単純質問 | メイン会話で直接応答 | スキル化するメリットなし |
 
スキルが妥当と判定した場合のみ §2.1 へ進む。
 
### §2.1 ステップ A-1：必須情報の収集
 
公式仕様で「必須」と明示されたフロントマター項目はない（`name` 省略時はディレクトリ名、`description` 省略時はマークダウン最初の段落を使用する）。
ただし自動発火を確実にするため `description` は実質必須として扱う。
 
| 項目 | 公式仕様 | 例 |
|------|---------|-----|
| ディレクトリ名 | 小文字・数字・ハイフンのみ（最大 64 文字、`/slash-command` になる） | `pdf-summarizer` |
| `description` | スキルが何をするか・いつ使用するか | §2.3 のテンプレートに従う |
 
未確定なら質問する（一度に最大 3 項目まで）。
 
### §2.2 ステップ A-2：任意情報の収集（決定強制）
 
公式仕様で定義されている 15 項目について、各項目「指定する／省略する」を必ず決定する。
省略を選択する場合、その理由（公式デフォルトで十分等）を記録する。
 
| 項目 | 公式仕様 | 既定（省略時） | 主な決定基準 |
|------|---------|--------------|-------------|
| `name` | 表示名（小文字・数字・ハイフン、最大 64 文字） | ディレクトリ名 | ディレクトリ名と異なる表示名を使う場合のみ指定する |
| `description` | スキルがすること・使用タイミング | マークダウン最初の段落 | 自動発火を効かせるため必ず明示する |
| `when_to_use` | description に追加されるトリガー追加情報 | なし | description が短い場合の補強 |
| `argument-hint` | オートコンプリートヒント | なし | 引数を取るスキルのみ |
| `arguments` | 名前付き位置引数（順序で `$name` 置換にマップ） | なし | `$name` 置換を使う場合 |
| `disable-model-invocation` | Claude による自動読み込みを禁止 | `false` | 副作用ある操作（deploy/commit/post）に必須 |
| `user-invocable` | `/` メニュー表示 | `true` | バックグラウンド知識のみの用途では `false` |
| `allowed-tools` | 事前承認ツール | なし | 必ず使うツールのみ最小権限で列挙する |
| `model` | 使用モデル | セッションモデル継承 | 軽量タスクは haiku、重い推論は opus |
| `effort` | 努力レベル（`low` / `medium` / `high` / `xhigh` / `max`） | セッション継承 | コスト・速度のトレードオフ |
| `context` | `fork` でサブエージェントとして分離実行 | インライン | 大量出力を分離したい・親 context を汚染したくない |
| `agent` | `context: fork` 時のサブエージェントタイプ | `general-purpose` | 読み取りのみは `Explore`、計画は `Plan` |
| `hooks` | スキルライフサイクルにスコープされたフック | なし | 特定ツールの前後で副作用が必要な場合のみ |
| `paths` | アクティブ化を制限する Glob パターン | なし | 特定パスのファイル操作のみで発火させたい場合 |
| `shell` | `bash`（既定）または `powershell` | `bash` | Windows 環境で PowerShell を使う場合のみ（`CLAUDE_CODE_USE_POWERSHELL_TOOL=1` が必要） |
 
### §2.3 ステップ A-3：description テンプレート（自動発火を確実にする）
 
`description` は Claude がスキルを適用するか判断する主要入力である。
公式：「主要なユースケースを前置きしてください。description と when_to_use の組み合わせテキストは 1,536 文字で短縮されます」
 
```yaml
description: |
  [このスキルが何をするか 1 文]。
  以下のいずれかに該当する場合に使用する。
  - [具体的なトリガー条件 1（動詞ベース）]
  - [具体的なトリガー条件 2（動詞ベース）]
  - [具体的なトリガー条件 3（動詞ベース）]
  [使用しないケース：除外条件を 1〜2 行で]。
```
 
注意点：
- 1,536 文字以内に収める（`when_to_use` と合算）。超過分は自動的に削られる
- 主要ユースケースを冒頭に置く（短縮時に削られないため）
- 動詞ベースで具体的に書く（「PDF 関連」ではなく「PDF からテキストを抽出する」）
> 注：「`PROACTIVELY` を冒頭に置く」はサブエージェントの慣習であり、スキル公式仕様にはない。
> プロジェクト規約として採用する場合は付録 B に明記する。
 
### §2.4 ステップ A-4：進歩的開示（Progressive Disclosure）の設計
 
公式：スキルは 3 レベルで読み込まれる。
 
| レベル | 内容 | サイズ目安 |
|-------|------|----------|
| 1. メタデータ | name + description | 常時 context（約 100 単語） |
| 2. SKILL.md 本体 | スキル発火時に context へ | 500 行以下を推奨 |
| 3. バンドルリソース | 必要に応じて読み込み | 無制限（スクリプトは読み込み不要で実行可） |
 
設計判定：
 
| 内容 | 配置先 |
|------|--------|
| いつスキルを使うか | description |
| スキルの中核手順・常時適用ルール | SKILL.md 本体 |
| 大量のリファレンス資料 | `references/*.md`（SKILL.md から「いつ読むか」と共に参照する） |
| 繰り返し処理スクリプト | `scripts/*`（SKILL.md から実行指示を出す） |
| 出力テンプレート・アセット | `assets/*` |
 
公式：「SKILL.md を 500 行以下に保ちます。詳細なリファレンス資料を別のファイルに移動します」「大規模なリファレンスファイル（>300 行）には目次を含めます」
 
### §2.5 ステップ A-5：設計検証チェックリスト

### §2.6 ステップ A-6：SKILL.md 生成・保存・報告

以下の手順を順守する。

#### A-6-1：template.md ベースの生成（必須）

`${CLAUDE_SKILL_DIR}/template.md` を読み込み、その章構造（フロントマター、目的、定義、原理原則、用語定義、強制ルール、実行プロセス、結果出力）に従って SKILL.md 本文を生成する。
テンプレートに無い章を独断で追加・削除しない。追加が妥当な場合は §0「仮説と事実の区別」に従い「（推奨／仮説）」と明示する。

§5 実行プロセスの各ステップには、template.md「ステップ詳細化要素」に定義される 3 要素（判定基準 / 出力先 / アンチパターン）を **適用条件に該当する場合のみ** 追加する。一律全ステップへの付与・該当ステップでの省略のいずれも禁止する。要素省略の根拠（適用条件のどの行に該当しないか）はユーザー報告の §3 設計検証結果に明記する。

§0「仮説と事実の区別」章は、template.md 末尾「§0 仮説と事実の区別 章」に定義される **適用条件に該当する場合のみ** 追加する。適用条件：(1) 外部権威からの引用と実務派生の推奨が混在する / (2) 主張の出所種別が複数ある / (3)「（推奨／仮説）」マーキングが本文に頻出する。機械的処理中心スキル（update-config 等）への適用は形骸化リスクのため避ける。設置時は誤読防御のため、§0 で宣言した区分マーカーを本文中で一貫して適用する（§0 単独では防御は完成せず、本文中の個別マーキングと両輪で機能する）。

§5 実行プロセスの「手順」要素（T3）は、template.md「ステップ詳細化要素」の 4 要素目として **適用条件に該当する場合のみ** 追加する。適用条件：(1) ステップが順序付きサブ操作に分解可能 / (2) 順序が意味を持つ / (3) 判定基準が併記される。手順 T3 を採用する場合、思考代替リスク防御セット（D1 原理ラッピング / D6 完了判定ゲート / D10 メタルール）を **必須セット** として併設する（template.md 末尾「手順 T3 採用時の思考代替リスク防御」参照）。手順 T3 単独採用（防御セットなし）は禁止する。

#### A-6-2：保存先の固定（必須）

生成した SKILL.md は以下の固定パスに保存する。

```
.claude/skills/<frontmatter.name>/SKILL.md
```

- `<frontmatter.name>` はフロントマター `name:` の値（§A.1 の命名規則：小文字・数字・ハイフン、≤64 文字）
- 同名ディレクトリが存在しない場合は新規作成する
- 既存 SKILL.md が存在する場合は上書き前にユーザー確認を取る
- 公式 §A.3 で定義された Project スコープに該当する

## §3. [B] 既存スキルレビューモード
 
入力されたスキル定義（YAML frontmatter + Markdown 本文）に対して、
以下の観点で必ずすべてレビューする。問題のない観点も「問題なし：[根拠]」として明示する。
 
### §3.1 レビュー観点（15 項目・必須適用）

各観点の詳細チェック項目は `${CLAUDE_SKILL_DIR}/references/review-observations.md` に外出し（進歩的開示適用）。
[B] 既存スキルレビューモード実行時は、本ファイルを必ず全文読み込んでから 15 観点すべてを評価する。問題のない観点も「問題なし：[根拠]」として明示する。

| 観点 | 内容 | 由来 |
|---|------|------|
| 1 | frontmatter 仕様適合 | 公式仕様（§2.2 / references/official-spec.md §A.1） |
| 2 | description のトリガー具体性（自動発火条件） | 公式仕様 |
| 3 | description 文字数（≤1,536 文字） | 公式仕様 |
| 4 | 呼び出し制御の妥当性（disable-model-invocation / user-invocable） | 公式仕様 |
| 5 | ツール権限の最小性（allowed-tools） | 公式仕様 |

## 付録 B：プロジェクト規約との連携（推奨／仮説）
 
> **注記**：本付録の内容はプロジェクト固有の運用合意であり、公式仕様ではない。
> 採用は任意。
 
### B.1 既存スキル命名との衝突回避

既存スキル名リストは `${CLAUDE_SKILL_DIR}/references/project-conventions.md` §B.1 を参照（推奨／仮説）。新規スキル設計時に名前重複を確認する。公式バンドルとの衝突回避は references/official-spec.md §A.9 を併読。
 
### B.2 description の言い切り形
 
description のトリガー条件は語尾を言い切り形（「〜する」「〜である」）で統一する（推奨／仮説：プロジェクト内既存スキルとの整合）。
 
### B.3 §0「仮説と事実の区別」章（推奨／仮説）

§0 章は適用条件に該当する場合のみ追加する（推奨／仮説：プロジェクト規約）。詳細は `${CLAUDE_SKILL_DIR}/template.md` 末尾「§0 仮説と事実の区別 章」を参照。

| 適用条件 | 適用例 |
|---------|--------|
| 外部権威からの引用と実務派生の推奨が混在する | clean-architecture / coding 系 / security |
| 主張の出所種別が複数ある | system-design / spec-driven-development / skill-designer |
| 「（推奨／仮説）」マーキングが本文に頻出する | clean-architecture / coding 系 |

不適用：機械的処理中心スキル（update-config 等）への適用は形骸化リスクのため避ける。

§0 の真の機能は **AI 生成のエピステミック契約を本文冒頭でコンテキスト注入する** ことであり、AI 著者の規律強制装置として位置付ける。誤読防御は §0 + 本文中の個別マーキングの両輪で機能する（§0 単独では完成しない）。
 
### B.4 出力フォーマットの統一
 
レビュー系スキルが評価レポートを出力する場合、深刻度ラベル（🔴 CRITICAL / 🟡 WARNING / 🔵 INFO）方式を採用する（推奨／仮説：プロジェクト内既存スキルとの整合）。
 
### B.5 サブエージェント関連スキルとの連携
 
スキル本体が `context: fork` でサブエージェントとして動作する設計を含む場合、subagent-creator スキルのレビュー観点（特に観点 2「description のトリガー具体性」と観点 3「ツール権限の最小性」）も併用する（推奨／仮説）。

### B.6 ステップ詳細化要素（推奨／仮説）

§5 実行プロセスの各ステップに付随させる以下 3 要素は、適用条件に該当する場合のみ追加する（推奨／仮説：プロジェクト規約）。詳細は `${CLAUDE_SKILL_DIR}/template.md` 末尾「ステップ詳細化要素」を参照。

| 要素 | 適用条件 | 適用例 |
|------|----------|--------|
| 判定基準 | ステップに判断要素がある（≒ ほぼ全ステップ） | system-design / error-diagnosis / tdd / spec-items-clarifier / code-review / coding 系 |
| 出力先 | スキルが外部出力テンプレート（`${CLAUDE_SKILL_DIR}/output.md` 等）を持つ | clean-architecture / coding 系 |
| アンチパターン | ドメインに既知失敗パターンが蓄積されている | tdd / git-local / document / coding 系 |

重複適用回避：clean-architecture / subagent-creator / skill-designer 等、既に richer な per-step プロトコル（「ユーザーからの問い／根拠／手順／出力」等）を持つスキルには適用しない。

機械的タスク中心のスキル（update-config 等）への適用は形骸化リスクのため避ける。

### B.7 手順 T3 + 思考代替リスク防御セット（推奨／仮説）

§5 実行プロセスの「手順」要素（T3）を採用するスキルは、思考代替リスク（AI が手順を機械的に踏襲し判断を放棄する失敗モード）を構造的に防ぐため、以下 3 防御を **必須セット** として併設する（推奨／仮説：プロジェクト規約）。詳細は `${CLAUDE_SKILL_DIR}/template.md` 末尾「手順 T3 採用時の思考代替リスク防御」を参照。

#### T3 該当範囲（適用範囲の限定）

T3 は **§5 実行プロセス章または同等の中核フロー章に配置され、スキル本体の主目的を達成するための中核フロー** を構成する手順のみを対象とする。以下は T3 対象外であり、防御セット併設は不要：

- 異常時例外回復手順・フォールバック条件分岐
- 前提条件確認手順・初期化手順
- 出力フォーマットの記述順序

「順序付き手順がある = T3」ではない。判定基準は観点 15.0（references/review-observations.md）を参照。
