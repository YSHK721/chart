# 目的

最速で試作を作り、動かして確認し、問題を早期に洗い出せ。

## §1. 定義

最小で動く試作を最短経路で作れ。実際に動かして確認せよ。問題を直し、再度試作と確認を繰り返せ。この高速ループで問題への気づきを最短化せよ。

確認はハイブリッドで行え。エージェントが起動・操作・スクリーンショット・実測で自動検証し、問題を証拠付きで列挙報告せよ。その上でユーザー確認を取れ。

アーキテクチャの美しさ・抽象化・恒久品質を追うな。前倒し検出のための軽量な高速ループに徹せよ。

## §2. 原理原則

- 最短経路を優先せよ。動く最小試作を最短で作れ。抽象化・レイヤー分離・最適化を持ち込むな。
- 試作は使い捨てとして作れ。再利用品質を求めるな。
- 必ず動かして確認せよ。「読んで正しそう」で止めるな。起動・操作・スクリーンショット・実測の証拠で判断せよ。
- 確認はハイブリッドで行え。自動検証だけで完了とするな。ユーザー確認を経て次サイクルを決めよ。
- テストの合否では落ちない設計・仕様・UX の問題を狙って洗い出せ。
- 1 サイクルを小さく区切れ。検出 → 修正 → 再確認を素早く回せ。完璧な 1 発を狙うな。
- **「最速」は試作を作る速さの意であり、仕様の簡略化を許す指示ではない。** 検証対象の核心挙動（仕様が定める方法・粒度・対象範囲）は仕様どおり忠実に再現せよ。これを偽装・簡略化・間引きしてはならない。省いてよいのは、核心の検証に無関係な周辺の足場のみ。
- **試作は隔離して作れ。** 既存の本体コード・データから分離した場所（専用のブランチ／ディレクトリ）に置き、**既存資産は読み取り専用**として改変・波及させるな。

## §3. 用語定義

| 用語 | 定義 |
|---|---|
| 試作 | 検証対象の振る舞いを最小限で再現する使い捨てコード。恒久品質・構造正しさを問わない |
| 最短経路 | 動作確認に到達する最小手数。既存コード・ハードコード・スタブ流用を許容する |
| ハイブリッド確認 | エージェント自動検証（起動・操作・スクショ・実測）による問題列挙報告と、ユーザー確認の 2 段 |
| 自動検証 | 起動・操作・スクリーンショット・実測（時間・出力・件数）による振る舞いの観察 |
| 収束 | ユーザーが方向性を承認し、次の作業へ引き渡せる状態 |

## §4. 強制ルール

| ルール | 内容 |
|---|---|
| 改変禁止 | 指示以外の改変を行うな |
| 主観禁止 | 主観・感想・印象を出力するな。問題は観察した証拠で示せ |
| 道具に徹せよ | このスキルはエージェントが使う道具である。他エージェントの招集・承認フローの統括を行うな |
| 過剰設計禁止 | 試作段階で最適化・抽象化・汎用化を行うな。最短経路を優先せよ |
| 証拠なし完了禁止 | 実際に動かした証拠なしに「確認済み」と報告するな |
| 確認スキップ禁止 | 自動検証の報告だけで完了とするな。ユーザー確認を経て次サイクルを判断せよ |
| 破壊的操作禁止 | データの不可逆削除・本番操作・既存共有モジュールの破壊的変更を行うな |
| 言い切り厳守 | 曖昧表現を使うな。観察事実と判断を言い切れ |

## §5. 実行プロセス

S-1 から S-4 を 1 サイクルとせよ。S-4 で未収束と判定したら S-1 へ戻り反復せよ。

### step S-1: 検証対象を 1 つに絞れ

- 判定基準：今サイクルで確かめる問いを 1 つに絞れ。動作で OK/NG を判定できる形にせよ。
- 禁止：複数の不安をまとめて検証するな。OK/NG を判定できない問いを立てるな。

### step S-2: 最速で試作を作れ

- 判定基準：S-1 の問いを動かして確かめられる最小コードにせよ。恒久品質・抽象化を持ち込むな。
- 手順：
  1. 動作確認に必要な最小範囲を特定せよ。問いに無関係な部分はスタブ・固定値で省け。
  2. 既存コード・流用可能資産を Glob / Grep で探し、再利用で手数を削れ。
  3. 最小試作を Write / Edit で作れ。
- 禁止：問いに無関係な部分を作り込むな。アーキテクチャを整えるな。テスト網羅を始めるな。

### step S-3: 動かして確認せよ（自動検証 ＋ ユーザー確認）

- 判定基準：動かした証拠で S-1 の問いに OK/NG を付けよ。問題を観察事実として列挙せよ。その上でユーザー確認を取れ。
- 手順：
  1. 試作を実際に動かせ。手段は対象に応じて選べ（付録 A）。
  2. 観察結果から設計・仕様・UX の問題を証拠付きで列挙せよ。
  3. 列挙した問題と現状をユーザーに報告し、確認と次アクションの判断を仰げ。
- 禁止：動かさず報告するな。問題を主観で書くな。ユーザー確認を省くな。

### step S-4: 直して収束を判定せよ

- 判定基準：今サイクルで直すと決めた問題を直せ。ユーザー判断で収束か未収束かを判定せよ。
- 手順：
  1. 合意した修正を最短経路で試作に反映せよ。
  2. ユーザーが方向性を承認したら収束とせよ。残課題があれば未収束とせよ。
  3. 未収束なら残った問いを S-1 に渡し、次サイクルを開始せよ。
- 禁止：ユーザー判断を待たず先へ進むな。試作修正で構造最適化を始めるな。未収束で完了報告するな。

### ステップ完了判定

各 step の手順を終えたら、次へ進む前に検証せよ：

- [ ] 判定基準（問い・証拠・確認）への回答を出力に含めたか。
- [ ] 入力前提と矛盾する結果を出していないか。
- [ ] 出力が次 step の入力として整合するか。

充足しないなら手順を機械的に繰り返すな。判定基準に立ち返り別経路を取れ。3 回失敗したら中断し、確かめられなかった点を証拠付きで報告せよ。

## §6. 結果出力

各サイクル完了時に簡潔に報告せよ：

1. 今サイクルで確かめた問い（S-1）。
2. 動かした証拠と検出した設計・仕様・UX の問題（S-3）。
3. 実施した修正と収束判定（S-4）。

## 付録 A：自動検証の手段

対象種別に応じて手段を選べ。

| 対象種別 | 起動・実行 | 観察 |
|---|---|---|
| CLI / スクリプト | Bash で直接実行せよ | 標準出力・終了コード・実測時間・出力件数を見よ |
| サーバ / API | Bash でサーバをバックグラウンド起動し、curl でリクエストせよ | HTTP 応答・ステータス・内容・レイテンシを見よ |
| ブラウザ UI | 起動手順で起動し、操作後のスクリーンショットを取れ | 取得画像を Read で視認し、ユーザーへ提示せよ |
| ライブラリ / 関数 | 最小呼び出しスクリプトを Bash で実行せよ | 戻り値・例外・境界値の挙動を見よ |
