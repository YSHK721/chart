# 目的

コードドキュメント必須化と粒度最適化

## §0. 仮説と事実の区別

| 区分 | 取り扱い | 表記 |
|---|---|---|
| 公式仕様（事実） | そのまま採用する | 出典なしで断定する |
| プロジェクト規約 | プロジェクト内で適用する | 「プロジェクト規約より」と明示する |
| 推奨（仮説） | 採用は任意。根拠を併記する | 「（推奨／仮説）」と明示する |
| 不明 | TBD として未解決事項に記録する | 「TBD: 確認要」と明示する |

## §1. 定義

コードドキュメントとは、関数・クラス・構造体・プロトコル・モジュールに付与する形式化された説明であり、役割・契約（前提・制約・副作用）・入出力仕様・例外・使用例を含む。本スキルでは「書く／書かない」を選択せず、**プロジェクト規約より必ず書く前提で粒度（高／中／低）のみを調整する**。

ドキュメントの形式は以下を含む。

| 形式 | 対象 | 主な記載内容 |
|---|---|---|
| ドキュメントコメント | 関数・クラス・構造体・プロトコル | 役割・パラメータ・戻り値・例外・使用例 |
| インラインコメント | 反直感的・複雑な実装行 | WHY（理由・背景・制約） |
| ADR（設計決定記録） | アーキテクチャ・設計判断 | 状況・決定・理由・結果・代替案 |
| API 仕様書 | 公開インターフェース | エンドポイント・契約・エラー条件 |
| README | プロジェクト・モジュール | 5 分概要・セットアップ・主要概念 |

## §2. 原理原則

- **必須記載原則**：関数・クラス・構造体・プロトコルには例外なくドキュメントコメントを付与する。記載するか否かを問わず、粒度のみを文脈で判定する（プロジェクト規約より）。
- **Why over What**：実装が示す「何を」ではなく「なぜ」「どの契約で」を記述する。
- **契約の明示**：前提・制約・副作用を曖昧さなく記述する。
- **実装整合性**：ドキュメントは実装と完全に一致する。乖離は陳腐化として即時是正する。
- **粒度の文脈依存**：複雑度・規模・期間・ドメインから粒度を導出する（推奨／仮説：実証研究では複雑コードでドキュメント有効性が顕著、単純コードで効果限定的）。
- **6 ヶ月後可読性**：未来の自分・新規メンバーが即理解できる抽象度を維持する。

## §3. 用語定義

| 用語 | 定義 |
|---|---|
| 粒度 | ドキュメント記述の深さ。高（背景・代替案・トレードオフまで）／中（目的・契約・境界条件）／低（要約・契約・使用例）の 3 段階 |
| 必須項目 | 役割・目的・パラメータ・戻り値・例外・使用例の 6 項目 |
| ADR | Architecture Decision Record。状況・決定・理由・結果・代替案を記録する設計判断文書 |
| 陳腐化 | 実装変更にドキュメントが追従せず、記述と実装が乖離した状態 |
| 契約 | 関数・モジュールが満たすべき前提条件・事後条件・不変条件・副作用 |
| 進歩的拡張 | 最小実装で全箇所に必須項目を記載した後、価値の高い箇所から粒度を高める段階的アプローチ |

## §4. 強制ルール

| ルール | 内容 |
|---|---|
| 改変禁止 | 指示以外の改変は絶対に禁止する |
| 主観禁止 | 主観・感想・印象（「良いドキュメント」等）の出力は絶対に禁止する |
| 必須項目省略禁止 | 役割・目的・パラメータ・戻り値・例外・使用例の 6 項目を「実装を読めば分かる」を理由に省略することを禁止する |
| 粒度ゼロ禁止 | 粒度判定で「書かない」を選択することを禁止する。低粒度（簡潔記載）が下限である |
| 曖昧語禁止 | 「適切に」「可能な限り」「効率的に」「一般的に」「標準的な」「速やかに」等の曖昧語をドキュメント本文で使用することを禁止する |
| 実装整合性違反禁止 | ドキュメントと実装が乖離した状態で完了とすることを禁止する |
| 自明性根拠拒否 | 「自明だから不要」を省略根拠として使用することを禁止する。自明性は読み手依存であり、書き手判定では決定不能 |

## §5. 実行プロセス

### step S-1: 文脈評価
- **判定基準**：複雑度（アルゴリズム・業務ロジック）／規模（コードベース行数・モジュール数）／期間（短期・中期・長期）／ドメイン（汎用・専門）の 4 軸を客観指標で測定する
- **アンチパターン**：主観的印象（「単純そう」）のみで判定する／複雑度を実装行数のみで近似する

### step S-2: 粒度判定
- **判定基準**：高粒度＝複雑度高 + 規模大 + 長期 + 専門ドメイン、中粒度＝条件が部分的に該当、低粒度＝複雑度低 + 規模小 + 短期 + 汎用ドメイン
- **アンチパターン**：「書かない」を選択肢に含める（必須記載原則違反）／全関数を一律高粒度にする（保守コスト過大）

### step S-3: 必須項目記載
- **判定基準**：役割／目的／パラメータ（型・意味・制約）／戻り値（型・意味・可能値）／例外（条件・対処）／使用例の 6 項目をすべて記述する。低粒度でも 1〜3 行で全項目を満たす
- **アンチパターン**：パラメータ説明を型シグネチャで代替する／例外項目を空欄にする／使用例を `TODO` で残置する

### step S-4: 補助記述
- **判定基準**：高粒度時は ADR 形式の設計決定記録／アルゴリズム解説（WHY・トレードオフ・参考資料）／API 仕様詳細を追加。中・低粒度時はインラインコメント（反直感箇所の WHY）／ビジネスルール／一時的回避策（撤去条件付き）／README の 5 分概要に限定
- **アンチパターン**：形式的すぎる仕様書を作成し読まれなくなる／頻繁に変わる実装詳細を逐語コピーして陳腐化を加速する

### step S-5: 整合性検証
- **判定基準**：ドキュメント記述と実装が完全一致しているか、Lint・静的解析・コメント-コード差分検出ツールで検証する。使用例は実行可能形式で検証する
- **アンチパターン**：実装変更時にドキュメント更新を後回しにする（「後でまとめて」が陳腐化を生む）／自動生成ツール（JSDoc / TypeDoc / Doxygen / Swift-DocC）出力を確認せず公開する

### step S-6: 継続見直し
- **判定基準**：価値・粒度・陳腐化を定期評価し、価値が高い箇所のみ粒度を引き上げる／陳腐化を検出した箇所のみ更新する
- **アンチパターン**：全体一律で粒度を変更する／陳腐化検出を CI に組み込まず人手レビューに依存する

## §6. 結果出力

完了時に以下を順に出力する。

1. **対象一覧**：ドキュメント追加・更新を行ったファイル・シンボル（関数・クラス・構造体）の一覧
2. **粒度判定根拠**：§S-1 文脈評価の 4 軸測定値と §S-2 で導出した粒度（高／中／低）
3. **記載内容サマリ**：各シンボルに対する必須 6 項目の記述状況（記載済み／不該当の理由）
4. **整合性検証結果**：実装との一致確認結果、自動化ツール出力、検出した陳腐化と是正内容
5. **未解決事項**：TBD として残った項目（例：「専門ドメイン用語の定義は SME 確認待ち」）を表で出力する

異常時（必須項目を埋められない／実装と矛盾／自動化ツール失敗）は §S-3 以降を中断し、原因と再開条件を明示して報告する。
