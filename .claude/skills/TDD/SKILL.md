# 目的

Red-Green-Refactor を厳守する

| 区分 | 取り扱い | 表記 |

| 古典文献（事実：Beck / Martin） | そのまま採用する | 出典なしで断定する |
| プロジェクト規約 | プロジェクト内で適用する | 「プロジェクト規約より」と明示する |

## §1. 定義

テスト駆動開発（Test-Driven Development）とは、Kent Beck が定式化した「失敗するテストを先に書き、最小実装で通過させ、テスト全通過状態でリファクタリングする」最小単位サイクル開発手法である。

本スキルは、Red→Green→Refactor の順序厳守、テストファースト、最小単位開発（1 サイクル = 1 機能 = 1 テストケース）、AAA パターン、F.I.R.S.T 原則、カバレッジ 100% 維持を構造的に強制し、実装前テスト作成違反・段階的リファクタリング原則違反を防止する。

## §2. 原理原則

- テストファースト：プロダクションコードはテストの後にしか書かない（Martin TDD 第一法則）
- 最小単位：1 サイクルで 1 振る舞いのみを扱い、複数機能の同時実装を禁止する
- 順序厳守：Red→Green→Refactor の順序を絶対に逆転させない
- 不変条件：リファクタ中に新規振る舞いを追加せず、テストが Green の状態でのみ構造改善する
- 100% カバレッジ：すべての分岐・境界・例外パスを累積結果としてカバーする（事後指標）
- AAA：各テストを Arrange / Act / Assert の 3 区分で構造化する
- F.I.R.S.T：Fast / Independent / Repeatable / Self-Validating / Timely を満たす

詳細は `${CLAUDE_SKILL_DIR}/references/principles.md` を参照（進歩的開示適用）。

## §3. 用語定義

| 用語 | 定義 |
|---|---|
| 🔴 Red | 仕様の意図を表明する失敗するテストを書き、期待された理由で失敗することを確認するフェーズ |
| 🟢 Green | 当該テストを通す最小実装を投入し、当該テスト + 全テストの通過を確認するフェーズ |
| ♻️ Refactor | テスト全通過状態で構造を改善するフェーズ。新規振る舞いの追加を禁ずる |
| AAA | Arrange（準備）/ Act（実行）/ Assert（検証）の 3 区分テスト構造 |
| F.I.R.S.T | Fast / Independent / Repeatable / Self-Validating / Timely の 5 原則（Beck） |
| 最小単位 | 1 サイクル = 1 機能 = 1 テストケース = 1 実装単位 |
| 境界値 | 同値クラスの境界に位置する入力値（references/test-design-patterns.md §TD.2） |
| カバレッジ 100% | 分岐・境界・例外パスのすべてに対応するテストケースが存在する状態 |
| 完了判定ゲート | 各サイクル完了時にチェックリスト全項目を検証するゲート（D6 防御） |

## §4. 強制ルール

| ルール | 内容 |
|---|---|
| 改変禁止 | 指示以外の改変は絶対に禁止する |
| 主観禁止 | 「良いテスト」等の感想・印象の出力は絶対に禁止する |
| テストなし実装禁止 | テストなしで実装コードを 1 行も書かない |
| 順序逆転禁止 | Red → Green → Refactor の順序を絶対に逆転させない |
| 同時実装禁止 | 1 サイクルで複数機能を扱わない |
| 成功テスト先行禁止 | 必ず通るテストを Red と称さない（Red は期待された理由で失敗する必要がある） |
| Refactor 中の振る舞い追加禁止 | リファクタ中に新規ロジック・分岐・APIを追加しない |
| カバレッジ偽装禁止 | 計測対象から除外して 100% を達成する設定変更を禁ずる |
| テストスキップ禁止 | 失敗テストを `skip` / `pending` / `xfail` に書き換えない |
| Red 観測ゲート | step S-3 で Red が観測できない場合（テストを書いた直後の初回実行で Pass した場合）は当該 step を中断し、原因を分類して報告する。分類軸：① 過剰実装（前 step S-4 で AP.2 G-1 の振る舞いを先取り実装した）／② 成功テスト先行（AP.1 R-2）／③ 実装の事前残存（テスト対象が既存コードに存在していた）／④ assertion 弱体（テストが実装の不在を検出できない弱い assertion）。Red 観測欠落のまま Green / Refactor に進むことを禁ずる（AP.1 R-7） |
| 思考代替防止 | 各 step の「手順」は必ず「判定基準」と併記する。手順単独記述を禁止する（D1 原理ラッピング） |
| 判定基準優先 | 各 step で「手順」と「判定基準」が衝突した場合は判定基準を優先する。手順への機械的従属を禁止する（D10 メタルール） |
| **計算量テスト必須** | **計算を伴うサイクルには計算量テスト（algorithmic complexity test）を必ず添える。例外なし**（絶対命令 2026-08-28）。詳細は §4.1 |

### §4.1 計算量テスト（絶対命令・例外なし）

状態検証（出力の正しさ）だけでは**原理的に落ちない**欠陥がある。「作ってから捨てる」実装は
出力が正しいままなので、通常の Red-Green では永久に緑になる。

| 項目 | 内容 |
|---|---|
| 測る対象 | **時間ではなく回数**。時間の閾値はマシン負荷で揺れ、緩んで浪費を通す |
| 最小形 | Test Spy で発行回数を数え `発行した計算 − 出力に使った計算 = 0` を assert する（インタラクションテスト／behaviour verification。同型例は `assertNumQueries`・N+1 検出） |
| 追加で固定 | 入力（窓・limit・期間長）を変えた 2 点以上で、**発行数が出力量だけで決まる**こと（オーダーの表明） |
| 禁止 | 回数そのもの（「N 回呼ばれること」）を期待値に焼き込むこと。浪費が仕様へ昇格する |
| 固定するもの | 実装詳細ではなく**無駄の不在** |

**根拠**: ISSUE-450。既存テスト 1,233 件が緑のまま 20 日間この浪費を保護し、1m チャートで
1 ティックあたり 12.2 秒・破棄率 98.0% を生んでいた。しかも
`test_window_bars_limits_the_output_but_not_the_folding` が「窓外バーの計算が発行されること」を
assert し、浪費を仕様へ昇格させていた。同型は ISSUE-257 でも裁定済みだったが、文章で残して
検査に落とさなかったため再発した。**規約は宣言でなく機械的検査で強制する。**

参照実装: `indigators/indicator_ui/api/tests/test_mtf_causal_complexity.py`

## §5. 実行プロセス

判定基準層（「どう決めるか」「完了条件」）が「手順」を原理的に拘束する（思考代替リスク防御 D1）。手順を逐次踏襲しただけではステップ完了とみなさない。判定基準充足の検証は §5 末尾「ステップ完了判定」（D6）で実施する。

### step S-1: 要件分析

- **判定基準**：機能・目的・入力・出力・制約条件・対象外の 6 要素が一意確定したか
- **出力先**：`${CLAUDE_SKILL_DIR}/output.md` §1 要件分析テンプレート
- **アンチパターン**：制約条件未確定で次へ進む。「対象外」を明示せず暗黙の仕様を後から追加する

### step S-2: テストケース設計

- **判定基準**：正常系・境界値（下限/上限/0/空）・異常系を網羅し、各テストケースに references/test-design-patterns.md §TD.X の設計根拠が紐付いているか
- **出力先**：`${CLAUDE_SKILL_DIR}/output.md` §2 テストケース設計テンプレート
- **アンチパターン**：正常系のみで進む。設計根拠を記載せず「思いつき」でケースを並べる

### step S-3: 🔴 Red — 失敗テスト作成・実行・確認

- **判定基準**：以下をすべて満たすか
  - 書いたテストが「期待された理由」で失敗している（コンパイルエラー・関数未定義による失敗は判定基準を満たさない場合がある — references/anti-patterns.md §AP.1 R-5 を参照）
  - テスト対象の実装（クラス・関数・メソッド）が事前に存在しないことを実証している（grep / Read による不在確認）— Red 観測ゲート（§4 強制ルール）の事前条件
  - 1 回目実行で当該テストが Pass しない（Pass した場合は R-7 Red 観測欠落に該当 → §6 異常時出力に進む）
- **手順**（D1 原理ラッピング — 判定基準と必ず併記）：
  1. step S-2 のテストケースから 1 件を選定
  2. **テスト対象の実装が事前に存在しないことを実証**（`grep -rn "対象シンボル" 対象ディレクトリ` または Read による不在確認）。実装が事前存在する場合は当該 step を中断し、原因を §4 強制ルール「Red 観測ゲート」の 4 分類軸で報告する
  3. 失敗するテストコードを書く（実装を先に書かない）
  4. テストを実行
  5. 失敗内容を確認し「期待された理由か」を判定。**初回実行で Pass した場合は R-7 Red 観測欠落として §X 異常時中断報告に進む**（手順 2 で不在確認したにも関わらず Pass する場合は assertion 弱体を疑う）
- **出力先**：`${CLAUDE_SKILL_DIR}/output.md` §3 Red 結果テンプレート
- **アンチパターン**：references/anti-patterns.md §AP.1（実装ファースト / 成功テスト先行 / 失敗確認スキップ / 多機能テスト / コンパイルエラー Red / 期待値置き去り / **Red 観測欠落**）

### step S-4: 🟢 Green — 最小実装・全テスト通過確認

- **判定基準**：当該テストが通り、既存全テストが破壊されていないか。最小性チェック（過剰実装・設計最適化・並行機能追加なし）を充足するか
- **手順**（D1 原理ラッピング — 判定基準と必ず併記）：
  1. テストを通す最小実装を書く（美しさ・最適化は後回し）
  2. 当該テスト（TC-XXX）を実行して通過確認
  3. 全テストを実行して破壊なし確認
  4. カバレッジ計測（前回比較）
- **出力先**：`${CLAUDE_SKILL_DIR}/output.md` §4 Green 結果テンプレート
- **アンチパターン**：references/anti-patterns.md §AP.2（過剰実装 / 設計最適化 / 並行機能追加 / 全テスト未実行 / テスト改変 / カバレッジ無視）

### step S-5: ♻️ Refactor — リファクタリング・全テスト通過確認

- **判定基準**：全テストが通過し、新規ロジック・分岐・API が追加されていないか。リファクタ前にテストが Green であったか
- **手順**（D1 原理ラッピング — 判定基準と必ず併記）：
  1. リファクタ対象（重複 / 命名 / 抽象化レベル等）を特定
  2. リファクタ前にテストが Green であることを確認
  3. リファクタリング実施（実装ファイルのみ。テストは変更しない）
  4. 全テストを実行して通過確認
  5. カバレッジ維持を確認
- **出力先**：`${CLAUDE_SKILL_DIR}/output.md` §5 Refactor 結果テンプレート
- **アンチパターン**：references/anti-patterns.md §AP.3（新規ロジック追加 / テスト未実行 / 赤のままリファクタ / テストコード変更 / 過剰抽象化 / 全置き換え）

### step S-6: 完了判定（D6 完了判定ゲート）

- **判定基準**：以下すべて充足するか
  - テストが存在し実行可能（step S-3 出力にテストコード）
  - Red / Green / Refactor の各 step 出力が揃っている
  - カバレッジ 100%（references/principles.md §P.6 条件）
  - テスト名が機能・期待結果を正確に記述
  - リファクタ後も全テストが通過
  - 横断アンチパターン（references/anti-patterns.md §AP.4）非該当
- **出力先**：`${CLAUDE_SKILL_DIR}/output.md` §6 完了判定テンプレート
- **アンチパターン**：未充足項目があるのに「完了」と報告する

### ステップ完了判定（思考代替リスク防御 D6）

各 step（S-1〜S-5）の「手順」完了後、以下を検証してから次の step に進む：

- [ ] 判定基準（問い・期待）への回答が出力に含まれているか
- [ ] 入力前提と矛盾する結果が出ていないか（例：Red 段階でテストが通過した／Green 段階で他テストが破壊された）
- [ ] 出力が次 step の入力として整合するか

充足しない場合：手順を機械的に再実行せず、判定基準に立ち返り別経路を検討する。最大 3 回再試行、3 回失敗時は §6 異常時出力（output.md §X）で中断報告する。

step S-6 完了判定ゲートが 3 回連続で未充足の場合も同様に中断報告に進む。
