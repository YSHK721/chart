# 目的

リスクベースのコードレビュー実施

## §0. 仮説と事実の区別

| 区分 | 取り扱い | 表記 |
|---|---|---|
| 公式仕様（事実） | そのまま採用する | 出典なしで断定する |
| プロジェクト規約 | プロジェクト内で適用する | 「プロジェクト規約より」と明示する |
| 推奨（仮説） | 採用は任意。根拠を併記する | 「（推奨／仮説）」と明示する |
| 不明 | TBD として未解決事項に記録する | 「TBD: 確認要」と明示する |

## §1. 定義

コードレビューとは、コミット差分・プルリクエスト・パッチに対し、セキュリティ・ビジネスロジック・パフォーマンス・設計・エラー処理・テスト・可読性の観点から品質欠陥を検出し、優先度付きフィードバックを発行する活動である。本スキルでは「変更のリスクレベル（高／中／低）」に応じてレビュー深度を切替える**リスクベース手法**を採用する（推奨／仮説：均一深度レビューによるレビュー疲労と重大欠陥の見落としを軽減）。

## §2. 原理原則

- **リスクベース原則**：レビュー深度は変更のリスクレベルに比例する。複数該当時は最高リスクを採用する。
- **優先度分類原則**：欠陥は必須（マージブロッカー）／推奨（次回リリースまでに対応）／将来改善（バックログ）の 3 段階に分類する。
- **証拠ベース指摘原則**：すべての指摘に「該当箇所の引用」「根拠（規約・仕様・実証）」「修正案」を併記する。
- **早期差し戻し原則**：定義された差し戻し基準に該当した時点でレビューを中断し、修正後の再提出を要求する。
- **観察的並列性**：レビュー観点は順序依存ではなく並列適用可能であり、観点間の独立性が網羅性を担保する。
- **承認基準明示原則**：必須修正の解消・CI 通過・回帰テスト合格・ドキュメント反映を承認の必要条件とする。

## §3. 用語定義

| 用語 | 定義 |
|---|---|
| リスクレベル | 変更が本番障害・セキュリティ侵害・データ破壊を引き起こす確率と影響度の合成評価。高／中／低の 3 段階 |
| 高リスク | セキュリティ・金融・PII/PHI・認証認可・DB スキーマ変更のいずれかを含む変更。3 段階レビュー必須 |
| 中リスク | ビジネスロジック・API 契約変更・パフォーマンスクリティカル処理・外部連携のいずれかを含む変更 |
| 低リスク | UI/UX 軽微調整・ドキュメント更新・テスト追加（ロジック変更なし）・挙動不変リファクタリングのみ |
| 必須修正（🔴） | マージブロッカー。セキュリティ脆弱性・データ破壊可能性・明らかなバグ |
| 推奨修正（🟡） | 次回リリースまでに対応。パフォーマンス改善・可読性向上・ベストプラクティス準拠 |
| 将来改善（🟢） | バックログへ。リファクタリング提案・設計パターン改善・ドキュメント充実 |
| 差し戻し基準 | レビュー継続を中断し修正再提出を要求する条件（§5 step S-5 で定義） |
| 承認基準 | マージ承認の必要条件 4 項目（§5 step S-6 で定義） |

## §4. 強制ルール

| ルール | 内容 |
|---|---|
| 改変禁止 | 指示以外の改変は絶対に禁止する |
| 主観禁止 | 主観・感想・印象（「良いコード」「きれい」「美しい」等）の出力は絶対に禁止する |
| リスク判定省略禁止 | step S-1 のリスクレベル判定を省略してレビューに入ることを禁止する |
| 証拠なし指摘禁止 | 該当箇所の引用・根拠・修正案を伴わない指摘の発行を禁止する |
| 優先度未分類禁止 | 必須／推奨／将来改善の優先度を付与せず指摘を羅列することを禁止する |
| 曖昧語禁止 | 「適切に」「可能な限り」「効率的に」「一般的に」「標準的な」「速やかに」「リアルタイム」等の曖昧語をフィードバック本文で使用することを禁止する |
| 差し戻し継続禁止 | step S-5 の差し戻し基準該当を検知した時点で残り観点のレビューを中断する。継続レビューによる総合承認判定を禁止する |
| 承認基準未充足承認禁止 | §6 で「承認可」と判定する前に必須修正解消・CI 通過・回帰テスト合格・ドキュメント反映の 4 条件すべての充足を確認することを禁止解除条件とする |

## §5. 実行プロセス

### step S-1: リスクレベル判定
- **判定基準**：高＝（セキュリティ／金融／PII/PHI／認証認可／DB スキーマ変更）のいずれかを含む。中＝（ビジネスロジック／API 契約変更／パフォーマンスクリティカル／外部サービス連携）のいずれかを含む。低＝UI 軽微・ドキュメント・テスト追加・挙動不変リファクタリングのみ。複数該当時は最高リスクを採用する
- **アンチパターン**：複数該当時に低い方を採用する／UI 変更だが認証チェックを含む差分を「UI 変更だから低」と誤判定する／差分行数のみでリスクを判定する

### step S-2: 事前チェック
- **判定基準**：①差分 ≤200 行／②CI/CD 全通過／③関連 issue・チケットがリンク済／④必要テスト（ユニット・統合・回帰）同梱／⑤静的解析・自動フォーマッター適用済／⑥依存関係の脆弱性スキャン済、の 6 項目を確認する。未通過項目はレビュー結果に明示記録した上で次 step に進む（差し戻し可否は step S-5 で判定）
- **アンチパターン**：事前チェック未通過のままレビュー深度を投入する／200 行超を「分割すべき」と注意せず黙認する／CI 失敗を flaky として確認なく無視する

### step S-3: リスクレベル別レビュー
- **判定基準**：高リスク＝（A）設計とアーキテクチャ／（B）ロジックとエラー処理／（C）品質と保守性の 3 段階全実施。中リスク＝主要ロジック・エラー処理・テストカバレッジ・可読性の 4 観点を実施し必要に応じて品質項目を参照。低リスク＝コーディング規約準拠・タイポ・不要差分・変更意図明確性の軽量確認のみ
- **アンチパターン**：高リスク変更で（A）設計確認を省略しいきなりロジックレビューに入る／中リスクを高リスクとして 3 段階全件実施しレビュー時間を消尽する／低リスクで主観に基づく「もっと美しく書けるはず」を指摘する

### step S-4: 指摘の優先度分類
- **判定基準**：🔴 必須＝セキュリティ脆弱性・データ破壊可能性・明らかなバグ。🟡 推奨＝パフォーマンス改善・可読性向上・ベストプラクティス準拠。🟢 将来改善＝リファクタリング提案・設計パターン改善・ドキュメント充実。各指摘に「該当箇所の引用・問題点・推奨される解決策・参考リンクまたはコード例」を付与する
- **アンチパターン**：可読性向上を必須に格上げする／セキュリティ脆弱性を推奨に格下げする／優先度を付与せず指摘を羅列する／修正案を示さず問題のみ指摘する

### step S-5: 差し戻し基準判定
- **判定基準**：以下のいずれか 1 件でも該当した時点で「差し戻し（承認不可）」を確定する。①セキュリティ脆弱性（未サニタイズ入力・秘匿情報のログ出力等）／②カバレッジ < 80% または重要経路のテスト欠落／③破壊的変更に互換性対策（移行・段階リリース）なし／④パフォーマンスが大幅劣化（実測または推定インパクト大）／⑤危険な環境依存コード・設定の本番混入／⑥ログ・例外メッセージへの機密情報（PII・トークン・鍵）混入の恐れ
- **アンチパターン**：差し戻し基準該当を検知後も残り観点をレビューし総合判定する／カバレッジ 79% を「ほぼ 80%」と許容する／秘匿情報ログ出力を「マスキング前提だから」と黙認する

### step S-6: 承認可否判定
- **判定基準**：①必須修正（🔴）がすべて解消／②CI/CD 全通過／③（高・中リスクの場合）回帰主要テスト合格／④仕様・API・運用ドキュメントの必要更新が反映済、の 4 条件すべて充足時のみ「承認可」と判定する。1 条件でも未充足は「承認不可」と判定する
- **アンチパターン**：必須修正を残したまま「軽微だから承認」とする／CI 失敗を「flaky だから無視」と判定する／ドキュメント未更新を「後追いで OK」と判定する

## §6. 結果出力

完了時に以下を順に出力する。

1. **リスクレベル判定結果**：高／中／低と該当根拠（どの判定基準項目に該当したか）
2. **事前チェック結果**：6 項目それぞれの通過／未通過と未通過時の状態記録
3. **指摘一覧**：優先度別（🔴 必須 → 🟡 推奨 → 🟢 将来改善 の順）に、以下のテンプレート構造で列挙する
   ```
   [優先度] [カテゴリ：セキュリティ／性能／設計／可読性／テスト／エラー処理／その他]
   該当箇所：{ファイルパス}:{行番号}
   引用：{該当コード}
   問題点：{何が問題か}
   根拠：{規約・仕様・実証データ}
   推奨される解決策：{修正案・コード例}
   参考リンク：{該当する場合のみ}
   ```
4. **差し戻し基準該当性**：①〜⑥のいずれかに該当した場合は明示し、該当時点でレビューを中断した旨を記録する
5. **承認可否判定**：「承認可」または「承認不可」と判定し、4 条件の充足状態（充足／未充足の内訳）を併記する
6. **継続的改善メモ**：発見問題のカテゴリ集計／特に有効だったレビュー観点／プロセス改善提案／対応工数目安（レビュー時間・修正サイクル数）を記録する
7. **未解決事項**：TBD として残った項目（例：「仕様書未確定により API 契約変更の互換性影響を確定不能」）を表で出力する

異常時（差分取得失敗／対象ファイル不存在／リスク判定不能）は step S-1 以降を中断し、原因と再開条件を明示して報告する。
